SWE Conventions

Software engineering practices, codebase standards, and operational discipline.

Git

Commit messages

Use Conventional Commits. The type(scope): subject pattern is not decoration -- it enables automated changelogs and git bisect readability.

feat(auth): add JWT refresh rotation
fix(upload): reject files exceeding 10MB limit
docs(readme): add local dev setup section

Keep the subject under 72 characters. Use imperative mood ("add", not "added"). The body explains why, not what -- the diff shows what.

Branch naming

Include the ticket number and a short descriptor. Dashes, not underscores. Lowercase.

feat/AUTH-142-jwt-refresh
fix/UPLOAD-89-file-size-limit

Avoid branches named "fix-bug" or "test" -- they tell you nothing in git log --oneline three weeks from now.

Never commit

  • Secrets, API keys, tokens -- even in config files. Use .env and .gitignore.
  • Generated build artifacts (dist/, node_modules/).
  • IDE-specific files (.idea/, .vscode/settings.json unless shared).

Code style

Naming

Name things for what they do, not how they work. A function called processData tells you nothing. A function called normalizeUserAddress tells you everything.

// Bad
function handleStuff(data) { ... }
const arr = users.filter(u => u.a > 18);

// Good
function normalizeUserAddress(raw: RawAddress): NormalizedAddress { ... }
const eligibleUsers = users.filter(user => user.age > 18);

Functions

Do one thing. If you need a conjunction to describe what a function does ("parse and validate and save"), it does three things. Split it.

Keep functions short enough to fit on one screen without scrolling. If you exceed ~40 lines, extract a helper. Not because short is inherently better -- because long functions hide logic that deserves its own name.

Comments

Write code that doesn't need comments. When code is unclear, a better name or smaller function beats a comment. Comments rot -- they go stale as the code evolves and nobody updates them.

When you must comment, explain why, not what:

// Bad: increments counter by 1
counter += 1;

// Good: rate limiter requires non-zero minimum to avoid division by zero
counter += 1;

Testing

What to test

Test behavior, not implementation. A test that breaks when you refactor internals but the public contract is unchanged is a bad test. It slows you down and adds no confidence.

  • Unit tests -- pure logic, data transformations, edge cases.
  • Integration tests -- API endpoints, database queries, external service boundaries.
  • E2E tests -- critical user flows only (login, checkout, core CRUD).

Test structure

Follow Arrange-Act-Assert. Three clear phases. No interleaving actions and assertions. Each test should read like a sentence: "given X, when Y, then Z."

describe('UserService', () => {
  it('rejects duplicate email during registration', async () => {
    // Arrange
    await createUser({ email: 'alice@example.com' });

    // Act
    const result = await registerUser({ email: 'alice@example.com', ... });

    // Assert
    expect(result.error).toBe('Email already in use');
  });
});

Coverage targets

80% line coverage is a floor, not a goal. Coverage of critical paths (auth, payments, data integrity) should be 100%. Coverage of UI rendering or logging is less important -- 60% there is fine. Chase confidence, not numbers.

Code review

As the author

Self-review before requesting. Read your own diff. If you find something you want to change, change it -- don't leave it for the reviewer to catch. Write a description that explains the why and any decisions you considered.

As the reviewer

Look for correctness, not style (the linter handles style). Ask questions when intent is unclear. Suggest alternatives -- don't just say "this is wrong." Approve when the code is good enough, not when it's perfect. Perfect is the enemy of shipped.

Error handling

Handle errors at the right layer. Don't catch exceptions just to log them and swallow. Don't return null when the caller needs to know why it failed. Return typed errors or throw with context.

// Bad
try {
  return await fetchUser(id);
} catch (e) {
  console.log(e);
  return null;
}

// Good
try {
  return await fetchUser(id);
} catch (e) {
  throw new AppError('USER_NOT_FOUND', `User ${id} not found`, { cause: e });
}

Differentiate between errors that are expected (user not found, validation failed) and errors that are unexpected (network down, database corrupted). The first are business logic. The second need alerting.

Logging

Log structured data, not free-form strings. A log line that says "something went wrong" is useless at 3 AM. A log line that says {"event":"payment.failed","userId":"123","reason":"insufficient_funds","traceId":"abc-456"} is actionable.

Use log levels honestly. DEBUG for development. INFO for normal operations. WARN for recoverable issues. ERROR for failures that need attention. If everything is ERROR, nothing is.

Dependencies

Every dependency is code you don't own. Before adding one, ask: does this solve a real problem I have, or does it just save me 20 minutes? The library that saves 20 minutes today costs hours in maintenance, security patches, and breaking upgrades later.

  • Pin versions. Never use * or latest.
  • Check maintenance status (last commit, open issues, license).
  • Prefer the standard library. fetch over axios for simple GET. Date over moment.js for basic formatting.

Security

  • Never trust client input. Validate and sanitize everything at the API boundary.
  • Use parameterized queries. Never concatenate user input into SQL strings.
  • Store secrets in environment variables, not in code. Rotate keys regularly.
  • Apply least privilege. A service that reads data doesn't need write access.

The best security practice is the one you actually follow. A complex security protocol that nobody enforces is worse than a simple one that everyone does.
