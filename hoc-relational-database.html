Mô hình quan hệ & lý thuyết nền

Hai câu hỏi quyết định mọi câu SQL bạn viết: bảng trong PostgreSQL có phải là relation theo lý thuyết không, và ràng buộc nào DB tự giữ thay application. Học phần này để làm được: dịch phép toán đại số sang SQL đúng ngữ nghĩa, chọn khóa cho bảng mới, viết ràng buộc không để lọt dữ liệu sai, và sửa các query mất kết quả âm thầm vì NULL.

Relation và thứ SQL thực sự chạy

Codd định nghĩa relation là cặp (heading, body): heading là tập attribute không thứ tự, body là tập tuple không trùng; tuple là hàm từng phần attribute sang giá trị thuộc domain. Mọi thông tin nằm trong giá trị tuple, không có chỉ số hàng (Information Principle). Bài báo gốc: "A Relational Model of Data for Large Shared Data Banks", CACM 13(6):377–387, tháng 6/1970.

PostgreSQL 16 mượn khung lý thuyết rồi nới ba chỗ: cột có thứ tự, hàng cho phép trùng (bag), NULL là marker riêng. Ba chỗ đó giải thích phần lớn kết quả 'đúng ngữ pháp mà khác ý', nên cần phân biệt rõ ranh giới này trước khi đọc EXPLAIN.

  • Relation, tuple, attribute, domain

    Relation = (heading, body). Degree là số attribute, cardinality là số tuple. Chèn hai dòng giống hệt vào relation lý thuyết không tạo thêm tuple.

    Bẫy: coi bảng SQL là relation sẽ hiểu sai DISTINCT, NULL và ràng buộc. Trong SQL hai dòng giống hệt là hai rows, nên COUNT và COUNT(DISTINCT) trả hai kết quả khác nhau.

  • Đại số quan hệ

    σ → WHERE, Π → SELECT, ∪ → UNION, − → EXCEPT, × → CROSS JOIN, ⋈ → JOIN ... ON, ρ → alias AS, ÷ → NOT EXISTS lồng vì SQL không có toán tử division.

    Bẫy: đẳng thức (R∪S)−T = (R−T)∪(S−T) đúng trên set, sai trên bag. Projection trong đại số luôn khử trùng, SELECT thì không.

  • Tuple relational calculus

    Query dạng { t | P(t) } nói điều GÌ cần, không nói LÀM THẾ NÀO. Tính khai báo này giải thích vì sao planner đổi tự do kế hoạch mà kết quả giữ nguyên, và vì sao EXPLAIN đọc được mọi cách thực thi.

    Bẫy: quantifier chạy trên domain vô hạn cho kết quả vô hạn. Query phải safe: mọi biến nằm trong tập giá trị thực có trong database.

  • Bag semantics

    SELECT ALL là mặc định, kết quả multiset giữ bản sao; chỉ SELECT DISTINCT mới ra set.

    Bẫy: UNION ALL giữ bản sao, UNION khử trùng; trộn hai loại trong một câu báo cáo là lỗi phóng đại số dòng.

Ví dụ điển hình là division: tìm sinh viên đã làm TẤT CẢ task của project. SQL không có phép ÷ nên dịch bằng NOT EXISTS lồng, mô tả đúng nghĩa "không tồn tại task nào mà sinh viên chưa làm".

CREATE TABLE products(task text PRIMARY KEY);
INSERT INTO products VALUES ('db1'),('db2');
CREATE TABLE completed(student text, task text);
INSERT INTO completed VALUES
  ('fred','db1'),('fred','db2'),('fred','compiler'),
  ('eugene','db1'),('eugene','compiler'),
  ('sarah','db1'),('sarah','db2');

SELECT DISTINCT c.student FROM completed c
WHERE NOT EXISTS (
  SELECT 1 FROM products p
  WHERE NOT EXISTS (
    SELECT 1 FROM completed c2
    WHERE c2.student = c.student AND c2.task = p.task));
-- fred, sarah: eugene thiếu db2
Cách viết division thứ hai: COUNT + HAVING

Hai cách cho cùng kết quả; COUNT + HAVING dễ kiểm tra hơn nhưng bắt buộc có guard WHERE ... IN: nếu sinh viên có task ngoài danh sách products thì COUNT vẫn bằng nhau dù chưa làm đủ.

SELECT c.student FROM completed c
WHERE c.task IN (SELECT task FROM products)
GROUP BY c.student
HAVING COUNT(DISTINCT c.task) = (SELECT COUNT(*) FROM products);

SELECT và UNION có mặc định ngược nhau: SELECT ALL giữ bản sao, còn UNION/INTERSECT/EXCEPT mặc định loại bản sao, thêm ALL mới giữ. INTERSECT bind chặt hơn UNION và EXCEPT, nên q1 UNION q2 INTERSECT q3 hiểu là q1 UNION (q2 INTERSECT q3); trộn ba toán tử không có ngoặc cho kết quả khác ý định.

CREATE TABLE colors(name text);
INSERT INTO colors VALUES ('red'),('red'),('blue');

SELECT name FROM colors;                                  -- 3 dòng: ALL là mặc định
SELECT DISTINCT name FROM colors;                         -- 2 dòng
SELECT name FROM colors UNION ALL SELECT name FROM colors; -- 6 dòng
SELECT name FROM colors UNION SELECT name FROM colors;     -- 2 dòng: UNION khử trùng

Bốn loại khóa

Superkey
Tập attribute phân biệt mọi tuple của relation.
Candidate key
Superkey tối giản: bỏ một cột là mất tính duy nhất. Một relation có thể có nhiều candidate key.
Primary key
Một candidate key được chọn làm định danh. Trên PostgreSQL 16: PRIMARY KEY = UNIQUE + NOT NULL + tự tạo unique B-tree index, tối đa một PK mỗi bảng.
Foreign key
Tập cột trỏ tới candidate key của bảng khác, chỉ nhận NULL hoặc giá trị đang tồn tại. FK không tự tạo index ở bảng tham chiếu.

Khác lý thuyết một điểm thực tế: PostgreSQL không bắt buộc bảng có PK. Docs cho thấy khai báo product_no UNIQUE NOT NULL nhận dữ liệu tương đương product_no PRIMARY KEY. Bỏ PK là tự bỏ định danh hàng, khi đó mọi FK tham chiếu và mọi lệnh "sửa dòng này" trong code application đều dựa trên dữ liệu thiếu chắc chắn.

Bảng nối cho quan hệ M-N

Quan hệ nhiều-nhiều không nằm được ở một phía: muốn cặp (sinh viên, khóa học) chỉ xuất hiện đúng một lần thì phải có bảng nối mang khóa ghép. Cột thuộc về mối quan hệ như enrolled_at sống trong bảng nối, không thêm vào bảng cha.

CREATE TABLE students(id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE courses(id int PRIMARY KEY, title text NOT NULL);
CREATE TABLE enrollments(
  student_id int NOT NULL REFERENCES students(id),
  course_id  int NOT NULL REFERENCES courses(id),
  enrolled_at date NOT NULL DEFAULT CURRENT_DATE,
  PRIMARY KEY (student_id, course_id));

INSERT INTO students VALUES (1,'An'),(2,'Bình');
INSERT INTO courses VALUES (10,'SQL Nâng Cao');
INSERT INTO enrollments(student_id, course_id) VALUES (1,10),(2,10),(1,10);
-- dòng cuối lỗi 23505: khóa ghép chặn cặp (1,10) lần thứ hai

Khóa, ràng buộc và chỗ PostgreSQL tự quyết định

Ràng buộc là lớp cuối cùng giữ dữ liệu đúng khi code application có bug. Nguyên tắc chọn: biểu diễn được bằng logic quan hệ thì để DB kiểm tra, application chỉ lo phần không mô tả được trong schema.

  • Surrogate key và natural key

    Surrogate IDENTITY (int 4 byte) ổn định theo dòng và join ngắn; uuid cũng ổn định nhưng 16 byte, join và sort nặng hơn int. Natural key mang ý nghĩa nghiệp vụ. PostgreSQL có GENERATED ALWAYS AS IDENTITY theo chuẩn SQL và serial kiểu riêng, serial mở rộng thành integer + DEFAULT nextval + NOT NULL.

    Bẫy: serial không tự gắn UNIQUE hay PK. Sequence luôn có lỗ vì rollback vẫn tiêu thụ giá trị, nên không dùng surrogate làm thứ tự thời gian. Dùng surrogate mà quên UNIQUE trên natural key là mất ràng buộc nghiệp vụ.

  • Khóa ghép M-N

    Bảng nối gồm hai FK của hai phía cộng PK ghép (student_id, course_id); cột quan hệ như role, enrolled_at là attribute của mối quan hệ đó. Cột ghép trái dẫn sẵn cho mọi lookup theo cặp.

    Bẫy: thay PK ghép bằng surrogate đơn lẻ rồi quên UNIQUE(student_id, course_id) là mất định danh của relationship, join theo cặp trả hai dòng cho cùng một cặp.

  • Entity, referential, domain integrity

    Entity: PK unique và not null. Referential: FK chỉ nhận NULL hoặc giá trị tồn tại. Domain: CREATE DOMAIN kèm CHECK, NOT NULL, DEFAULT; UNIQUE tạo unique B-tree index, mặc định NULLS DISTINCT nên cột UNIQUE nhận bao nhiêu NULL tùy ý.

    Bẫy: CHECK chỉ chạy khi INSERT hoặc UPDATE và coi TRUE lẫn UNKNOWN là pass, nên CHECK (price > 0) không chặn NULL; CHECK không được tham chiếu bảng khác.

  • ON DELETE, ON UPDATE và DEFERRABLE

    Năm action: NO ACTION (mặc định), RESTRICT, CASCADE, SET NULL, SET DEFAULT. SET CONSTRAINTS {ALL|tên} {DEFERRED|IMMEDIATE} đổi thời điểm kiểm tra cho UNIQUE, PRIMARY KEY, REFERENCES, EXCLUDE.

    Bẫy: khác biệt duy nhất giữa NO ACTION và RESTRICT là khả năng hoãn: chỉ NO ACTION defer được đến commit, RESTRICT không bao giờ. NOT NULL và CHECK luôn kiểm tra ngay bất kể SET CONSTRAINTS.

  • FK không tự tạo index

    PK và UNIQUE tự tạo unique B-tree index, cột FK thì không. Không index cột FK thì DELETE/UPDATE trên bảng bị tham chiếu phải quét toàn bộ bảng tham chiếu.

    Bẫy: schema chỉ có FK, càng nhiều dữ liệu thì xóa đơn hàng càng chậm. Thêm index cho cột FK trước khi bật ON DELETE CASCADE.

PostgreSQL 16 không tự tạo index cho cột foreign key của bảng tham chiếu, khác PK và UNIQUE vốn có unique B-tree index sẵn. DELETE FROM orders ở đoạn trên sẽ quét order_items nếu order_id chưa có index riêng. Chạy EXPLAIN và tìm Seq Scan để xác nhận; cách thêm index nằm ở phần Query optimizer & EXPLAIN.

Quy trình dùng khi thêm bảng mới vào schema:

  1. Tìm candidate key: liệt kê tập cột phân biệt mọi dòng, bỏ từng cột cho tới khi còn tối giản. Cột nào bỏ ra mà vẫn unique thì chưa thuộc candidate key.
  2. Chọn primary key: một candidate key ổn định nhất, giữ natural key dưới UNIQUE constraint kể cả khi PK là surrogate.
  3. Quyết định surrogate: thêm IDENTITY chỉ khi natural key dài, nhiều cột hoặc hay đổi; không dùng sequence làm thứ tự thời gian vì rollback vẫn tiêu thụ giá trị và để lại lỗ.
  4. Dựng quan hệ M-N: bảng nối gồm hai FK cộng PK ghép, không thay bằng surrogate đơn lẻ.
  5. Khai báo hành động FK: viết rõ ON DELETE, ON UPDATE theo logic nghiệp vụ thay vì nhận mặc định NO ACTION.
  6. Index cột FK: thêm index trước khi bật CASCADE để DELETE, UPDATE trên bảng cha không quét bảng tham chiếu.

Tập, túi và ba giá trị logic

WHERE chỉ giữ dòng khi predicate bằng TRUE, UNKNOWN bị loại ngang FALSE. So sánh với NULL luôn ra UNKNOWN nên x = NULL không bao giờ đúng, phải dùng IS NULL; IS DISTINCT FROM không bao giờ trả NULL (1 IS DISTINCT FROM NULL là true).

Bẫy cổ điển là NOT IN, nó không phải phủ định của IN khi subquery trả về NULL.

CREATE TABLE t(id int);
INSERT INTO t VALUES (1),(2),(NULL);

SELECT 1 AS x WHERE 3 NOT IN (SELECT id FROM t WHERE id IS NOT NULL); -- 1 dòng
SELECT 1 AS x WHERE 3 NOT IN (SELECT id FROM t);                      -- 0 dòng: có NULL thì UNKNOWN
SELECT 1 AS x WHERE NOT EXISTS (SELECT 1 FROM t WHERE id = 3);        -- 1 dòng: an toàn với NULL
SELECT 1 AS x WHERE 1 IS DISTINCT FROM NULL;                          -- true

expr NOT IN (subquery) trả UNKNOWN khi expr không bằng dòng nào nhưng subquery có ít nhất một NULL, và WHERE coi UNKNOWN như FALSE nên mất kết quả mà không báo lỗi. Sửa bằng NOT EXISTS hoặc lọc NULL trong subquery. CHECK (price > 0) mắc cùng cơ chế: CHECK(NULL > 0) = UNKNOWN nên vẫn pass.

Ngoại lệ với outer join: ON xử lý trước, WHERE xử lý sau

Predicate trong ON áp trước bước thêm dòng NULL-extend, predicate trong WHERE áp sau. Chuyển điều kiện từ ON sang WHERE với LEFT JOIN sẽ loại luôn dòng không khớp, đổi kết quả chứ không chỉ đổi cách viết.

CREATE TABLE t1(num int, name text);
INSERT INTO t1 VALUES (1,'a'),(2,'b'),(3,'c');
CREATE TABLE t2(num int, value text);
INSERT INTO t2 VALUES (1,'xxx'),(3,'yyy'),(5,'zzz');

SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num AND t2.value > 'xxx';
-- 3 dòng: (1,'a') bị ON loại điều kiện nhưng vẫn giữ, cột của t2 pad NULL
SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num WHERE t2.value > 'xxx';
-- 1 dòng (3,'c',3,'yyy'): WHERE loại luôn dòng không khớp

Thời điểm kiểm tra ràng buộc dưới luồng ghi song song và SET CONSTRAINTS DEFERRED nằm ở phần Transaction & concurrency; cách planner dùng index trên các khóa vừa chọn nằm ở phần Query optimizer & EXPLAIN.

Thiết kế schema & chuẩn hóa

Mỗi dạng chuẩn bị vi phạm là một lớp anomaly cụ thể: sửa một dòng phải nhớ sửa N dòng khác, xóa một dòng làm mất thông tin không liên quan đến nó. Phần này để làm được bốn việc: chuyển ER thành bảng có khóa đúng, chỉ ra vi phạm 2NF/3NF/BCNF trên schema thật, quyết định khi nào denormalize có chủ đích, và chọn kiểu dữ liệu không làm sai số tiền.

Từ ER đến bảng quan hệ

PostgreSQL không có entity, chỉ có table và constraint. Chọn khóa, đặt FK, quyết định có bảng nối hay không là bước quyết định mọi thứ về sau — chuẩn hóa chỉ dọn dẹp trên cấu trúc đó. Bốn ánh xạ dưới đây là đủ cho phần lớn schema giao dịch.

Armstrong axioms và attribute closure

Phụ thuộc hàm (FD) X → Y không được kiểm bằng mắt. Ba luật Armstrong sinh toàn bộ F+ từ một tập FD gốc: reflexivity (X → X, tầm thường, luôn đúng), augmentation (X → Y suy ra XZ → YZ), transitivity (X → Y và Y → Z suy ra X → Z). Từ đó định nghĩa hình bao (attribute closure) X⁺ = mọi cột suy ra được từ X theo F; X → Y đúng trong F+ đúng khi Y ⊆ X⁺. Kiểm candidate key bằng cách tính X⁺: X⁺ bằng toàn bộ quan hệ thì X là superkey, bỏ bớt một cột mà X⁺ vẫn đủ thì không phải minimal, tức không phải candidate key.

-- R(A,B,C,D), F = {A→B, B→C, C→D}. Kiểm FD bằng data:
-- projection theo determinant không được có nhiều giá trị khác nhau cho cột dependent
CREATE TABLE emp_demo (e int, d int, s int, PRIMARY KEY (e));
INSERT INTO emp_demo VALUES (1,10,100),(2,20,200);

-- e→d đúng: 0 dòng vi phạm
SELECT e FROM emp_demo GROUP BY e HAVING count(DISTINCT d) > 1;

-- Chèn dòng phá d→s: d=10 map cả s=100 lẫn s=999
INSERT INTO emp_demo VALUES (3,10,999);
SELECT d FROM emp_demo GROUP BY d HAVING count(DISTINCT s) > 1;  -- trả về d=10
-- Tính closure bằng recursive CTE, bitmask: a=1 b=2 c=4 d=8
-- closure({b}) theo F={A→B,B→C,C→D} là {b,c,d} = 14, thiếu a nên không phải superkey
WITH RECURSIVE fds(lhs, rhs) AS (VALUES (1,2),(2,4),(4,8)),
     closure(cur) AS (
       SELECT 2
       UNION ALL
       SELECT c.cur | f.rhs FROM closure c JOIN fds f ON (f.lhs & c.cur) = f.lhs
       WHERE (c.cur | f.rhs) <> c.cur
     )
SELECT max(cur) AS closure_b, (max(cur) & 15) = 15 AS is_superkey FROM closure;
-- closure_b = 14, is_superkey = false
-- closure({a}) = 15, is_superkey = true  →  a là candidate key duy nhất

Bỏ qua closure rồi phán "cột này có vẻ phụ thuộc khóa kia" là cách 2NF/3NF bị vi phạm mà không ai biết: mỗi lần thêm dòng mới là một lần FD bị phá âm thầm, không constraint nào ném lỗi. Kiểm FD trên data bằng GROUP BY/HAVING chỉ phủ dòng đang có; FD là ràng buộc schema, phải được enforce bằng PK/UNIQUE hoặc CHECK ở tầng DB, không phải bằng query đếm lúc develop.

Sáu dạng chuẩn và bẫy tương ứng

  • 1NF — giá trị nguyên tử

    Không multi-value trong một cell, không chuỗi kiểu 'a,b,c'. Mỗi giá trị lẻ cần một dòng để CHECK, UNIQUE, JOIN và index hoạt động theo giá trị đó.

    Bẫy: WHERE tags LIKE '%sql%' vừa match 'mysql' vừa quét toàn bảng; UPDATE một tag là read-modify-write cả chuỗi. Junction post_tags (post_id, tag) chặn trùng cặp, nhưng PK trái dẫn (post_id, tag) không dùng được cho WHERE tag — thêm index riêng trên tag (hoặc cặp (tag, post_id)) thì planner mới đi Bitmap Index Scan.

  • 2NF — không phụ thuộc một phần khóa

    Chỉ đặt vấn đề khi PK ghép: cột không khóa phụ thuộc nửa khóa là vi phạm. PK đơn không có khái niệm phụ thuộc một phần.

    Bẫy: @@id([tenant_id, user_id]) mà display_name chỉ phụ thuộc user_id: đổi tên user phải update N dòng. Tách bảng users với PK là user_id, giữ FK ở bảng cũ.

  • 3NF — không phụ thuộc bắc cầu

    Cột không khóa không được quyết định cột không khóa khác. orders có zip và city với FD zip → city; zip không phải khóa nên city phải chuyển sang bảng tra zip_codes.

    Bẫy: Đổi city của một zip phải sửa mọi đơn mang zip đó, sót một dòng là báo cáo tự mâu thuẫn mà không constraint nào bắt được.

  • BCNF — mọi determinant là superkey

    Mạnh hơn 3NF ở chỗ bỏ ngoại lệ cho prime attribute. Vi phạm kinh điển: rate_type → court, với rate_type nằm trong candidate key nhưng không phải superkey.

    Bẫy: Tách BCNF có thể mất dependency preservation ({AB→C, C→B} phải kiểm qua JOIN); giữ 3NF cộng constraint ở tầng app đôi khi đúng hơn là ép tách.

  • 4NF — không multivalued dependency

    Hai multiset độc lập trên cùng determinant: restaurant xác định đa trị variety và area. Đặt chung một bảng, 3 variety nhân 4 area sinh 12 dòng cho một nhà hàng.

    Bẫy: Một multivalued dependency đơn lẻ thì junction hai cột là đủ; 4NF chỉ bắt đầu nói khi có từ hai dependency độc lập cùng determinant.

  • 5NF — join dependency

    Constraint xuyên ba cột: salesman chào brand X thì phải chào mọi product type của brand X. Join hai bảng bất kỳ sinh cặp chưa từng tồn tại, chỉ join đủ ba projection mới lossless.

    Bẫy: Ép 5NF làm mỗi read join thêm bảng, app gánh consistency mà DB không enforce. Ngoài master-data, dừng ở 3NF/BCNF là mặc định của phần lớn hệ thống.

Quy trình soi một schema thật

  1. Liệt kê functional dependency từ business rule và các UNIQUE đang có: cột nào quyết định cột nào.
  2. Với mỗi FD X → Y không tầm thường: X có phải superkey (hoặc prime attribute, xét riêng cho 3NF) không? Không thì schema đang vi phạm.
  3. X là một phần của PK ghép? Đó là 2NF; tách cột phụ thuộc ra bảng riêng với PK là phần khóa đó.
  4. Hai FD độc lập cùng determinant? Kiểm tra 4NF trước khi thêm cột thứ ba vào bảng nối.
  5. Ước giá chi phí tách: mỗi lần đọc thêm một JOIN, mỗi constraint mất dependency preservation là một invariant chuyển sang app. Chỉ tách khi anomaly đắt hơn chi phí join.

Denormalization có chủ đích

Báo cáo read-heavy không nên join năm bảng mỗi request. Ba cách xếp theo rủi ro tăng dần: materialized view refresh định kỳ, summary table rebuild, trigger cập nhật ngay khi ghi. Cách cuối đúng nhất về độ tươi của dữ liệu nhưng phải test race giữa hai transaction ghi đồng thời; hai cách đầu chấp nhận độ trễ.

CREATE TABLE payments (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  created_at   timestamptz NOT NULL DEFAULT now(),
  amount_cents bigint NOT NULL CHECK (amount_cents > 0)
);

CREATE MATERIALIZED VIEW mv_daily_sales AS
  SELECT date_trunc('day', created_at) AS day, sum(amount_cents) AS total
  FROM payments GROUP BY 1;

CREATE UNIQUE INDEX ON mv_daily_sales (day);  -- bắt buộc cho REFRESH CONCURRENTLY
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales;  -- reader không bị block

Grain của bảng tổng hợp phải trả lời câu hỏi sẽ được hỏi, không phải câu hỏi đang hỏi: tổng theo ngày không slice được theo user, cần cả hai thì grain là (day, user_id) hoặc dựng hai view. REFRESH CONCURRENTLY cần unique index trên cột khóa, thiếu là lỗi ngay lúc chạy.

Tiền: numeric hoặc integer cents, không float

float8 là xấp xỉ nhị phân nên so sánh bằng có thể trả false với hai số ai cũng biết là bằng nhau; numeric chính xác. Chọn kiểu theo ràng buộc: BIGINT cents khi cần tốc độ và không có phần lẻ, NUMERIC(12,2) cho đơn currency, NUMERIC(19,4) khi multi-currency.

SELECT 0.1::float8 + 0.2::float8 = 0.3::float8;  -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3;        -- true
SELECT round(2.5::numeric), round(2.5::float8);  -- 3, 2: numeric tròn xa 0, float8 half-to-even
SELECT 1999 / 100;    -- 19: integer division
SELECT 1999 / 100.0;  -- 19.99
amount_cents BIGINT
Chia 100 khi hiển thị. Sum và so sánh chính xác, chi phí thấp hơn numeric. Đặt tên có hậu tố _cents để không ai nhân nhầm hai lần.
NUMERIC(p, s)
Chính xác, làm tròn xa 0 (2.5 → 3). p tối đa 1000; 12,2 đủ cho VND/USD, 19,4 cho tỉ giá.
serial
Chỉ là NOT NULL cộng DEFAULT nextval, không tự UNIQUE, không tự là PK. Identity GENERATED ALWAYS từ chối giá trị người dùng trừ khi INSERT ghi OVERRIDING SYSTEM VALUE.
float4 / float8
Xấp xỉ; dùng cho đo lường khoa học, không cho số tiền cần đối soát.

Cây phân cấp: adjacency list và recursive CTE

parent_id là lựa chọn ghi rẻ nhất: thêm node, đổi cha là một UPDATE một dòng. Đọc subtree cần recursive CTE. Dữ liệu có vòng làm UNION ALL chạy vô hạn, nên từ PostgreSQL 14 dùng CYCLE clause để cắt vòng và đánh dấu thay vì tự viết mảng path.

WITH RECURSIVE tree AS (
  SELECT id, parent_id, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, t.depth + 1
  FROM categories c JOIN tree t ON c.parent_id = t.id
) CYCLE id SET is_cycle USING path
SELECT id, depth, is_cycle FROM tree WHERE depth < 8;

Khi subtree query là truy vấn chính (menu, phân loại), ltree lật ngược đánh đổi: path dạng Top.Science.Astronomy cho descendants bằng toán tử <@ trong một câu kèm GiST index; cái giá là di chuyển node phải update path của toàn bộ subtree.

Soft delete: unique index phải là partial

deleted_at NULL nghĩa là còn sống. UNIQUE(email) đầy đủ chặn luôn email của user đã xóa; partial unique WHERE deleted_at IS NULL là bản đúng. Mọi query đọc phải lọc deleted_at IS NULL, gom vào view hoặc tầng repository để không sót chỗ nào.

CREATE UNIQUE INDEX users_email_active_unique
  ON users (lower(email)) WHERE deleted_at IS NULL;

INSERT INTO users (email) VALUES ('a@x.com')
ON CONFLICT (lower(email)) WHERE deleted_at IS NULL
DO UPDATE SET email = EXCLUDED.email
RETURNING id;  -- arbiter phải khai đúng cả biểu thức lẫn WHERE

EXCLUDE constraint: ràng buộc không giao nhau

UNIQUE chặn hai dòng trùng giá trị, nhưng không diễn đạt được "hai khoảng thời gian của cùng một phòng không được chồng". EXCLUDE trên opclass GiST làm việc đó: mỗi dòng mới phải không thỏa operator so với mọi dòng cũ đang có. btree_gist mở rộng GiST để index được scalar (int, text) cạnh range, vì GiST mặc định chỉ biết range/geometry.

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE bookings (
  room_id int NOT NULL,
  during  tstzrange NOT NULL,
  guest   text NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

-- Phòng 101, 2 khoảng không chồng: OK
INSERT INTO bookings VALUES
  (101, tstzrange('2026-01-01 14:00+07','2026-01-03 12:00+07'), 'An'),
  (102, tstzrange('2026-01-02 14:00+07','2026-01-04 12:00+07'), 'Chi');

-- Cùng phòng 101, khoảng chồng lên: lỗi exclusion
INSERT INTO bookings VALUES
  (101, tstzrange('2026-01-02 14:00+07','2026-01-04 12:00+07'), 'Binh');

Bẫy: && là "overlap", không phải "contains": chèn một khoảng lọt thỏm bên trong khoảng đang có vẫn bị chặn vì hai range giao nhau. Muốn chỉ chặn đúng overlap một-ở-trong-một thì operator phải đổi thành @> / <@ và viết policy khác. Constraint kiểm tra ngay khi INSERT, nên chèn hàng loạt khoảng chồng nhau trong cùng một statement sẽ fail ở dòng đầu; cần defer thì đặt DEFERRABLE INITIALLY DEFERRED rồi SET CONSTRAINTS ALL DEFERRED trong transaction.

Nguồn: PostgreSQL 16 — CREATE TABLE … EXCLUDE · PostgreSQL 16 — btree_gist

Foreign key không cascade theo soft delete: parent đã đánh dấu xóa vẫn "còn sống" trong mắt constraint, nên quy tắc dọn dẹp phải nằm ở tầng ứng dụng hoặc job định kỳ.

SCD Type 2: lịch sử version cho dimension

Dimension đổi theo thời gian (tier khách hàng) cần báo cáo point-in-time thì phải giữ version. Partial unique trên is_current enforce "mỗi entity đúng một version hiện tại" ở tầng DB thay vì tin vào code.

CREATE TABLE customer_scd (
  version_id  bigserial PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  tier        text NOT NULL,
  valid_from  timestamptz NOT NULL,
  valid_to    timestamptz,
  is_current  boolean NOT NULL DEFAULT true
);
CREATE UNIQUE INDEX ON customer_scd (customer_id) WHERE is_current;

Fact table trỏ version_id chứ không trỏ customer_id: join theo customer_id gộp mọi version của khách, count và sum kết quả gấp số version mà không lỗi nào được ném ra. Version cũ ở lại làm lịch sử, cần partition hoặc archive khi số dòng lớn.

Multi-tenant: tenant_id, RLS và GRANT

Shared schema đặt cột tenant_id trên mọi bảng business: một bộ migration, một lịch backup, join support giữa hai tenant chạy được ngay. Cái giá là mọi truy vấn phải lọc theo tenant, và chỗ lọc đó không được lệch — lệch một dòng policy là rò dữ liệu cross-tenant. Schema-per-tenant (hoặc database-per-tenant) đảo đánh đổi: schema-per-tenant vẫn chung catalogue và chỉ cài extension một lần cho cả database, nhưng đổi DDL phải chạy trên từng schema của N tenant; database-per-tenant mới tách catalogue và extension theo tenant, đổi DDL phải chạy trên N database. Cả hai đều khiến báo cáo gộp tenant phải nối tay. SaaS multi-tenant trên Citus ở phần Phân tán vẫn đi theo mẫu tenant_id; distribution key gắn với tenant thì dữ liệu mới locality khi query.

Row-Level Security đẩy việc lọc xuống tầng database. Bật RLS trên bảng chưa có policy thì mặc định là default-deny: vai trò vẫn giữ quyền table-level nhưng thấy 0 dòng. CREATE POLICY khai FOR ALL (mặc định) cho SELECT, INSERT, UPDATE, DELETE, hoặc tách FOR SELECT / FOR INSERT / FOR UPDATE khi quyền đọc và quyền ghi khác expression (báo cáo được đọc nhiều tenant nhưng ghi chỉ trong một tenant). USING lọc dòng đã tồn tại; WITH CHECK lọc dòng sẽ được ghi vào, và chỉ khai USING thì WITH CHECK lấy mặc định expression đó. Siêu user và role BYPASSRLS luôn bypass; table owner bypass theo mặc định, FORCE ROW LEVEL SECURITY buộc cả owner tuân policy, cần bật khi chính account sở hữu bảng cũng là account chạy query nghiệp vụ.

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::int);

-- owner bypass theo mặc định; FORCE để cả owner bị policy lọc
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_rw;
GRANT SELECT ON orders TO report_ro;  -- role báo cáo chỉ đọc

Trong ứng dụng, đặt tenant vào session GUC ngay trong transaction: BEGIN; SET LOCAL app.tenant_id = 42; -- các query; COMMIT;. SET LOCAL hết hiệu lực khi transaction kết thúc, committed hay rolled back, nên không rò sang request kế tiếp. Ngược lại, SET mặc định là SESSION và sống tới hết session; dưới pgbouncer transaction pooling mỗi transaction có thể vào một server connection khác, còn server_reset_query bị bỏ qua ở chế độ pooling đó, nên SET session-level không dùng được. Session pooling giữ connection cho client tới khi ngắt nên SET không sang người khác, nhưng mỗi request vẫn phải set lại tenant của chính mình. GRANT theo least privilege: role app_rw chỉ nhận SELECT/INSERT/UPDATE/DELETE trên bảng nghiệp vụ, role report_ro chỉ nhận SELECT, không gộp hai việc vào một role vì sửa policy cho báo cáo sẽ nới luôn quyền ghi của app.

Ba chỗ hỏng thường gặp: quên SET LOCAL khiến current_setting('app.tenant_id') ném lỗi (missing_ok=false là mặc định); nếu gọi với missing_ok=true thì trả NULL, và NULL luôn fail predicate nên trả 0 dòng cho cả tenant đúng; khai policy FOR ALL khi USING cho phép đọc nhiều tenant mà không tách WITH CHECK chặt hơn cho INSERT: WITH CHECK lấy mặc định expression USING rộng nên ghi nhầm tenant_id vẫn qua, còn USING đơn-tenant chặt như ví dụ trên thì mặc định đã chặn (INSERT sai tenant trả lỗi new row violates row-level security policy); bật RLS nhưng để role app nằm chung nhóm owner mà quên FORCE ROW LEVEL SECURITY, owner bypass lặng lẽ mở toàn bộ bảng. Kiểm tra thực tế: kết nối bằng đúng role app, SELECT count(*) không WHERE, số dòng phải đúng bằng số dòng của tenant đang set.

CREATE VIEW: updatable, WITH CHECK OPTION, security_invoker

View thường là query đã đặt tên, không lưu data. Một view là updatable khi nó đọc đúng một bảng, không aggregate, không DISTINCT, không UNION/GROUP BY/HAVING/window — mọi cột INSERT/UPDATE đi thẳng xuống bảng base. Vi phạm điều kiện đó, PostgreSQL từ chối ghi với thông báo rõ ràng thay vì đoán.

-- Updatable: WHERE đơn giản trên một bảng
CREATE VIEW v_orders_t1 AS
  SELECT id, tenant_id, total FROM orders_v WHERE tenant_id = 1;
INSERT INTO v_orders_t1 (tenant_id, total) VALUES (1, 55);  -- OK

-- Không updatable: GROUP BY
CREATE VIEW v_orders_agg AS
  SELECT tenant_id, count(*) AS n FROM orders_v GROUP BY tenant_id;
-- INSERT INTO v_orders_agg ... →
-- ERROR:  cannot insert into view "v_orders_agg"
-- DETAIL:  Views containing GROUP BY are not automatically updatable.

WITH CHECK OPTION buộc mọi dòng INSERT/UPDATE qua view phải thỏa WHERE của chính view. Không có nó, chèn tenant_id=2 qua view WHERE tenant_id=1 vẫn qua, dòng đó biến mất khỏi view và data base lệch ý định khai báo.

CREATE VIEW v_orders_t1_chk AS
  SELECT id, tenant_id, total FROM orders_v WHERE tenant_id = 1
  WITH CHECK OPTION;

INSERT INTO v_orders_t1_chk (tenant_id, total) VALUES (2, 10);
-- ERROR:  new row violates check option for view "v_orders_t1_chk"
-- DETAIL:  Failing row contains (6, 2, 10.00).

Từ PostgreSQL 15, security_invoker = true đổi quyền chạy của view. Mặc định view chạy bằng quyền của người tạo (definer): nếu người tạo là owner bảng và bảng bật RLS nhưng không FORCE, owner bypass policy, mọi người đọc qua view đều thấy toàn bộ dòng cross-tenant. Đặt WITH (security_invoker = true) thì view chạy bằng quyền người gọi, RLS của người gọi được áp dụng.

-- Owner tạo 2 view trên bảng có RLS (USING tenant_id=1), KHÔNG FORCE
CREATE VIEW v_rls_definer AS SELECT * FROM rls_demo;
CREATE VIEW v_rls_invoker WITH (security_invoker = true) AS SELECT * FROM rls_demo;

-- Người dùng app (không phải owner):
SELECT count(*) FROM v_rls_definer;   -- 3 (owner bypass, thấy mọi tenant)
SELECT count(*) FROM v_rls_invoker;   -- 2 (policy được áp, đúng tenant)

RLS ở multi-tenant section phía trên chỉ có hiệu lực khi người chạy query không nằm trong nhóm bypass. View mặc định definer-rights chính là lỗ hổng bypass đó: owner view thấy mọi dòng, người đọc qua view thấy theo owner, policy RLS thành trang trí. Khi view expose bảng có tenant_id, luôn khai security_invoker = true trừ khi chủ đích gom data nhiều tenant cho role báo cáo đã được cấp riêng.

SQL chuyên sâu: ngữ nghĩa & mẫu truy vấn

Hai lỗi đắt nhất trong query backend là ngữ nghĩa NULL (three-valued logic) và vị trí điều kiện lọc trong JOIN: cú pháp đúng mà kết quả vẫn mất hàng. Học phần này để làm được anti-join không mất hàng, đọc EXPLAIN query JOIN, chọn OFFSET hay keyset, và viết upsert atomic trên PostgreSQL 16.

Năm khái niệm quyết định kết quả query

  • Three-valued logic

    So sánh với NULL trả UNKNOWN, không phải FALSE. AND có absorbing FALSE, OR có absorbing TRUE, và WHERE chỉ giữ hàng có giá trị TRUE.

    Bẫy: NOT IN (subquery) ≡ <> ALL: subquery chứa NULL là biểu thức trả UNKNOWN, không TRUE. Sửa bằng NOT EXISTS.

  • ON trước, WHERE sau

    Restriction trong ON áp dụng trước khi join, restriction trong WHERE áp dụng sau join. Với outer join, hai chỗ cho kết quả khác nhau.

    Bẫy: Lọc cột phải trong WHERE sau LEFT JOIN = vô tình INNER. NATURAL JOIN âm thầm đổi join key khi schema đổi.

  • EXISTS là semi-join

    EXISTS trả TRUE khi subquery có ≥1 hàng và thường dừng ở hàng đầu. IN ≡ = ANY, NOT IN ≡ <> ALL. Planner thường convert correlated subquery sang semi-join.

    Bẫy: Scalar subquery trong SELECT list chạy cho từng hàng outer: N+1 ngay bên trong database.

  • CTE không còn fence từ PG12

    CTE side-effect-free tham chiếu đúng 1 lần được inline vào query cha; tham chiếu nhiều hơn 1 lần mặc định MATERIALIZED, force bằng MATERIALIZED / NOT MATERIALIZED.

    Bẫy: Trước PostgreSQL 12, CTE luôn là optimization fence nên predicate không pushdown được.

  • Aggregate trả NULL khi 0 hàng

    sum, min, max và array_agg trên 0 hàng trả NULL; chỉ count(*) trả 0.

    Bẫy: GREATEST/LEAST trong PostgreSQL bỏ qua NULL, khác SQL standard: chuẩn trả NULL ngay khi có một đối số NULL.

NULL và three-valued logic: WHERE chỉ giữ TRUE

Mọi câu WHERE, JOIN, IN và aggregate chạy trên thang TRUE / FALSE / UNKNOWN. COALESCE trả giá trị đầu tiên không-NULL; NULLIF(a,b) trả NULL khi a = b.

SELECT 1 WHERE 1 = NULL;                 -- 0 hàng: UNKNOWN bị loại như FALSE
SELECT NULL AND false, NULL OR true;     -- false, true
SELECT GREATEST(1, NULL), GREATEST(NULL, NULL);  -- 1, NULL (PG bỏ qua NULL)

NOT IN (subquery) ≡ <> ALL: nếu subquery chứa một dòng NULL và không có giá trị nào match, biểu thức trả UNKNOWN thay vì TRUE, WHERE loại sạch kết quả. Sửa bằng NOT EXISTS hoặc IS NOT DISTINCT FROM. Row value thì IS NULL true khi hàng NULL hoặc tất cả field NULL, còn IS NOT NULL chỉ true khi hàng và mọi field cùng không NULL, hai điều không phải nghịch đảo khi hàng trộn NULL.

-- Trả 0 hàng khi b.a_id có bất kỳ NULL nào; NOT EXISTS thì an toàn:
SELECT a.id FROM a WHERE a.id NOT IN (SELECT b.a_id FROM b);
SELECT a.id FROM a
WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id);

JOIN: điều kiện lọc nằm ở ON hay WHERE

Tài liệu PostgreSQL 16 về table expressions chốt: restriction trong ON xử lý trước khi join, trong WHERE xử lý sau. Với INNER JOIN hai cách thường cho cùng kết quả; với outer join thì khác, vì hàng null-pad từ nửa ngoài đã bị WHERE loại trước khi bạn thấy chúng.

Bốn loại join và nơi đặt filter cột phải

INNER JOINChỉ hàng match cả hai phíaON hay WHERE đều được

-- Sai: WHERE loại hàng null-pad, vô tình biến LEFT thành INNER
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.total > 100;

-- Giữ khách chưa có order: filter nằm trong ON
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id AND o.total > 100;

-- Anti-join tường minh
SELECT c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

Khách chưa từng order biến mất khỏi báo cáo sau khi ai đó thêm WHERE o.total > 100 cho chắc: NULL > 100 là UNKNOWN nên WHERE loại hàng. Anti-join thì viết NOT EXISTS tường minh; NATURAL JOIN nên tránh vì đổi schema là đổi join key.

Subquery: EXISTS, IN, ANY, ALL

EXISTS trả TRUE khi subquery trả ≥1 hàng và thường dừng ở hàng đầu. ALL trả TRUE khi mọi so sánh TRUE, với subquery rỗng là TRUE. Correlated subquery đánh giá lặp theo từng hàng; planner thường convert sang semi-join, không phải hình thức nào cũng vậy.

-- Semi-join: khách có đơn hàng lớn hơn 1000
SELECT c.name FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id AND o.total > 1000);

Không để function có side-effect (nextval, hàm volatile) trong subquery, planner có thể evaluate sớm hoặc dừng giữa chừng. Scalar subquery trong SELECT list chạy một lần scan mỗi hàng outer; gộp bằng aggregate rồi LEFT JOIN.

Aggregate đa tầng: FILTER, ROLLUP, GROUPING()

WHERE lọc hàng trước khi group, HAVING lọc sau aggregate. Thứ tự đánh giá:

  1. FROM / JOIN dựng hàng nguồn, null-pad nếu outer join.
  2. WHERE lọc hàng, UNKNOWN bị loại như FALSE.
  3. GROUP BY gom nhóm; HAVING lọc sau aggregate.
  4. Window functions tính trên group rows; ORDER BY và LIMIT / OFFSET cuối cùng.
SELECT region, product,
       sum(amount) AS total,
       grouping(region) AS is_grand_total,
       count(*) FILTER (WHERE status = 'paid') AS paid_cnt
FROM sales
GROUP BY ROLLUP (region, product);

Cột vắng trong grouping set trả NULL, trùng hệt NULL dữ liệu, nên GROUPING() phân biệt hàng subtotal với hàng dữ liệu: trả 1 khi expr không có trong set hiện tại. ROLLUP(a,b,c) sinh 4 grouping set (n+1), CUBE sinh 8 (2^n). HAVING không nhận alias cột aggregate, viết lại biểu thức.

Window functions: xếp hạng, running total, frame

ROW_NUMBER luôn unique 1..n, RANK có gap sau tie, DENSE_RANK không gap. Frame mặc định khi có ORDER BY chạy từ đầu partition đến last peer của hàng hiện tại, vì thế last_value trả "giá trị đến hàng hiện tại" chứ không phải hàng cuối partition; muốn cả partition thì chỉ định ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. PostgreSQL chưa có IGNORE NULLS.

SELECT emp_name, dept, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
       salary - LAG(salary) OVER (PARTITION BY dept ORDER BY salary) AS delta,
       SUM(salary)  OVER (PARTITION BY dept
                          ORDER BY salary
                          ROWS UNBOUNDED PRECEDING) AS running_dept
FROM employees;
Mở rộng: gap-and-island bằng một câu

Lấy DISTINCT ngày, trừ đi ROW_NUMBER (nhân đơn vị khoảng): các ngày liên tiếp tạo cùng một key group, GROUP BY key gom mỗi khoảng.

WITH t AS (
  SELECT d, d - (ROW_NUMBER() OVER (ORDER BY d))::int * interval '1 day' AS grp
  FROM (SELECT DISTINCT d FROM events) s
)
SELECT min(d) AS range_start, max(d) AS range_end
FROM t GROUP BY grp;

CTE và recursive CTE từ PostgreSQL 12

Trước PostgreSQL 12, CTE luôn là optimization fence: predicate của query cha không pushdown vào CTE. Từ PG12, CTE side-effect-free tham chiếu đúng 1 lần được inline vào query cha, tham chiếu nhiều hơn 1 lần mặc định MATERIALIZED; MATERIALIZED / NOT MATERIALIZED force chủ đích. WITH chứa INSERT/UPDATE/DELETE + RETURNING chạy đúng 1 lần trong cùng snapshot, các câu trong khối không thấy kết quả của nhau.

WITH RECURSIVE org AS (
  SELECT id, name, manager_id, 1 AS depth, ARRAY[id] AS path
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, o.depth + 1, o.path || e.id
  FROM employees e JOIN org o ON e.manager_id = o.id
  WHERE NOT e.id = ANY(o.path)   -- UNION ALL không tự dừng vòng
)
SELECT depth, name FROM org ORDER BY path;

PostgreSQL còn hỗ trợ SEARCH DEPTH/BREADTH FIRST và CYCLE id SET, viết gọn hơn mảng path khi chỉ cần cờ. Cẩn thận với NOT MATERIALIZED trên CTE chứa hàm đắt đỏ tham chiếu nhiều lần: mỗi lần reference là một lần tính lại.

LATERAL: subquery tương quan trong FROM

Subquery trong FROM đánh giá độc lập, không tham chiếu được cột của bảng khác trong cùng FROM. Đặt LATERAL trước subquery thì subquery chạy lại cho từng hàng của bảng đứng trước và dùng được cột của hàng đó trong WHERE, ORDER BY. Trong cây JOIN, nó tham chiếu được cả các bảng nằm bên trái. Với table function, LATERAL là tùy chọn vì tham số hàm vốn thấy cột đứng trước; với subquery, từ khóa bắt buộc.

Dạng dùng LATERAL hay gặp là top-N mỗi nhóm: lấy 3 đơn mới nhất của từng khách.

-- 3 đơn mới nhất của mỗi khách
SELECT c.name, x.id, x.created_at
FROM customers c
CROSS JOIN LATERAL (
  SELECT o.id, o.created_at
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY o.created_at DESC
  LIMIT 3
) x;

-- Giữ cả khách chưa có đơn nào: LEFT JOIN ... ON TRUE
SELECT c.name, x.id
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.id
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY o.created_at DESC
  LIMIT 3
) x ON TRUE;

ROW_NUMBER() giải cùng bài toán theo đường khác: window function chỉ đứng được trong SELECT list hoặc ORDER BY, nên điều kiện rn <= 3 phải lọc ở query ngoài, và bộ đánh số thường đi qua hết hàng của mỗi partition rồi query ngoài mới cắt. LATERAL khép điều kiện vào trong subquery; planner đưa LIMIT vào lúc chọn plan, nên khi có index (customer_id, created_at DESC), subquery đọc khoảng 3 hàng mỗi khách thay vì toàn bộ đơn của khách đó.

CROSS JOIN LATERAL làm khách chưa có đơn biến mất khỏi kết quả; LEFT JOIN LATERAL ... ON TRUE giữ lại hàng nguồn với cột phải NULL. Điều kiện nằm trong subquery nên ON chỉ cần TRUE; đổi sang WHERE x.id IS NULL là ra anti-join.

Set operations khác JOIN ở chỗ nào

JOIN ghép theo điều kiện quan hệ, mỗi hàng nguồn có thể ra nhiều hàng kết quả; set ops ghép row-wise hai result set union-compatible, cùng số cột và type tương ứng. NULL = NULL trong set op coi là "not distinct", khác so sánh WHERE vốn trả UNKNOWN. ORDER BY, LIMIT đặt sau set op áp cho toàn bộ kết quả, không cho từng branch: LIMIT riêng mỗi branch bắt buộc ngoặc.

-- LIMIT từng branch bắt buộc parenthesize
(SELECT id FROM logs  ORDER BY id DESC LIMIT 5)
UNION ALL
(SELECT id FROM audit ORDER BY id DESC LIMIT 5);

UNION không phải cách ghép hai bảng theo khóa, việc đó cần JOIN. ALL đổi cách đếm bản sao: INTERSECT ALL giữ min(m,n) bản sao, EXCEPT ALL giữ max(m-n, 0) bản sao; còn dedup mặc định và thứ tự bind của INTERSECT đã nói ở phần Mô hình quan hệ. Set ops thường đi qua hash hoặc sort, planner ít dùng index trực tiếp như JOIN.

Upsert: ON CONFLICT và MERGE

INSERT ... ON CONFLICT là extension của PostgreSQL, có RETURNING và atomic cả với concurrent writer: luôn insert hoặc update đúng một nhánh. DO UPDATE bắt buộc conflict_target (columns của unique index hoặc ON CONSTRAINT); DO NOTHING thì optional. MERGE theo SQL:2003 vào từ PostgreSQL 15, cho nhiều WHEN trong một statement nhưng không có RETURNING và không có WITH RECURSIVE.

INSERT INTO users (email, name, created_at)
VALUES ('a@x.com', 'Alice', now())
ON CONFLICT (email) DO UPDATE
  SET name = EXCLUDED.name, updated_at = now()
RETURNING id, (xmax = 0) AS was_inserted;

MERGE INTO inventory i
USING shipments s ON i.sku = s.sku
WHEN MATCHED AND i.qty + s.delta >= 0 THEN UPDATE SET qty = i.qty + s.delta
WHEN NOT MATCHED AND s.delta > 0 THEN INSERT (sku, qty) VALUES (s.sku, s.delta);

Với MERGE, WHEN match đầu tiên được thực hiện, các WHEN sau của cùng hàng bỏ qua; một hàng target join nhiều hàng source gây cardinality violation. EXCLUDED là hàng proposed, tức hàng sẽ được insert.

Phân trang: OFFSET sâu và keyset

OFFSET nhận "số hàng cần bỏ", planner chỉ fetch và drop từng đó hàng theo định nghĩa SQL, không nhảy index range. Keyset so sánh với hàng cuối trang trước bằng row-value comparison, trả về đúng vùng dữ liệu tiếp theo qua index, không drift khi có hàng chèn giữa hai lần fetch.

-- OFFSET: chậm khi N lớn, planner vẫn phải đi qua N hàng đầu
SELECT * FROM products ORDER BY created_at DESC LIMIT 20 OFFSET 5000;

-- Keyset: trang sau truyền (created_at, id) của hàng cuối trang trước
SELECT id, name, created_at
FROM products
WHERE (created_at, id) < ($1::timestamptz, $2::bigint)
ORDER BY created_at DESC, id DESC
FETCH FIRST 20 ROWS ONLY;

CREATE INDEX idx_products_created_id ON products (created_at DESC, id DESC);

Keyset không nhảy tới số trang tùy ý, hợp với infinite scroll hơn paginator. OFFSET thiếu ORDER BY unique thì hàng chèn giữa hai lần fetch làm kết quả lệch. DISTINCT sau JOIN thường là dấu hiệu join nhân bản hàng, xem lại join trước đã.

Chống pattern: SELECT *, function wrap cột, anti-N+1

SELECT * kéo cột thừa, phá covering index và tăng IO. Function wrap quanh cột không match index thường; expression index trên hàm immutable thì match, ví dụ LOWER(email). Fetch toàn bộ rồi filter trong application tốn network và memory, trong khi WHERE hay FILTER làm ngay trong database. Cùng nhóm lỗi: nối chuỗi thành SQL thay vì parameterized query, với Prisma là $queryRaw có tham số.

-- Chọn cột tường minh thay vì *
SELECT id, email, name FROM users WHERE id = $1;

-- Expression index + query match cùng biểu thức
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
SELECT id FROM users WHERE LOWER(email) = 'alice@example.com';

-- Đếm nhiều trạng thái một câu, không fetch về app
SELECT count(*) FILTER (WHERE status = 'paid')    AS paid,
       count(*) FILTER (WHERE status = 'pending') AS pending
FROM orders;

Aggregate trên 0 hàng trả NULL, không phải 0: sum, min, max và array_agg đều NULL; count(*) thì trả 0. App cần số thì bọc COALESCE(sum(x), 0) ở tầng query. Đọc plan bằng EXPLAIN (ANALYZE, BUFFERS): sai số estimated với actual lớn nghĩa là statistics cũ hoặc biểu thức không match index.

timestamp vs timestamptz: lưu instant hay wall-clock

timestamp (tương đương timestamp without time zone) giữ đúng chuỗi wall-clock bạn ghi vào, không zone, không offset. timestamptz lưu instant UTC; hiển thị theo TimeZone của session. So sánh hai timestamptz là so sánh instant, bất kể session đang ở múi nào.

SET TIME ZONE 'UTC';
SELECT timestamptz '2026-03-15 02:30:00+07' AS tz_instant,
       timestamptz '2026-03-15 02:30:00+07' AT TIME ZONE 'UTC' AS as_utc_wall,
       timestamp   '2026-03-15 02:30:00' AS naive_wall;
--  tz_instant          | as_utc_wall        | naive_wall
--  2026-03-14 19:30:00+00 | 2026-03-14 19:30:00 | 2026-03-15 02:30:00

AT TIME ZONE đổi kiểu: trên timestamptz nó trả timestamp (wall-clock ở zone đích); trên timestamp nó gắn zone rồi thành timestamptz. Hai chiều không nghịch đảo nếu bạn không để ý kiểu trả về.

::date, date_trunc('day', …) trên timestamptz cắt theo múi giờ session — cùng instant có thể ra hai ngày khác nhau.

SELECT (timestamptz '2026-01-01 20:00:00+00')::date AS d_utc;  -- 2026-01-01
SET TIME ZONE 'Asia/Ho_Chi_Minh';
SELECT (timestamptz '2026-01-01 20:00:00+00')::date AS d_vn;   -- 2026-01-02
SET TIME ZONE 'UTC';

Chọn timestamptz cho mọi cột thời điểm nghiệp vụ (created_at, paid_at, event_at). Dùng timestamp chỉ khi wall-clock cố định không zone (giờ tàu chạy, lịch biểu đã local hóa). Trong app nhiều múi giờ, set TimeZone của connection về UTC và đổi zone ở tầng hiển thị — nếu để driver lấy local timezone của máy app, cùng query trả hai ::date khác nhau tùy container.

CAST: assignment, explicit và SQLSTATE 22P02

PostgreSQL phân biệt ngữ cảnh cast: explicit (::int, CAST(…)), assignment (INSERT/UPDATE ghi vào cột), và implicit (so sánh, function overload). Mỗi ngữ cảnh có tập phép cast riêng; assignment lỏng hơn implicit nhưng không bằng explicit. Ngữ cảnh được phân loại bởi pg_cast.castcontext với mã e (explicit), a (assignment), i (implicit).

Ví dụ float8 → int4 và numeric → int4: explicit cast (::int, CAST) dùng round theo kiểu round-to-nearest; assignment cast trong INSERT/UPDATE cũng dùng đường round (không trunc về 0). Thêm nữa, cho float8, hành vi tie-case là round-half-to-even (banker's rounding): 2.5 và 3.5 lần lượt làm tròn về 2 và 4; với numeric → int, các half-value thường round away from zero. Cùng input, trên float8→int4, cả explicit lẫn assignment đều làm tròn như nhau.

SELECT 4.5::float8::int AS explicit_float_to_int;   -- 4 (round half-to-even)
BEGIN;
CREATE TEMP TABLE assign_int (n int);
INSERT INTO assign_int VALUES (4.5::float8), (4.9::float8), (2.5::float8), (3.5::float8);
SELECT array_agg(n ORDER BY n) AS assignment_float_to_int FROM assign_int;
-- {2,4,4,5}  — round half-to-even trên float8 (banker's rounding) cho cả assignment lẫn explicit
ROLLBACK;

Khi input không parse được kiểu đích, cả explicit lẫn assignment đều abort statement với invalid_text_representation / SQLSTATE 22P02. Trong transaction, statement fail đánh dấu aborted; câu lệnh sau đó trả 25P02 cho tới khi ROLLBACK (xem thêm 25P02 ở phần Transaction).

-- 22P02: invalid input syntax for type integer: "abc"
SELECT 'abc'::int;

Bẫy: Không có trường hợp "assignment trunc" cho float8→int4 trong PostgreSQL 16. Cả explicit và assignment đều dùng round; ví dụ 4.9 → 5, 4.5 → 4 trên float8. Lỗi 22P02 chỉ xảy ra khi chuỗi không thể parse về kiểu đích, không xảy ra khi làm tròn giá trị nằm trong phạm vi.

Collation và citext: so sánh chuỗi theo locale nào

Mỗi chuỗi text mang collation (từ database, column, hoặc COLLATE tường minh). Collation quyết định thứ tự sort, equality và index opclass. Hai collation khác nhau so sánh với nhau là 42P21 collation mismatch.

SELECT 'a' < 'B' AS ci,                      -- t  (en_US: case-insensitive order)
       'a' COLLATE "C" < 'B' COLLATE "C" AS coll_c;  -- f  (C: byte order, 'B'(0x42) < 'a'(0x61))
-- so sánh mixed → ERROR: collation mismatch … (42P21)

Index B-tree theo default collation không dùng được cho COLLATE "C" lookup (và ngược lại); cần expression index với cùng COLLATE, hoặc opclass text_pattern_ops khi so sánh byte-wise với LIKE 'abc%'.

Extension citext (contrib) cho kiểu case-insensitive: equality và DISTINCT coi 'Alice@x' = 'alice@x'. Đăng ký email bằng citext là shortcut khi không muốn expression index LOWER(email).

CREATE EXTENSION IF NOT EXISTS citext;
SELECT count(*) AS citext_distinct FROM (
  SELECT DISTINCT e FROM (VALUES
    ('Alice@Example.COM'::citext),
    ('alice@example.com'::citext)
  ) s(e)
) t;   -- 1

Citext không thay thế collation-aware full-text search; nó chỉ làm equality/DISTINCT/unique case-insensitive theo collation của nó. Unique index trên citext chặn 'A@x' và 'a@x' chung một hàng — đúng ý email, sai nếu bạn muốn phân biệt hoa thường ở cột khác.

DISTINCT ON: một hàng đại diện mỗi nhóm

DISTINCT ON (expr, …) giữ đúng một hàng cho mỗi tập giá trị của expr; hàng nào được giữ do ORDER BY quyết định — các biểu thức đầu tiên trong ORDER BY phải trùng đúng danh sách expr của DISTINCT ON, rồi mới tới cột phân định thứ tự trong nhóm.

-- Đơn mới nhất (id lớn nhất) của mỗi user
SELECT DISTINCT ON (user_id) user_id, id, total
FROM (VALUES
  (1,1,100),(1,2,250),(1,3,90),
  (2,4,400),(2,5,120),(3,6,77)
) AS o(user_id,id,total)
ORDER BY user_id, id DESC;
-- user_id | id | total
--       1 |  3 |    90
--       2 |  5 |   120
--       3 |  6 |    77

Bẫy: Bỏ ORDER BY … id DESC (hoặc để ORDER BY user_id, total DESC) thì "mới nhất" thành "lớn nhất total" hoặc hàng tùy planner — cú pháp vẫn hợp lệ, kết quả sai nghiệp vụ. SELECT DISTINCT thường không liên quan: DISTINCT ON là PostgreSQL extension, không phải SQL chuẩn; dùng portable thì viết ROW_NUMBER() OVER (PARTITION BY …) rồi lọc rn = 1 ở query ngoài.

JSONB: toán tử so sánh và extract

jsonb (khác json) parse một lần, bỏ duplicate key (giữ cuối), chuẩn hóa thứ tự object key. Hai jsonb bằng nhau khi object key set bằng nhau, không phụ thuộc thứ tự ghi.

SELECT '{"x":1,"y":2}'::jsonb = '{"y":2,"x":1}'::jsonb;  -- t

Toán tử extract: -> trả jsonb (giữ kiểu), ->> trả text, #> / #>> nhận path array. Toán tử so sánh: @> containment (object và array), ? existence key, ?| / ?& nhiều key.

SELECT '{"a":1,"b":[10,20]}'::jsonb ->  'a' AS arrow_jsonb,  -- 1 (jsonb)
       '{"a":1,"b":[10,20]}'::jsonb ->> 'a' AS arrow_text,   -- 1 (text)
       '{"a":1}'::jsonb @> '{"a":1}' AS contains,             -- t
       '{"a":1}'::jsonb ?  'a' AS has_key,                     -- t
       jsonb_path_query('{"a":{"b":5}}', '$.a.b') AS jsonpath; -- 5

Containment index được bằng GIN (CREATE INDEX … USING gin (j)); planner dùng Bitmap Index Scan trên @>. Jsonpath (jsonb_path_query) mạnh hơn #> khi cần filter trong mảng, nhưng không GIN-index thẳng — pre-filter bằng @> rồi refine bằng jsonpath.

Bẫy: -> trên array nhận index 0-based; path sai kiểu (số thay tên) trả NULL im lặng. So sánh json (text) là so sánh chuỗi, khác jsonb; luôn cast hoặc khai báo cột jsonb.

Ordered-set aggregates: percentile và mode WITHIN GROUP

Aggregate thường (sum, count) không phụ thuộc thứ tự hàng. Ordered-set aggregates chạy theo thứ tự của WITHIN GROUP (ORDER BY …): percentile_cont (interpolate, trả giá trị nội suy), percentile_disc (chọn hàng thật trong data), mode() (giá trị lặp nhiều nhất).

SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY v) AS p50_cont,
       percentile_disc(0.5) WITHIN GROUP (ORDER BY v) AS p50_disc,
       mode()               WITHIN GROUP (ORDER BY v) AS mode_v
FROM (VALUES (1),(2),(2),(3),(3),(3),(4)) t(v);
-- p50_cont | p50_disc | mode_v
--        3 |        3 |      3

Trên data 1,2,3,4: percentile_cont(0.5) = 2.5 (nội suy), percentile_disc(0.5) = 2 (hàng thật đầu tiên đạt phân vị). Hai hàm khác nhau khi median rơi giữa hai giá trị — phải nói rõ nghiệp vụ muốn nội suy hay lấy giá trị có thật.

SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY amount) AS p50
FROM (SELECT 1 AS amount WHERE false) s;   -- NULL (0 hàng trong nhóm)

Bẫy: Viết percentile_cont(0.5) không WITHIN GROUP → function percentile_cont(numeric) does not exist; WITHIN GROUP là bắt buộc, không optional. Trong GROUP BY, mỗi nhóm chạy ORDER BY riêng — không có phạm vi "toàn bảng" khi đã partition. mode() trên data không có giá trị lặp trả một giá trị bất kỳ (thường là đầu tiên theo ORDER BY), không raise "no mode".

Transaction & concurrency: isolation level, khóa, retry

Dữ liệu sai khi chạy song song quy về ba câu hỏi: transaction nào thấy gì, transaction nào chờ ai, khi abort thì code nào chạy lại. Phần này đi qua bảng phenomenon ↔ isolation level trên PostgreSQL 16, FOR UPDATE đúng chỗ, và retry bọc ngoài transaction cho 40001/40P01.

ACID ở mức kỹ thuật từng chữ

Atomicity
Một statement fail thì mọi thay đổi của transaction bị ROLLBACK theo.
Consistency
Chuyển từ valid-state này sang valid-state khác: gồm constraint vật lý (UNIQUE, CHECK, FK) lẫn application invariant như số dư không âm. Invariant không có constraint thì không ai enforce.
Isolation
Kết quả phải tương đương một thứ tự serial của các transaction, đạt bằng locking (2PL) hoặc snapshot/MVCC.
Durability
Commit đã flush WAL thì sống sót crash; chỉ cần flush file WAL, full_page_writes và synchronous_commit bật mặc định.

Sequence không thuộc transaction: nextval và setval không bị rollback nên transaction fail vẫn làm số tăng tiếp. Gap giữa hai ID là hành vi bình thường, đừng dùng sequence cho mã cần không gap như số hóa đơn.

25P02: aborted transaction và cách recover

Sau khi một statement trong transaction fail, PostgreSQL đánh dấu transaction ở trạng thái aborted; câu lệnh tiếp theo trả in_failed_sql_transaction (25P02) với thông báo "current transaction is aborted, commands ignored until end of transaction block". Chỉ ROLLBACK, hoặc ROLLBACK TO SAVEPOINT, mới clear trạng thái đó; COMMIT trên transaction aborted bị PostgreSQL thực thi thành ROLLBACK (in tag ROLLBACK, không commit được).

BEGIN;
SAVEPOINT sp1;
INSERT INTO t VALUES (1);   -- ok
SELECT 1/0;                 -- ERROR: division by zero
INSERT INTO t VALUES (2);
-- ERROR: current transaction is aborted, commands ignored until end of transaction block  (25P02)
ROLLBACK TO SAVEPOINT sp1;  -- lùi về mốc, clear aborted flag
INSERT INTO t VALUES (2);   -- chạy được
COMMIT;

Bẫy: Interactive $transaction(async tx => …) bắt mọi exception trong callback và ROLLBACK nguyên khối. Nếu bạn catch lỗi rồi gọi tiếp tx.$executeRaw, câu lệnh đó gặp 25P02 từ driver (hoặc Prisma ném client ném P2028 'Transaction already closed: … cannot be executed on a transaction that was rolled back'); cách đúng là ném lại exception để Prisma rollback, hoặc SAVEPOINT + ROLLBACK TO SAVEPOINT trước khi retry từng phần.

Isolation level chuẩn ↔ PostgreSQL

PostgreSQL chỉ implement ba level: Read Uncommitted chạy y hệt Read Committed ("the only sensible way to map the standard isolation levels"), còn Repeatable Read của PG chặn luôn phantom, mạnh hơn chuẩn yêu cầu. Mặc định của PG là READ COMMITTED, của chuẩn ISO là SERIALIZABLE.

  • Snapshot mỗi statement (RC)

    Mỗi SELECT thấy snapshot tại thời điểm câu lệnh bắt đầu; hai SELECT liên tiếp thấy dữ liệu khác nếu có commit xen giữa.

    Bẫy: Read-modify-write trong application (đọc qty ở Node, ghi lại số mới) bị lost update ở RC dù có WHERE.

  • Snapshot Isolation (RR)

    Snapshot đóng băng tại câu lệnh truy vấn đầu tiên; write-write xử lý theo first-committer-wins.

    Bẫy: RR chặn P4 nhưng vẫn cho phép write skew; chỉ Serializable chặn cả hai.

  • MVCC: xmin / xmax

    xmin là transaction tạo row version, xmax là transaction xóa nó (0 nếu còn sống). UPDATE tạo version mới, đọc không block ghi.

    Bẫy: Session "idle in transaction" giữ snapshot lâu kìm VACUUM, dead tuple không thu hồi được, sinh bloat.

  • Optimistic version column

    Mỗi row một cột version; UPDATE kèm WHERE version = giá trị đã đọc rồi kiểm số hàng bị ảnh hưởng, không giữ lock xuyên suốt.

    Bẫy: Quên điều kiện version thì optimistic thành ghi đè tự do; count = 0 mới là conflict.

Read Committed: re-evaluate WHERE sau khi chờ lock

Level mặc định của mọi session NestJS/Prisma. UPDATE gặp row bị lock thì chờ; tới khi nhả, PostgreSQL kiểm lại row bản mới còn khớp WHERE không (EvalPlanQual), không khớp thì bỏ row, kết thúc 0 hàng thay vì báo lỗi. Docs cảnh báo RC "unsuitable for commands that involve complex search conditions": statement thấy snapshot không nhất quán giữa các row.

-- Session A, chưa COMMIT
BEGIN;
UPDATE website SET hits = hits + 1;        -- 10 → 11, giữ row lock

-- Session B chạy cùng lúc, chờ row lock
DELETE FROM website WHERE hits = 10;
-- A COMMIT → WHERE re-evaluate trên bản hits=11 → 0 hàng xóa,
-- dù row hits=10 vẫn tồn tại ở đầu statement

Read Committed không cứu được pattern đọc-modify-ghi trong application: Hermitage test P4 ở RC cho phép cả hai transaction commit, và "T1's update is overwritten". Sửa bằng một trong ba cách ở mục Lost update, không phải bằng đổi isolation level.

Repeatable Read: một snapshot, lỗi 40001 khi ghi tranh

Snapshot đóng băng tại câu lệnh đầu tiên nên các SELECT liên tiếp thấy một bản duy nhất. Row bị transaction khác sửa sau thời điểm đó làm câu UPDATE abort với could not serialize access due to concurrent update (40001); docs yêu cầu "abort the current transaction and retry the whole transaction from the beginning". Transaction read-only không dính conflict này.

BEGIN ISOLATION LEVEL REPEATABLE READ;   -- phải là câu lệnh đầu tiên
SELECT qty FROM inventory WHERE id = 1;  -- 10
-- session B lúc này: UPDATE qty = 9; COMMIT;

UPDATE inventory SET qty = 9 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update  (40001)
-- ROLLBACK rồi chạy lại TOÀN BỘ transaction

RR của PG chặn phantom dù chuẩn không yêu cầu ("higher guarantees are acceptable"); docs RR thừa nhận view "will not necessarily always be consistent with some serial execution".

Serializable (SSI): predicate locking, retry bắt buộc

SSI xây trên Snapshot Isolation cộng giám sát dependency dẫn tới bất thường serialization. Predicate lock không gây block ("can not play any part in causing a deadlock"), hiện trong pg_locks với mode SIReadLock. Phát hiện xung đột thì abort với could not serialize access due to read/write dependencies among transactions, cùng 40001.

Sequential scan lấy predicate lock cấp relation nên tăng tỉ lệ fail; max_pred_locks_per_transaction mặc định 64, thiếu bộ nhớ thì lock bị gộp và tỉ lệ fail tăng. Job report thêm READ ONLY; SERIALIZABLE READ ONLY DEFERRABLE là trường hợp duy nhất Serializable block còn Repeatable Read không. Unique constraint vẫn nổ giữa chừng dù pre-check đã qua.

Khóa: FOR UPDATE, NOWAIT, SKIP LOCKED

Tầng table có 8 mode, chỉ ACCESS EXCLUSIVE chặn SELECT thường; ROW SHARE/ROW EXCLUSIVE tự lấy khi có FOR UPDATE hoặc INSERT/UPDATE/DELETE, hoạt động như intention lock báo trước cho DDL.

-- Queue pattern: nhiều worker giành việc mà không tranh nhau
BEGIN;
SELECT id FROM jobs WHERE status = 'pending' ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 1;
UPDATE jobs SET status = 'running' WHERE id = 1;
COMMIT;

-- NOWAIT: báo lỗi thay vì chờ
SELECT * FROM jobs WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR: lock not available  (55P03)

SKIP LOCKED không phải cơ chế đọc nhất quán: "Skipping locked rows provides an inconsistent view of the data", chỉ hợp lệ cho bảng hàng đợi. ORDER BY + FOR UPDATE ở RC có thể trả row sai thứ tự vì planner sort trước khi khóa; cách an toàn là bọc subquery FOR UPDATE rồi ORDER BY ở query ngoài.

Khi cần bảo đảm chỉ một process chạy một việc tại một thời điểm mà không muốn dựng bảng hàng đợi, dùng pg_advisory_lock(key bigint) hoặc pg_advisory_xact_lock(key bigint): khóa cấp application, nhận diện bằng một khóa bigint (hoặc cặp int4), không gắn với row nào trong bảng và PostgreSQL không kiểm tra nội dung công việc, application tự đặt quy ước. Ca điển hình: migration leader, job single-instance. Xact-lock tự nhả khi transaction commit/rollback, không có lệnh unlock thủ công; session-lock giữ tới khi gọi unlock hoặc session đóng. Khác FOR UPDATE SKIP LOCKED ở chỗ SKIP LOCKED khóa row trong bảng hàng đợi rồi bỏ qua row đang bị giữ; advisory lock bỏ hẳn nhu cầu tạo bảng hàng đợi.

Deadlock: check sau 1 giây, victim khó đoán

PostgreSQL tự phát hiện deadlock rồi abort một trong hai transaction; "exactly which transaction will be aborted is difficult to predict and should not be relied upon". Phát hiện không tức thì: deadlock_timeout mặc định 1 giây, cũng là ngưỡng log khi bật log_lock_waits.

-- Chống deadlock: mọi transaction lấy lock theo cùng một thứ tự
BEGIN;
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 50  WHERE id = 2;
COMMIT;
-- Trái thứ tự (A khóa 1 rồi 2, B khóa 2 rồi 1) là deadlock kinh điển
-- → sau ~1s: ERROR: deadlock detected  (40P01) → retry

2PL growing/shrinking giải thích vì sao phải lấy mọi lock cần thiết trước khi nhả lock nào; conservative 2PL lấy đủ lock trước khi chạy thì tránh deadlock, PostgreSQL không có cơ chế đó trong core nên phải tự viết retry. Bốn mode row lock theo quyền lực: FOR UPDATE > FOR NO KEY UPDATE > FOR SHARE > FOR KEY SHARE, giữ tới hết transaction.

Lost update thực tế: ba cách đúng

Trừ kho, giữ chỗ ghế, cộng điểm đều là chỗ hai request đọc cùng một số rồi cả hai ghi. Cách sai luôn giống nhau: đọc ở app, tính, ghi đè.

-- Cách 1: UPDATE atomic, biểu thức tính trong DB, WHERE gộp điều kiện
UPDATE inventory SET qty = qty - 1
WHERE id = 1 AND qty >= 1;             -- rowCount = 0 → báo hết hàng

-- Cách 2: pessimistic, giữ row lock rồi mới ghi
BEGIN;
SELECT qty FROM inventory WHERE id = 1 FOR UPDATE;
UPDATE inventory SET qty = qty - 1 WHERE id = 1 AND qty > 0;
COMMIT;

-- Cách 3: optimistic, không lock, kiểm version khi ghi
UPDATE seat
SET status = 'held', version = version + 1
WHERE id = 7 AND status = 'free' AND version = 3;
-- 0 rows → conflict, báo "ghế đã được đặt trước"

Cách 1 đủ cho phần lớn truy vấn trừ kho vì row lock tự lấy theo statement. Cách 2 hợp khi giữ lock nhiều bước như luồng thanh toán. Cách 3 hợp khi conflict hiếm, request đồng thời cao: Prisma khuyến nghị updateMany({ where: { id, version }, … }) rồi kiểm count = 0. Điều kiện phải nằm cùng statement WHERE với biểu thức trừ; tách "kiểm qty" và "trừ qty" thành hai câu thì race còn nguyên.

Prisma / NestJS: $transaction và retry P2034

Prisma 7 có hai hình thức: mảng $transaction([q1, q2]) chạy tuần tự trên một connection, rollback cả mảng khi một query fail; interactive $transaction(async tx => …) cho query trước nuôi query sau, hết function là commit, ném exception là rollback. Options chỉ gồm maxWait (2000 ms), timeout (5000 ms), isolationLevel, không có retryOnConflict.

Write conflict hoặc deadlock thì Prisma trả P2034 (PostgreSQL 40001/40P01), docs yêu cầu tự viết retry. Vòng lặp bọc NGOÀI $transaction với backoff; retry bên trong callback vô nghĩa vì callback đã abort.

async function withRetry<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 5; i++) {
    try { return await fn(); } catch (e) {
      const code = (e as any)?.code;
      if (code !== 'P2034' && code !== '40001' && code !== '40P01') throw e;
      await new Promise(r => setTimeout(r, 2 ** i * 50 + Math.random() * 50));
    }
  }
  throw new Error('transaction failed after retries');
}
await withRetry(() => prisma.$transaction(
  async tx => { /* trừ kho + tạo order */ },
  { timeout: 8000, isolationLevel: 'RepeatableRead' },
));

P2034 cũng có thể nổi ở chính lệnh commit, nên nhánh thành công vẫn trong try. Giữ transaction ngắn, đặt idle_in_transaction_session_timeout làm safety net vì session kẹt giữ snapshot chặn VACUUM. Prisma 8 (bản RC hiện tại) expose db.transaction(async tx => …) trên serverless client; với Prisma 7 stable vẫn dùng prisma.$transaction(...).

SAVEPOINT + ROLLBACK TO SAVEPOINT mở subtransaction: đánh dấu một mốc trong transaction, lùi về mốc đó rồi chạy tiếp, dùng để retry từng phần bên trong transaction lồng nhau thay vì vứt bỏ cả vòng. Đánh đổi nằm ở tầng MVCC: subxid sinh ra trong lúc chạy làm VACUUM phức tạp hơn khi xác định dead tuple, vì trạng thái của subtransaction phải phân giải qua pg_subtrans/pg_xact thay vì chỉ đọc một XID top-level; docs ghi quá 64 subxid còn mở trên mỗi backend thì overhead tra pg_subtrans "increases significantly".

Chọn isolation level cho một service

  1. Đọc-modify-ghi mức row: giữ READ COMMITTED, sửa bằng UPDATE atomic; đổi level không sửa được bug này.
  2. Đọc nhiều bảng nhất quán, ít conflict: REPEATABLE READ, nhận chi phí retry toàn bộ khi dính 40001.
  3. Invariant trải nhiều row, hai txn ghi row rời nhau: SERIALIZABLE kèm retry; read-only thêm READ ONLY.
  4. Luôn đặt level ở câu lệnh đầu: sau câu lệnh truy vấn đầu tiên, PostgreSQL từ chối đổi.
  5. Prisma: truyền isolationLevel trong options, bọc retry ngoài $transaction; mảng và interactive dùng chung vòng lặp retry.

2PC và khi nào application không nên dùng

PREPARE TRANSACTION 'gid' detach transaction khỏi session: state ghi ra đĩa, mọi session khác thấy nó trong pg_prepared_xacts, kết thúc bằng COMMIT PREPARED 'gid' hoặc ROLLBACK PREPARED 'gid' từ session bất kỳ. Mục đích gốc là external transaction manager phối atomic commit giữa nhiều resource (XA).

BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
PREPARE TRANSACTION 'pay_42';
-- session bất kỳ, sau khi resource kia cũng "prepared":
COMMIT PREPARED 'pay_42';   -- hoặc ROLLBACK PREPARED 'pay_42'
SELECT gid FROM pg_prepared_xacts;  -- rỗng sau khi kết thúc

Docs chốt: "Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION". Lock giữ tới COMMIT/ROLLBACK PREPARED, kìm VACUUM; prepared transaction kẹt có thể buộc shutdown chống xid wraparound. max_prepared_transactions mặc định 0 (tắt feature); nếu bật, để giá trị ≥ max_connections. Thay thế ở application: saga + outbox ghi event cùng transaction business — xem mục Outbox pattern trong Replication, partitioning & khi nào rời RDBMS.

Snapshot, row version và row lock là nền cho phần PostgreSQL internals (MVCC, VACUUM, bloat); phần Index & storage giải thích vì sao mỗi UPDATE tạo dead tuple kéo theo index.

Index & storage engine: đọc EXPLAIN và chọn index đúng

Mỗi câu SELECT chậm đều về một trong hai việc: planner quét sai phạm vi, hoặc row phải đọc thêm vòng ra heap. Học phần này để làm được bốn việc: đọc cấu trúc trang 8KB để giải thích UPDATE sinh version mới, phân biệt 7 loại index của PostgreSQL và chọn đúng loại, viết composite/partial index theo đúng quy tắc leftmost prefix, và dùng pg_stat_user_indexes để drop index chết thay vì giữ chúng làm chậm mọi INSERT.

Heap page 8KB: nơi row thật sự sống

PostgreSQL không có "file table". Mọi bảng và mọi B-tree index đều cắt thành trang cố định 8192 bytes, cùng một format. Hiểu layout của một trang giải thích được hai câu hỏi phỏng vấn phổ biến: tại sao UPDATE tạo row mới thay vì ghi đè, và tại sao ctid không dùng làm ID.

|<--------------- 8192 bytes --------------->|
+------------------+--------------------------+
| PageHeaderData   | 24 bytes                 |
+------------------+--------------------------+
| line pointer #1  | ItemIdData, 4 bytes      |
| line pointer #2  | trỏ tới offset tuple     |
+------------------+  free space (fillfactor) +
| tuple #1         | header 23B + data        |
|   t_xmin, t_xmax | XID insert / delete      |
|   t_ctid         | vị trí vật lý hiện tại   |
+------------------+--------------------------+
| special space    | (index page: downlink)    |
+------------------+--------------------------+
Tuple không bao giờ span 2 trang → row rộng phải TOAST ra ngoài.

Tuple header 23 bytes giữ ba thứ quyết định MVCC: t_xmin (transaction INSERT), t_xmax (transaction DELETE/UPDATE, 0 nếu còn sống), t_ctid (vị trí vật lý, trỏ sang version kế tiếp khi row bị UPDATE). UPDATE không sửa tại chỗ: ghi version mới, set t_xmax của bản cũ, để lại dead tuple cho VACUUM dọn. Đó là lý do fillfactor (mặc định 100 với bảng, 90 với index) quyết định một bảng ghi nhiều có nên chừa % trống để HOT update giữ row cùng trang.

-- Thấy trực tiếp version và vị trí vật lý
SELECT ctid, xmin, xmax, id, email FROM users LIMIT 5;
-- UPDATE rồi chạy lại: ctid đổi, xmax của bản cũ được set
UPDATE users SET email = 'new@example.com' WHERE id = 1;
SELECT ctid, xmin, xmax, id, email FROM users WHERE id = 1;

Dùng ctid làm ID vĩnh viễn là bug âm thầm: VACUUM FULL (hoặc CLUSTER) di chuyển mọi row nên ctid đổi toàn bộ, trong khi primary key không đổi. ctid chỉ hợp lệ để debug "row này nằm ở trang nào" trong một thời điểm.

  • TOAST: row lớn ra ngoài trang

    Row rộng hơn toast_tuple_target (mặc định 2040 bytes = 4 tuple/trang) bị nén rồi đẩy sang bảng TOAST riêng theo strategy EXTENDED; chunk ~2000 bytes, pointer TOAST 18 bytes ở lại trong row. Cột text/jsonb lớn vì thế có hai vòng đọc: heap trước, TOAST sau.

    Bẫy: đặt toast_tuple_target quá thấp làm mọi row bị chia nhỏ; TOAST table không set được fillfactor.

  • WAL & durability

    Write-ahead: mọi thay đổi ghi vào WAL trước, data page để "no-force" chỉ flush lúc checkpoint. COMMIT chỉ cần fsync WAL; một lần fsync chốt được nhiều transaction, đó là lý do gộp batch commit giảm I/O.

    Bẫy: synchronous_commit=off chỉ làm mất dữ liệu gần nhất (cửa sổ tối đa 3 × wal_writer_delay); fsync=off gây hỏng cấu trúc ("arbitrarily bad corruption") sau crash. Hai thứ khác hẳn nhau.

  • Checkpoint

    Checkpointer flush toàn bộ dirty page và ghi checkpoint record; recovery bắt đầu từ checkpoint gần nhất. Mặc định PG16: checkpoint_timeout 5min, max_wal_size 1GB (soft limit), min_wal_size 80MB, checkpoint_completion_target 0.9 để trải I/O.

    Bẫy: hạ checkpoint_timeout quá ngắn khiến full_page_writes=on phải ghi lại cả trang nhiều lần, WAL tăng ngược.

  • B+tree non-clustered

    Metapage + trang nội bộ + trang lá cùng format 8KB; "over 99% of all pages are leaf pages", lá liên kết doubly-linked nên quét range không phải leo lại từ root. Height 3–4 chứa hàng triệu dòng nhờ fanout cao. Leaf chỉ chứa (key, TID) trỏ vào heap.

    Bẫy: PG không có clustered index, khác InnoDB nơi data sống trong leaf clustered index và secondary index chứa PK (lookup 2 bước). CLUSTER chỉ là một lần chạy, insert sau đó mất thứ tự.

  • Visibility map (VM)

    2 bit/trang heap (all-visible, all-frozen), chỉ VACUUM set, mọi thao tác ghi clear. VM nhỏ hơn heap khoảng 4 orders of magnitude nên gần như luôn nằm trong cache. Index không có VM, chỉ heap có.

    Bẫy: không chạy VACUUM → bit không bao giờ set → index-only scan rơi về index scan thường, planner vẫn phải xuống heap.

  • Leftmost prefix

    Quy tắc chính thức của docs: equality trên cột dẫn, cộng inequality trên cột đầu chưa có equality, giới hạn phần index được quét; cột bên phải chỉ tiết kiệm lượt đọc heap. Index (a, b) không phục vụ WHERE b = … một mình.

    Bẫy: planner chọn seq scan thay vì full index scan khi predicate bỏ cột dẫn; đó là dấu hiệu index vô dụng cho query đó chứ không phải bug planner.

  • UNIQUE + NULL (PG16)

    Mặc định "null values in a unique column are not considered equal, allowing multiple nulls"; thêm NULLS NOT DISTINCT để coi NULL bằng nhau. Multicolumn unique chỉ reject khi tất cả cột trùng. Chỉ B-tree khai báo được UNIQUE.

    Bẫy: unique constraint không chặn nhiều NULL, nên đơn đăng ký trùng email khi email null lọt qua. Muốn đúng 1 NULL thì partial unique index WHERE col IS NULL.

  • FK không tự tạo index

    Docs: "the declaration of a foreign key constraint does not automatically create an index on the referencing columns". Chỉ phía referenced được đảm bảo index; phía tham chiếu không có, nên DELETE/UPDATE parent seq scan bảng con.

    Bẫy: thêm FK ở code, không thêm index, rồi thao tác xóa trên bảng cha chậm dần theo số dòng con.

Bảy loại index: chọn theo operator, không theo thói quen

Chọn sai type thì index đúng cột vẫn vô dụng, vì mỗi type hỗ trợ một tập operator khác nhau. Chỉ B-tree, GiST, GIN, BRIN hỗ trợ multicolumn; chỉ B-tree khai báo được UNIQUE; Bloom là extension chứ không phải type built-in.

Composite index, index-only scan và visibility map

Thứ tự cột quyết định index có dùng được hay không. Quy tắc sắp xếp thực dụng: cột equality trước, cột range sau, cột khớp ORDER BY cuối; tối đa 32 cột kể cả INCLUDE, và quá 3 cột thường hiếm hữu ích theo docs.

-- equality -> range -> ORDER BY
CREATE INDEX idx_tenant_status_created ON orders (tenant_id, status, created_at DESC);
EXPLAIN SELECT id FROM orders
WHERE tenant_id = 7 AND status = 'new' ORDER BY created_at DESC LIMIT 20;

-- index-only scan: cột nằm hết trong index + visibility map set
CREATE INDEX idx_cov ON users (email) INCLUDE (name);
EXPLAIN (ANALYZE, BUFFERS) SELECT name FROM users WHERE email = 'a@b.c';
VACUUM users;  -- set bit all-visible, chạy lại EXPLAIN để thấy fallback biến mất

Index-only scan cần đồng thời hai điều kiện: query chỉ tham chiếu cột có trong index (INCLUDE cho phép thêm cột phụ, nhưng chỉ B-tree/GiST/SP-GiST hỗ trợ INCLUDE và unique chỉ tính theo cột key), và visibility map đặt bit all-visible cho trang heap chứa row. Thiếu điều kiện nào planner cũng phải xuống heap; đọc EXPLAIN mà thấy "Index Only Scan" nhưng heap fetches cao thì VM chưa sẵn sàng.

UNIQUE với INCLUDE chỉ unique theo cột key, không theo cột INCLUDE. CREATE UNIQUE INDEX ON users (email) INCLUDE (name) vẫn cho phép hai row cùng name khác email; điều đó đúng, nhưng đừng hiểu nhầm thành unique cả hai.

Partial index, expression index và hai cái bẫy planner

Partial index chứa chỉ row thỏa predicate, nhỏ và nóng hơn. Điều kiện dùng: planner phải nhận ra "WHERE condition của query ngụ ý logic predicate của index" tại thời điểm planning. Planner chỉ chứng minh được implication với giá trị xác định tại planning time; câu lệnh prepared có placeholder ($1) thường dùng generic plan và không thỏa mãn điều kiện implication → thường không dùng được partial index. Với custom plan (5 EXECUTEs đầu), giá trị cụ thể được biết tại planning time và có thể dùng index nếu predicate match trực tiếp.

CREATE INDEX idx_orders_unbilled ON orders (order_nr) WHERE billed IS NOT TRUE;
EXPLAIN SELECT * FROM orders WHERE billed IS NOT TRUE AND order_nr < 10000;  -- dùng index
EXPLAIN SELECT * FROM orders WHERE order_nr = 3501;  -- KHÔNG dùng: predicate không implied

-- expression index: query phải viết đúng expression y hệt
CREATE INDEX idx_users_lower_email ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'alice@example.com';

-- chống email khác hoa/thường bị chặn khi NULL không distinct
CREATE UNIQUE INDEX u_email ON users (lower(email)) NULLS NOT DISTINCT;  -- PG15+

Tạo một partial index cho mỗi category là "bad idea" theo docs: số index nhân với mỗi INSERT, còn partitioning hoặc composite index (category, data) xử lý cùng bài toán với giá trị sửa thấp hơn. Expression index cũng đắt hơn khi ghi, vì mỗi INSERT/UPDATE phải tính lại biểu thức.

Khi index không cứu được

Index thừa là chi phí âm thầm: mỗi index là một bản ghi đồng bộ thêm khi INSERT, và "Indexes can also prevent the creation of heap-only tuples" nên mọi index trên bảng làm giảm khả năng HOT update. Bốn dấu hiệu planner không dùng index bạn kỳ vọng:

  • Cardinality thấp (boolean, status có 2 giá trị). random_page_cost mặc định 4.0 (SSD nên hạ về ~1.1) so với seq_page_cost 1.0, seq scan thắng với bảng nhỏ hoặc quét gần toàn bảng.
  • Query bọc function quanh cột (WHERE lower(email) = … khi index trên email thô); cần expression index.
  • Thứ tự cột sai leftmost prefix; planner quét full index rồi vẫn phải heap visit từng dòng.
  • Chỉ check EXPLAIN trên data mẫu nhỏ; planner cost đổi khi table lớn, phải chạy EXPLAIN (ANALYZE) và pg_stat trên data thật.
-- FK thiếu index: seq scan bảng con trong mỗi lần xóa cha
EXPLAIN ANALYZE DELETE FROM customers WHERE id = 42;
CREATE INDEX idx_order_items_order ON order_items (order_id);
EXPLAIN ANALYZE DELETE FROM customers WHERE id = 42;  -- giờ là index scan

Nuôi index: audit, bloat, REINDEX CONCURRENTLY

Index chết vẫn ăn dung lượng và làm mọi INSERT chậm đi. pg_stat_user_indexes cho ba số để quyết định: idx_scan (số lần planner khởi tạo scan), idx_tup_read (index entry trả về), idx_tup_fetch (live row lấy từ heap; bitmap scan không tăng số này của index, chỉ tăng idx_tup_read). Một điểm cần verify thêm trước khi dùng làm chuẩn: index chỉ dùng cho constraint check (UNIQUE/PK khi INSERT) được đếm thế nào vào idx_scan, monitoring-stats chưa nói rõ.

-- AUDIT index không dùng (giữ PK/constraint, chỉ drop index thường)
SELECT schemaname, tablename, indexname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexname NOT LIKE '%_pkey';

DROP INDEX CONCURRENTLY idx_dead;
  1. Chạy EXPLAIN (ANALYZE, BUFFERS) với query thật — xem Seq Scan/Index Scan/Index Only Scan/Bitmap và "_heap fetches"; không tin EXPLAIN chưa ANALYZE.
  2. Kiểm tra visibility map trước khi kết luận index-only scan hỏng — chạy VACUUM bảng rồi EXPLAIN lại; nếu heap fetches về 0 thì vấn đề là VACUUM chưa chạy.
  3. Đối chiếu pg_stat_user_indexes theo lịch — idx_scan = 0 kéo dài thì drop (trừ PK/UNIQUE giữ ràng buộc); đọc idx_tup_fetch để phân biệt bitmap scan.
  4. Rebuild index bloat bằng REINDEX INDEX CONCURRENTLY — hai lần scan, không chặn ghi, chờ transaction cũ kết thúc; không chạy được trong transaction block.
  5. Nếu concurrent build fail thì DROP rồi chạy lại — deadlock/unique violation để lại index INVALID, vẫn tốn update overhead dù planner ignore.

FSM (Free Space Map): tìm chỗ trống nhanh

Free Space Map (FSM) lưu khoảng trống của từng trang heap/index để INSERT tìm trang có đủ chỗ mà không quét toàn bộ. INSERT/DELETE/HOT update và VACUUM đều cập nhật FSM. FSM là file riêng, thường nằm trong cache và nhỏ hơn nhiều so với heap.

Kiểm chứng khoảng trống bằng extension pg_freespacemap: CREATE EXTENSION IF NOT EXISTS pg_freespacemap; rồi SELECT * FROM pg_freespace('tên_bảng'); để xem cột avail (byte trống) từng trang. FSM chỉ phản ánh không gian đã được VACUUM giải phóng: sau khi DELETE, dead tuple chưa nhả chỗ nên avail vẫn 0 cho tới khi VACUUM chạy. Muốn nhìn theo tuple thay vì theo trang, dùng pgstattuple_approx (CREATE EXTENSION IF NOT EXISTS pgstattuple;).

CREATE TABLE fsm_probe AS SELECT g AS id, repeat('x', 200) AS pad FROM generate_series(1, 400) g;
DELETE FROM fsm_probe WHERE id % 2 = 0;
SELECT count(*) FROM pg_freespace('fsm_probe');  -- 16 trang, avail đều 0
VACUUM fsm_probe;
SELECT min(avail), max(avail) FROM pg_freespace('fsm_probe');  -- 4064 | 5024
SELECT approx_free_percent FROM pgstattuple_approx('fsm_probe');  -- ≈ 50.59

Buffer pool, shared_buffers và clock sweep

PostgreSQL giữ trang dữ liệu trong shared buffer pool (mặc định 128 MB = 16.384 block 8KB). Khi cần đọc trang, nó tìm trong buffer trước: nếu không có thì đọc từ đĩa vào buffer theo cơ chế thay thế clock sweep (một biến thể clock), ưu tiên giữ trang "hot". Với scan tuần tự lớn, ring buffer được dùng để tránh đẩy trang hot ra ngoài.

SHOW shared_buffers;  -- 128MB (16.384 block 8kB)

OS page cache và double-caching

Linux/OS vẫn cache file trên đĩa, nên PostgreSQL có hai lớp cache: buffer pool (nội bộ PG) và OS page cache. Cấu hình hợp lý: đặt shared_buffers ~25% RAM cho workload OLTP trung bình (không ép 100%), tận dụng track_io_timing để đo I/O thực, và cân nhắc effective_io_concurrency cho hệ thống có nhiều disk (hiện effective_io_concurrency = 1). Double-caching là hợp lý: PG có quyền kiểm soát flush (WAL), OS cache giúp đọc tuần tự; không nên vô hiệu hoá OS cache một cách máy móc.

SHOW track_io_timing;  -- on
SHOW effective_io_concurrency;  -- 1

B-tree page split: khi trang đầy

B-tree chia trang (page split) khi không đủ chỗ ghi tuple mới vào trang lá hoặc trang nội bộ. Split tạo trang mới, phân bố key, cập nhật parent. Với fillfactor < 100, mỗi trang để lại khoảng trống để tránh split sớm (hữu ích với UPDATE làm tăng kích thước tuple hoặc HOT update ít hiệu quả). PostgreSQL không tự merge trang B-tree khi tuple bị xóa nhiều (chỉ co lại khi VACUUM/REINDEX hoặc page rỗng hoàn toàn có thể được trả lại); đó là lý do bloat có thể tích tụ nếu không VACUUM đều.

full_page_writes, torn page và crash recovery

Khi trang bị sửa đổi lần đầu sau checkpoint, PostgreSQL ghi toàn bộ trang 8KB vào WAL (full page write) để đảm bảo replay an toàn nếu hệ thống crash giữa lúc ghi một nửa trang (torn page) xuống đĩa. full_page_writes mặc định on; tắt chỉ khi filesystem/storage ngăn được partial page writes (ví dụ ZFS) hoặc controller đảm bảo ghi full 8kB page; BBU write-back thông thường không đủ và chấp nhận rủi ro crash recovery. Giá trị hiện tại xác thực được.

SHOW fsync;  -- on
SHOW wal_buffers;  -- 4MB (= 512 block 8kB)

Query optimizer & EXPLAIN: đọc plan thay vì đoán

Plan chậm đến từ ước lượng sai, không từ cú pháp: planner chọn Nested Loop trên bảng hàng triệu dòng vì statistics cũ hoặc index thiếu cột đúng thứ tự. Học phần này để chạy EXPLAIN ANALYZE đúng cách, chỉ ra node nào ước lượng lệch, sửa một thứ rồi đo lại.

Tám khái niệm quanh một plan

  • Cost-based planner

    Planner tính cost cho mọi access path và mọi thứ tự join rồi chọn plan rẻ nhất, không theo thứ tự viết trong FROM. Cost neo theo seq_page_cost = 1.0, tức đọc tuần tự một block 8kB; không gồm thời gian gửi kết quả về client.

    Bẫy: So cost với milliseconds là sai. Đổi random_page_cost hay work_mem là đổi kết quả chọn plan, không làm query tự nhanh hơn.

  • Statistics và ANALYZE

    Mọi ước lượng rows đến từ statistics. ANALYZE lấy mẫu với minrows = 300 × attstattarget (target 100 → 30.000 dòng), kết quả nằm trong pg_stats: n_distinct, correlation, MCV, histogram.

    Bẫy: Tăng STATISTICS cho cột skew mà không chạy lại ANALYZE thì planner vẫn đọc bảng cũ. Correlation chỉ đổi ước lượng chi phí I/O, không đổi selectivity.

  • EXPLAIN và EXPLAIN ANALYZE

    EXPLAIN in plan ước tính, không đụng dữ liệu. EXPLAIN ANALYZE chạy thật query và thêm actual time, actual rows, loops từng node, là cách duy nhất thấy chỗ estimated lệch actual.

    Bẫy: Actual time và rows là trung bình mỗi lần node chạy, phải nhân với loops mới ra tổng. BitmapAnd và BitmapOr luôn báo actual rows = 0.

  • Index Cond, Filter, Recheck

    Index Cond lọc ngay trong index; Filter là điều kiện quét xong mới lọc, "Rows Removed by Filter" đếm dòng thừa. Recheck Cond là bitmap lossy do work_mem giới hạn nên kiểm tra lại trên heap.

    Bẫy: Index Only Scan vẫn đọc heap khi visibility map chưa set bit all-visible; "Heap Fetches: 0" chỉ đạt sau VACUUM.

  • Ba thuật toán join

    Nested Loop probe từng dòng outer vào inner, hợp khi outer nhỏ và inner có index. Hash Join build hash bên nhỏ rồi probe, chỉ nhận equi-join, tốn tối đa 2 × work_mem. Merge Join merge hai stream đã sort trên join key.

    Bẫy: Chỉ FULL JOIN ghì join order hoàn toàn; INNER JOIN vẫn cho đổi thứ tự bảng, muốn ép thì join_collapse_limit = 1. Batches > 1 là hash tràn temp.

  • Parallel query

    Gather gộp stream từ worker; leader vừa chạy phần parallel vừa đọc toàn bộ tuple worker trả về, nên 4 worker là gấp 5 lần tài nguyên và work_mem tính riêng mỗi worker.

    Bẫy: Workers Planned lớn hơn Workers Launched là pool hết worker. Hàm user-defined mặc định PARALLEL UNSAFE, có trong query là mất plan parallel.

  • work_mem và sort/hash

    work_mem = 4MB tính cho mỗi sort/hash operation của mỗi session, nhân theo số node và số connection. Tràn bộ nhớ thì Sort nhảy external Merge, Hash Join ra "Batches".

    Bẫy: SET work_mem lớn cho mọi session là cách tạo OOM khi vài chục connection cùng sort. enable_seqscan = off không ép được planner.

  • Custom plan và generic plan

    5 lần EXECUTE đầu của prepared statement dùng custom plan với giá trị bind thật; từ lần 6, planner so generic với trung bình cost của 5 plan đó và nhận nếu không cao hơn nhiều.

    Bẫy: EXPLAIN EXECUTE cũng tính vào đếm 5 lần. Generic plan sai khi phân bố tham số lệch giữa test và production.

EXPLAIN dự đoán, EXPLAIN ANALYZE mới lộ sai số

EXPLAIN in plan mà planner định chạy mà không đọc dữ liệu; EXPLAIN ANALYZE thực thi query và in số thật từng node để so estimated với actual. Execution Time gồm trigger, không gồm parse và rewrite.

Đọc node quét: Index Cond, Filter, Recheck Cond

Seq Scan đọc toàn bộ heap; Index Scan tìm dòng trong index rồi nhảy vào heap, điều kiện nằm ở Index Cond. Index Only Scan trả lời ngay từ index khi cột nằm đủ trong index (kể cả INCLUDE) và visibility map đánh dấu trang all-visible. Bitmap Heap Scan đọc heap theo thứ tự vật lý nên mất ORDER BY, planner phải thêm Sort.

Ước lượng lệch bắt đầu ở pg_stats

Sai số estimated rows là nguyên nhân trực tiếp của plan xấu: ước lượng 10 dòng mà thật 10 triệu thì planner chọn Nested Loop và query treo hàng phút. Chưa có statistics thì planner giả định 200 distinct, equality selectivity = 0.005, range = 1/3. Predicate AND được mô phỏng độc lập với nhau, nên nhiều điều kiện correlated trên cùng phân bố bị ước lượng sai nặng.

SELECT attname, n_distinct, correlation, null_frac, avg_width
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

n_distinct âm nghĩa là (−số distinct / số dòng), đúng −1 là cột unique. Correlation trong khoảng −1 đến +1 chỉ đổi chi phí I/O ước tính cho index scan: gần 0 nghĩa là row vật lý xáo trộn nên planner tính random I/O đắt, kể cả khi index chọn được rất ít dòng. default_statistics_target = 100, đổi target xong phải chạy lại ANALYZE.

  1. Chạy EXPLAIN (ANALYZE), tìm node có sai số estimated với actual lớn nhất.
  2. Kiểm tra cột WHERE qua pg_stats: n_distinct, null_frac, correlation đã đủ mới chưa.
  3. Đổi một thứ: SET STATISTICS rồi ANALYZE, hoặc tạo index đúng thứ tự cột.
  4. Chạy lại cùng query, so rows và actual time; cải thiện thì giữ, không thì lùi.

CREATE STATISTICS cho tổ hợp cột tương quan

WHERE tenant_id = 42 AND status = 'active' trên bảng orders nhiều tenant: mỗi tenant có phân bố status riêng, còn planner vẫn nhân selectivity hai cột như thể chúng độc lập, estimated rows lệch actual và plan được chọn trên con số đó. CREATE STATISTICS, có từ PostgreSQL 10, khai statistics object trên tổ hợp cột; lệnh chỉ ghi catalog, ANALYZE mới đọc bảng và điền dữ liệu, nên chạy CREATE xong mà chưa ANALYZE thì planner vẫn ước lượng theo dữ liệu cũ. Tùy chọn mcv thêm ở PostgreSQL 12.

Khai kind trong ngoặc: dependencies ghi mức một cột xác định cột kia (stxddependencies), ndistinct đếm số distinct của tổ hợp từ hai cột trở lên (stxdndistinct), mcv giữ các tổ hợp giá trị hay gặp kèm tần suất (stxdmcv); bỏ trống danh sách kind thì object lấy hết kind hỗ trợ. Kind đã khai nằm ở cột stxkind của pg_statistic_ext, dữ liệu thu được nằm ở pg_statistic_ext_data. Extended statistics hiện chỉ dùng cho selectivity trong một bảng, ước lượng join chưa dùng tới.

CREATE STATISTICS st_tenant_status (dependencies, ndistinct) ON tenant_id, status FROM orders;
CREATE STATISTICS st_tenant_status_mcv (mcv) ON tenant_id, status FROM orders;
ANALYZE orders;   -- hai statistics object chưa có dữ liệu cho tới khi ANALYZE chạy

SELECT stxname, stxkeys, stxddependencies, stxdndistinct
FROM pg_statistic_ext JOIN pg_statistic_ext_data ON (oid = stxoid)
WHERE stxname LIKE 'st_tenant_status%';

Parallel query: điều kiện hẹp, tài nguyên gấp 5

Planner cân bằng chi phí setup (parallel_setup_cost = 1000, parallel_tuple_cost = 0.1) với kích thước quét, sàn là min_parallel_table_scan_size = 8MB. "Workers Planned" là planner định dùng, "Workers Launched" là thực tế có; lệch nghĩa là worker pool đã hết. Defaults: max_parallel_workers_per_gather = 2, max_parallel_workers = 8.

Query có write thì không được parallel, kể cả write trong CTE, ngoại lệ CREATE TABLE AS, SELECT INTO và REFRESH MATERIALIZED VIEW. DECLARE CURSOR, vòng lặp PL và hàm PARALLEL UNSAFE cũng chặn; hàm user-defined mặc định PARALLEL UNSAFE tới khi được đánh dấu PARALLEL SAFE.

EXPLAIN (ANALYZE, VERBOSE)

Phân trang sâu và plan của prepared statement

OFFSET lớn buộc server đi qua và vứt bỏ từng đó dòng theo định nghĩa, tài liệu PostgreSQL gọi là inefficient với OFFSET lớn. Keyset so sánh với hàng cuối trang trước bằng row-value comparison, đi thẳng vùng index kế tiếp. LIMIT không kèm ORDER BY thì subset không xác định, planner dùng LIMIT/OFFSET lúc plan nên hai trang liên tiếp có thể ra thứ tự khác. Thiếu tiebreaker là id thì dòng chèn giữa hai lần fetch làm hàng lặp hoặc lọt.

PREPARE p(bigint) AS SELECT * FROM orders WHERE customer_id = $1;

Đo bằng pg_stat_statements và auto_explain

Không có measurement thì mọi "tối ưu" là đoán. pg_stat_statements cộng dồn calls, total_exec_time, mean_exec_time, rows theo queryid; lọc mean_exec_time DESC ra query đắt nhất. auto_explain ghi plan query vượt ngưỡng log_min_duration, mặc định −1 là tắt; log_analyze = true bật per-node timing cho mọi statement, kéo I/O và CPU tăng nên chỉ bật khi đang đo.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT queryid, calls, round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms, rows
FROM pg_stat_statements
WHERE query NOT ILIKE '%pg_stat_statements%'
ORDER BY mean_exec_time DESC
LIMIT 10;

-- superuser: đo kế hoạch query của app
LOAD 'auto_explain';
SET auto_explain.log_min_duration = '200ms';
SET auto_explain.log_analyze = true;

N+1 của Prisma hiện ra ở đây: hàng trăm query cùng mẫu nối nhau với calls cao. prisma include vẫn là hai câu query (bảng cha rồi relation) khi chưa bật relationJoins. Khi bật preview relationJoins trong generator, Prisma chuyển sang chiến lược JOIN một câu — lúc đó relationLoadStrategy mặc định đã là join, muốn giữ multi-query thì đặt =query. dataloader chỉ batch findUnique với cùng params nên findMany trong vòng lặp vẫn là N+1 thật. Thêm index không sửa N+1, chỉ làm từng câu bớt đau; sửa bằng include/select hoặc findMany với danh sách id. pg_stat_user_indexes với idx_scan = 0 là index chết; CTE tham chiếu đúng một lần được fold nên predicate pushdown chạy, chi tiết ở phần SQL chuyên sâu.

Đọc EXPLAIN một lần trên bảng 100 dòng của dev rồi kết luận cho production 100 triệu dòng là sai phương pháp: plan đổi theo quy mô và statistics. Tương tự, để log_analyze = true lâu trong production làm tăng I/O và CPU rõ rệt. Quy tắc đo: reproduce với data cùng quy mô, EXPLAIN ANALYZE, đổi một thứ, đo lại.

Đọc cây plan: root → leaf, startup cost vs total cost

Plan là cây (tree): node cha nhận tuple từ node con. Đọc từ leaf → root để hiểu dữ liệu đi qua đâu, nhưng diễn giải chi phí đọc từ root → leaf: node gốc (root) là node trả kết quả cuối cùng. Mỗi node có startup cost (chi phí để trả về hàng đầu tiên) và total cost (chi phí để trả về toàn bộ hàng). Chi phí là đơn vị ước tính của planner (so sánh tương đối), không phải milliseconds.

HashAggregate vs GroupAggregate + work_mem

GroupAggregate yêu cầu input đã sắp xếp theo key nhóm (Group Key), thường đi kèm Sort hoặc Incremental Sort trước; trả kết quả khi key đổi. HashAggregate build hash table của các nhóm trong bộ nhớ (work_mem), không cần sort input, có thể dùng Partial HashAggregate → Finalize HashAggregate (parallel). Khi hash table không đủ chứa tất cả nhóm, PostgreSQL chia thành nhiều batch (Batches > 1) và có thể ghi ra đĩa (Disk Usage) — đây là dấu hiệu spill.

Materialize / CTE Scan nodes

Materialize lưu tạm kết quả của một subnode (thường inner side của Nested Loop được probe nhiều lần) vào bộ nhớ/temp để tránh tính lại. CTE Scan đọc kết quả của CTE. Từ PostgreSQL 12, CTE side-effect-free được inline (fold) vào query cha nếu chỉ tham chiếu đúng 1 lần. Nếu tham chiếu nhiều hơn 1 lần, mặc định CTE được MATERIALIZED (tạo CTE Scan đọc kết quả đã lưu). Có thể ép bằng WITH cte AS MATERIALIZED (...) hoặc NOT MATERIALIZED.

EXPLAIN (COSTS OFF)
WITH cte AS MATERIALIZED (
  SELECT user_id, score FROM plan_items WHERE cat = 'a'
)
SELECT (SELECT count(*) FROM cte) AS n1,
       (SELECT max(score) FROM cte) AS n2;

Trong plan trên, CTE cte xây dựng tập kết quả (Bitmap Heap/Index Scan), sau đó InitPlan 2 và InitPlan 3 mỗi cái chạy một CTE Scan on cte (đọc lại kết quả đã materialize). Ngược lại, nếu dùng NOT MATERIALIZED và CTE vẫn an toàn (side-effect-free) nhưng được tham chiếu nhiều lần, planner có thể không materialize — cần cân nhắc chi phí tính lại.

Materialize cũng xuất hiện trong Nested Loop khi inner side phải được đọc lại nhiều lần (vd. outer lớn, inner không index hiệu quả) để tránh I/O lặp lại.

Memoize node (PostgreSQL 14+)

Memoize cache kết quả của node con theo Cache Key (thường là giá trị join key). Khi Nested Loop probe inner nhiều lần với cùng key, Memoize trả về kết quả từ cache (Hits) thay vì chạy lại inner scan. Điều kiện thường gặp: Nested Loop, inner side là Index Scan/Index Only Scan, các probe lặp lại nhiều key giống nhau (workload có nhiều bản sao key).

BEGIN;
SET LOCAL max_parallel_workers_per_gather = 0;
SET LOCAL enable_hashjoin = off;
SET LOCAL enable_mergejoin = off;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT l.k, count(r.id) FROM memo_left l
JOIN memo_right r ON r.k = l.k
GROUP BY l.k;
ROLLBACK;

Trong trường hợp có Memoize: xuất hiện node Memoize với Cache Key: r.k, Cache Mode: logical, Hits: … Misses: … Evictions: … Overflows: … Memory Usage: …kB. Nếu tắt enable_memoize = off, Nested Loop sẽ probe inner trực tiếp (thường tăng số lần truy cập index/heap). Memoize hữu ích khi outer tạo nhiều probe trùng lặp; với probe gần như toàn duy nhất, cache ít hiệu quả.

Bẫy: Memoize chỉ xuất hiện trong một số cấu hình Nested Loop (PG14+). Nếu không thấy node này trong plan, đó có thể do probe không đủ trùng lặp để planner chọn, hoặc inner side không phù hợp.

JIT (Just-In-Time compilation)

JIT biên dịch expression và một số đoạn execution thành native code để giảm overhead, chủ yếu có lợi với query tính toán nặng, quét lớn, nhiều tuple. GUC liên quan: jit (on/off), jit_above_cost (default 100000), jit_optimize_above_cost (default 500000), jit_inline_above_cost, jit_tuple_deforming.

EXPLAIN (COSTS ON)
SELECT sum(g::bigint) FROM generate_series(1, 50000000) g;

Plan có thể hiển thị block JIT: với Functions: N và Options: Inlining…, Optimization…, Expressions…, Deforming… khi tổng cost vượt ngưỡng. Với query nhỏ (total cost < jit_above_cost) planner thường không bật JIT. Container này có jit=on; bật JIT chỉ khi benefit vượt overhead biên dịch.

Bẫy: JIT giúp query CPU-bound lớn; với I/O-bound nặng, hiệu quả thường nhỏ. Overhead đo EXPLAIN ANALYZE vẫn tồn tại.

Runtime partition pruning vs plan-time pruning

Plan-time pruning: giá trị điều kiện là hằng/pseudoconstant (biết tại thời điểm lập plan) → planner loại bỏ partition ngay trong plan (có thể thấy Seq Scan chỉ trên partition còn lại, hoặc Append chỉ giữ child cần thiết).

Runtime partition pruning: giá trị điều kiện chỉ biết lúc thực thi (subquery/INITPLAN, expression phụ thuộc runtime, parameter từ prepared statement EXECUTE trong một số trường hợp) → planner vẫn đưa tất cả partition vào Append, nhưng khi chạy sẽ loại bỏ partition không cần. Runtime pruning thể hiện qua child marked never executed trong EXPLAIN ANALYZE; trường Subplans Removed trong JSON đếm subplan bị loại ở plan-time, không phải child bỏ qua lúc runtime. Với EXPLAIN ANALYZE trên partitioned table, partition không được chạm có thể hiện never executed.

-- plan-time pruning (constant bounds)
EXPLAIN (COSTS OFF)
SELECT count(*) FROM events_rt
WHERE ts >= '2024-02-01' AND ts < '2024-02-15';

-- runtime pruning (subquery/INITPLAN)
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT count(*) FROM events_rt
WHERE ts >= (SELECT '2024-02-01'::timestamptz)
  AND ts <  (SELECT '2024-02-15'::timestamptz);

Ví dụ runtime: Append có 4 child partition, 3 child never executed (chỉ 2024_02 chạy) nghĩa là 3 partition bị loại bỏ lúc runtime (2024_01, 2024_03, 2024_04). Ngược lại plan-time chỉ thấy 1 child Seq Scan trên partition tương ứng. Runtime pruning thể hiện qua child marked never executed trong EXPLAIN ANALYZE; trường Subplans Removed trong JSON đếm subplan bị loại ở plan-time và ở đây bằng 0. Pruning dựa trên partition bounds, không đòi hỏi index trên partition key (index phục vụ selectivity trong partition).

Bẫy: Dùng subquery/biểu thức làm tham số khoảng thời gian có thể chuyển pruning từ plan-time sang runtime. enable_partitionwise_join/aggregate mặc định off, chỉ bật khi join key chứa trọn partition key và tập dữ liệu khớp 1-1.

PostgreSQL internals: MVCC, VACUUM và vận hành

PostgreSQL không ghi đè row: mỗi UPDATE tạo một version mới và để lại dead tuple, còn VACUUM là lệnh duy nhất trả chỗ đó về cho database. Học phần này để đọc header của tuple đang sống bằng psql, ước lượng bloat, chọn isolation level cho NestJS/Prisma, và phát hiện XID wraparound trước khi server chuyển sang read-only.

Tuple header: xmin, xmax và vị trí vật lý của row

Mỗi tuple trên heap mang theo xmin (XID tạo version), xmax (XID xóa hoặc lock, bằng 0 nếu row chưa bị đụng tới), cmin/cmax (command ID bên trong transaction), ctid (vị trí vật lý, đổi khi UPDATE phải sang page khác hoặc khi VACUUM FULL rewrite) và tableoid. UPDATE ghi version mới với xmin của chính nó, stamp xmax lên version cũ, và version cũ trở thành dead tuple cho tới khi bị prune hoặc VACUUM thu gom. Index không trỏ tới row, index trỏ tới ctid, nên cùng một dòng logic đọc được cả trước và sau khi UPDATE chuyển bản ghi sang page khác.

SELECT ctid, xmin, xmax, cmin, cmax, id, balance
FROM accounts
WHERE id = 1;

xmax khác 0 không có nghĩa row đã bị DELETE: giao dịch xóa có thể còn uncommitted, hoặc đã abort và giá trị sẽ trở về. Kết luận "row biến mất" chỉ đúng khi transaction của xmax đã commit và bản version mới không còn visible với snapshot của bạn.

Snapshot: đơn vị cách ly dữ liệu trong MVCC

Snapshot gồm xmin (mọi XID nhỏ hơn đã hoàn tất), xmax (ngưỡng trên của dải XID đang chạy) và danh sách xip (các XID in-progress), hiển thị dạng xmin:xmax:xip, ví dụ 10:20:10,14,15. Từ PostgreSQL 13 dùng pg_snapshot với kiểu xid8 64-bit, nhóm hàm txid_* đã deprecated. Tuple visible với snapshot khi xmin đã commit trước snapshot (hoặc chính là XID hiện tại) và xmax chưa commit hoặc không nằm trong snapshot. Snapshot không chặn writer: writer vẫn ghi, reader cũ vẫn thấy version cũ, đó là lý do bloat hình thành.

SELECT pg_current_snapshot();

SELECT (pg_snapshot_xmin(pg_current_snapshot()))::text AS xmin,
       (pg_snapshot_xmax(pg_current_snapshot()))::text AS xmax,
       (pg_snapshot_xip(pg_current_snapshot()))::text  AS xip;
Lab hai psql session: thấy xmax chạy trước mặt mình

Session A giữ transaction mở, session B UPDATE và COMMIT. A vẫn thấy số dư cũ, đồng thời xmax của version cũ đã khác 0, chứng minh hai session đọc hai version khác nhau của cùng một row. Session A cần Repeatable Read, vì dưới Read Committed mặc định mỗi statement lấy snapshot mới và A sẽ thấy 900 ngay.

-- Session A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT id, balance FROM accounts WHERE id = 1;   -- 1000

-- Session B (psql khác)
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- Session A
SELECT ctid, xmin, xmax, balance FROM accounts WHERE id = 1;
-- vẫn thấy 1000, xmax đã bằng XID của session B
ROLLBACK;

Isolation level: hợp đồng hành vi với application

PostgreSQL 16 map Read Uncommitted về Read Committed. Mặc định Read Committed lấy snapshot mới cho mỗi statement; Repeatable Read là Snapshot Isolation, mạnh hơn SQL standard ở chỗ chặn phantom, và ném could not serialize access due to concurrent update khi ghi tranh; Serializable dùng SSI với predicate lock không block, lỗi SQLSTATE 40001. Chỉ writer cần retry. Sequence không thuộc transaction, và dưới Read Committed, SELECT FOR UPDATE re-evaluate WHERE trên version được update song song.

  • Dead tuple & table bloat

    Mỗi UPDATE/DELETE để lại version đã chết, chiếm không gian page; sequential scan phải skip qua chúng nên query chậm dần theo tỉ lệ dead/live. pgstattuple_approx trả về dead_tuple_percent để đo thay vì đoán.

    Bẫy: pg_total_relation_size không giảm sau VACUUM plain là bình thường, plain VACUUM chỉ đánh dấu không gian reusable trong relation, không trả về OS.

  • HOT update

    Heap-Only Tuple: UPDATE chỉ thành công theo hướng HOT khi không cột indexed nào thay đổi và còn free space trên cùng page, khi đó không cần index entry mới. Old versions bị loại ngay trong lúc SELECT chạy thay vì chờ VACUUM.

    Bẫy: UPDATE mọi cột, kể cả updated_at = now(), trên bảng có index liên quan thì không HOT, bloat tăng theo từng request.

  • Visibility map

    VACUUM plain ghi bitmap đánh dấu page chỉ chứa tuple visible, cho phép index-only scan trả lời truy vấn chỉ từ index, bỏ qua heap; vacuum cũng dùng bit này để bỏ qua page đã all-frozen.

    Bẫy: bloat làm mất page "sạch" trong visibility map, index-only scan rụng về heap fetch, EXPLAIN đổi chữ mà không ai sửa query.

  • TOAST

    Row vượt ngưỡng khoảng 2 kB được tách thành chunk khoảng 2000 B (1996 B trên page 8 kB, 4 chunk mỗi page) cộng pointer 18 byte; chiến lược mặc định EXTENDED, nén pglz trước khi tách, giá trị lớn nhất 2^30−1 byte. Giá trị ngoài không đổi thì UPDATE không tốn I/O đọc lại.

    Bẫy: SELECT * trên bảng có text/jsonb lớn buộc detoast mọi cột, tốn CPU và network cho dữ liệu không dùng tới.

  • backend_xmin & vacuum horizon

    Mọi session giữ snapshot đều kìm horizon mà VACUUM được phép thu hồi; backend_xmin trong pg_stat_activity cho biết session nào đang giữ.

    Bẫy: idle_in_transaction_session_timeout mặc định 0, tức không bao giờ tự cắt, session quên COMMIT giữ horizon vô thời hạn.

  • pg_stat_progress_vacuum

    VACUUM đang chạy lộ 7 phase: initializing, scanning heap, vacuuming indexes, vacuuming heap, cleaning up indexes, truncating heap, performing final cleanup, kèm số page đã quét để ước lượng thời gian còn lại.

    Bẫy: tiến độ là per-backend; không thấy dòng nào nghĩa là autovacuum chưa cần chạy, không phải nó hỏng.

HOT update và fillfactor: giảm bloat ngay tại chỗ

fillfactor của table mặc định 100 (vùng 10–100), của B-tree index mặc định 90; TOAST table không nhận tham số này. Hạ fillfactor để trống chỗ cho HOT trên bảng update-heavy, giá trị chỉ có hiệu lực với page được ghi mới, không xén page cũ. XID wraparound: failure mode khiến server từ chối ghi

XID là 32-bit, mỗi table phải được freeze ít nhất một lần mỗi khoảng 2 tỷ transaction, nếu không PostgreSQL không phân biệt được version cũ với version chưa sinh. autovacuum_freeze_max_age mặc định 200 triệu, và chuỗi anti-wraparound này vẫn chạy kể cả khi autovacuum bị tắt trên table. Các mốc theo thứ tự: WARNING khi còn khoảng 40 triệu XID, ERROR database is not accepting commands to avoid wraparound data loss khi còn dưới 3 triệu, database chuyển sang chỉ nhận read-only.

-- Bảng nào đang tiến gần ngưỡng
SELECT c.relname, n.nspname, age(c.relfrozenxid) AS xid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY xid_age DESC
LIMIT 15;

-- Database-level
SELECT datname, age(datfrozenxid) AS db_xid_age FROM pg_database;
  1. Tìm session giữ horizon: state = 'idle in transaction' với backend_xmin khác NULL, và replication slot chưa advance trong pg_replication_slots.
  2. Cắt nguồn giữ horizon trước: pg_terminate_backend(pid) cho session kẹt, pg_drop_replication_slot cho slot không còn instance nào đọc.
  3. Chạy plain VACUUM cho các bảng có xid_age cao nhất, theo dõi age(relfrozenxid) giảm sau từng lệnh.
  4. Xác nhận WARNING wraparound biến mất trong log trước khi mở lại traffic ghi; chống tái diễn bằng cảnh báo trên age() và idle_in_transaction_session_timeout.

Khủng hoảng wraparound xử lý bằng session cleanup cộng plain VACUUM, không dùng VACUUM FULL và không dùng VACUUM FREEZE: FULL lấy ACCESS EXCLUSIVE khi server đang gần từ chối ghi, FREEZE làm chậm lệnh vốn đã kẹt vì session giữ horizon.

Infomask và hint bits (HEAP_XMIN_COMMITTED/HEAP_XMIN_INVALID)

Tuple header lưu t_infomask (2 byte) chứa bit trạng thái để tránh phải đọc clog mỗi lần xác định xem xmin/xmax đã commit hay abort. Khi transaction commit/abort, PostgreSQL không cập nhật ngay mọi tuple trên disk — thay vào đó nó ghi hint bit lên tuple khi tuple đó được đọc lần đầu (lazy) hoặc khi VACUUM/VACUUM FREEZE chạy. Điều này giảm I/O đọc clog nhiều lần, đặc biệt với workload đọc nặng.

Các bit quan trọng (PostgreSQL 16): HEAP_XMIN_COMMITTED (0x0100), HEAP_XMIN_INVALID (0x0200), HEAP_XMAX_COMMITTED (0x0400), HEAP_XMAX_INVALID (0x0800), cùng cờ HEAP_XMIN_FROZEN = HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID (0x0300) được VACUUM FREEZE đặt khi xmin đã vượt ngưỡng anti-wraparound. Khi hint bit được set, visibility check rút ngắn: không cần tra pg_xact (clog) nữa.

-- Đọc infomask sau khi SELECT 1 row (hint bits đã set cho xmin committed)
SELECT lp, t_xmin, t_xmax, t_infomask,
       ((t_infomask::int) & 256)  <> 0 AS xmin_committed,
       ((t_infomask::int) & 512)  <> 0 AS xmin_invalid,
       ((t_infomask::int) & 1024) <> 0 AS xmax_committed,
       ((t_infomask::int) <> 0 AND ((t_infomask::int) & 2048) <> 0) AS xmax_invalid_mask
FROM heap_page_items(get_raw_page('hint_demo', 0))
ORDER BY lp LIMIT 2;

Bẫy: t_infomask là số nguyên 16-bit; dùng bitwise AND với kiểu số nguyên (bigint/int) khi decode. Hint bit chỉ được set lazily (khi tuple được đọc) hoặc bởi VACUUM — không được ghi ngay khi transaction commit.

pageinspect: đọc trực tiếp trang heap/B-tree

pageinspect cho phép xem cấu trúc trang vật lý (heap, B-tree, TOAST) để hiểu visibility, ctid, infomask thực tế. Trên container này đã cài pageinspect (extension plpgsql hiện có). Hàm hữu ích: get_raw_page(relname, blkno), heap_page_items(page), bt_metap(relname), bt_page_stats(relname, blkno).

-- Heap page items: ctid, xmin, xmax, t_infomask, lp_flags
SELECT lp, lp_off, lp_flags, t_xmin, t_xmax, t_ctid, t_infomask
FROM heap_page_items(get_raw_page('ver_demo', 0))
ORDER BY lp;

lp_flags: 1 = LP_NORMAL (normal), 2 = LP_REDIRECT (HOT redirect), 3 = LP_DEAD (đã được VACUUM đánh dấu). Sau khi VACUUM trên ver_demo, version cũ (lp 1) chuyển sang HOT redirect (lp_flags=2), version còn sống (lp 2) giữ lp_flags=1. Trong trường hợp bảng có index (non-HOT), version cũ sẽ chuyển thành LP_DEAD (lp_flags=3) sau VACUUM.

Data checksums, wal_log_hints và full_page_writes

Data page checksums: bật bằng initdb --data-checksums (hoặc -k) để ghi checksum 16-bit vào page header, giúp phát hiện corruption trên storage. Kiểm tra: SHOW data_checksums; hoặc SELECT data_page_checksum_version FROM pg_control_init();. Container hiện tại có data_checksums = off, data_page_checksum_version = 0. PostgreSQL 18 chuyển sang bật mặc định ở một số build, nhưng việc bật yêu cầu initdb lại toàn bộ cluster.

wal_log_hints: khi bật (hoặc khi data_checksums bật), PostgreSQL ghi full-page write hints/WAL trước khi ghi page bị thay đổi lần đầu sau checkpoint (full page image) để recovery an toàn khi storage có torn page. full_page_writes mặc định on (bảo vệ crash recovery). archive_mode hiện off, archive_command disabled — nghĩa là PITR qua WAL archive chưa bật trên cluster này.

SHOW wal_log_hints;

SHOW archive_command;

Bẫy: Bật data_checksums sau initdb là không thể; chỉ có thể initdb lại. full_page_writes nên giữ on trừ khi storage đã bảo đảm atomic page write (ZFS, certain SAN) và đã test crash recovery kỹ.

Replication, partitioning & khi nào rời RDBMS

HA không đến từ một GUC: streaming replication ship WAL theo byte nhưng async là mặc định; logical replication cho row filter nhưng không replicate sequence; partitioning cắt I/O nhờ pruning chứ không nhờ index. Học phần này để đọc được pg_stat_replication, dựng publication có filter, DROP PARTITION retention O(1), và biết lúc nào KHÔNG nên rời PostgreSQL.

Bảy khái niệm quyết định topology

  • Streaming replication (physical)

    Primary ship WAL byte-level; standby mở hot standby read-only. Bản sao block-level y hệt, không chọn lọc table. Failover bằng Patroni: leader lock trên DCS (etcd/Consul), ttl=30, loop_wait=10, retry_timeout=10, bất biến loop_wait + 2×retry_timeout ≤ ttl.

    Bẫy: Async mặc định: commit xong nhưng WAL chưa tới standby là mất data khi failover. Slot inactive giữ WAL vô thời hạn, đầy pg_wal.

  • Synchronous commit

    synchronous_standby_names ép commit chờ standby flush: quorum 'ANY 1 (s1,s2)' hoặc 'FIRST 1 (s1)'. synchronous_commit set per-transaction/per-role: remote_apply > on > remote_write > local > off.

    Bẫy: off vẫn mất tối đa 3×wal_writer_delay ≈ 600ms. Sync standby chết không thay thế thì commit treo vô hạn. Cascading replication LUÔN async.

  • Replication lag

    Chuỗi LSN trên primary: sent_lsn → write_lsn → flush_lsn → replay_lsn; lag thời gian là write_lag / flush_lag / replay_lag. Standby: pg_last_wal_receive_lsn() vs pg_last_wal_replay_lsn().

    Bẫy: replay_lag là NULL, không phải 0, monitoring treat NULL là healthy sẽ báo sai. Replay chậm vì CPU vẫn là SPOF khi failover.

  • Logical replication

    Publication/subscription: row filter + column list (PG15+), cross-version, CDC ra Kafka/Debezium (pgoutput built-in). PG16 thêm streaming = off|on|parallel cho transaction lớn. Cần wal_level=logical.

    Bẫy: DDL và sequence counter không replicate, cut-over phải setval thủ công. Bảng không PK cần REPLICA IDENTITY trước khi UPDATE/DELETE.

  • Declarative partitioning

    RANGE/LIST/HASH; pruning chạy theo partition bound, KHÔNG cần index trên khoá. Retention = DETACH CONCURRENTLY + DROP: không VACUUM reclaim hàng triệu row.

    Bẫy: PK partitioned table phải include toàn bộ partition key. UPDATE partition key move row giữa partition. Vài trăm partition là upper bound hợp lý khi query prune về ít.

  • Sharding (Citus / FDW)

    Citus hash rows theo distribution column; reference table replicate mọi worker; co-location cho join không qua network. FDW: pushdown chỉ trong cùng foreign server.

    Bẫy: Hotspot tenant quá lớn → một shard quá tải. FDW không 2PC cross-server, isolation remote mặc định REPEATABLE READ.

  • Outbox pattern

    Ghi event vào bảng outbox trong CÙNG transaction business; relay bằng polling FOR UPDATE SKIP LOCKED hoặc CDC. At-least-once, consumer phải idempotent.

    Bẫy: CDC slot inactive giữ WAL đầy disk. Debezium có thể emit duplicate quanh snapshot boundary, exactly-once không có sẵn.

Dựng streaming replication: primary + standby

Primary cần wal_level=replica (default PG16; minimal cấm max_wal_senders>0, server không start). max_wal_senders/max_replication_slots default 10, WAL segment 16MB; recovery_target_timeline=latest cho standby follow timeline mới sau failover.

-- primary (postgresql.conf): wal_level=replica, max_wal_senders=10
CREATE ROLE repl LOGIN REPLICATION PASSWORD 'replpass';
-- pg_hba.conf: host replication repl 10.0.0.0/8 md5

-- standby: -R tự tạo standby.signal + primary_conninfo
pg_basebackup -h primary.example.com -D /var/lib/postgresql/16/main -U repl -R -P
pg_ctlcluster 16 main start

-- verify: SELECT * FROM pg_stat_replication;   (primary)
--         SELECT * FROM pg_stat_wal_receiver;  (standby)

Patroni: synchronous_mode=on chỉ cho last known leader hoặc synchronous replica join leader race; synchronous_mode_strict block writes khi không có sync replica. Test patronictl switchover trước khi cần thật.

Cascading replication (standby → standby) luôn asynchronous: synchronous_standby_names chỉ áp cho direct-connected standbys. hot_standby_feedback=true chống vacuum conflict trên standby nhưng làm bloat primary khi standby có query dài chạy lâu, feedback giữ horizon cleanup của primary (PG16 đã bỏ vacuum_defer_cleanup_age).

Logical replication: publication / subscription

Cho subset table, cross-version PG, CDC ra Kafka/Debezium, và zero-downtime migration (replicate sang PG mới song song rồi cut-over). max_parallel_apply_workers_per_subscription mặc định 2 khi streaming=parallel. Row filter chỉ nhận simple expressions, không user-defined function/operator, không system column.

-- publisher:
CREATE PUBLICATION pub_orders FOR TABLE public.orders
  WHERE (created_at >= '2024-01-01')
  WITH (publish = 'insert,update,delete');

-- subscriber:
CREATE SUBSCRIPTION sub_orders
  CONNECTION 'host=newpg dbname=app user=repl password=...'
  PUBLICATION pub_orders
  WITH (connect = true, copy_data = true, streaming = parallel);

-- apply_error_count > 0 là subscription đang kẹt:
SELECT subname, apply_error_count, sync_error_count FROM pg_stat_subscription_stats;
SELECT subname, latest_end_time FROM pg_stat_subscription;

Cut-over checklist vì logical replication không replicate DDL: (1) thêm cột bên subscriber TRƯỚC theo kiểu additive; (2) sync sequence bằng setval(max(id)) ngay trước khi chuyển ghi; (3) dừng ghi publisher → chờ apply hết → drop subscription. Bỏ bước 2 là duplicate key ngay sau cut-over.

Partitioning & retention: thao tác cụ thể

CREATE TABLE events (
  id bigserial,
  created_at timestamptz NOT NULL,
  payload jsonb
) PARTITION BY RANGE (created_at);
CREATE TABLE events_2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE INDEX ON events (created_at DESC);

-- pruning: plan chỉ chạm partition trong khoảng truy vấn
EXPLAIN (ANALYZE, COSTS OFF)
SELECT count(*) FROM events
WHERE created_at >= '2024-01-15' AND created_at < '2024-01-20';

-- retention: detach không cần ACCESS EXCLUSIVE, không VACUUM reclaim
ALTER TABLE events DETACH PARTITION events_2024_01 CONCURRENTLY;
DROP TABLE events_2024_01;

-- attach partition mới: pre-create bằng LIKE ... INCLUDING CONSTRAINTS
-- + ADD CONSTRAINT CHECK khớp bounds, rồi ATTACH PARTITION FOR VALUES ...
  • Bounds: inclusive lower, exclusive upper, value 2024-02-01 thuộc partition kế, không phải events_2024_01.
  • Pruning chỉ dựa trên bounds; index trên partition key phục vụ selectivity trong partition. enable_partitionwise_join/aggregate default off; bật chỉ có lợi khi join key chứa trọn partition key và sets khớp 1-1.
  • DETACH CONCURRENTLY chỉ lấy SHARE UPDATE EXCLUSIVE; DETACH thường và DROP TABLE lấy ACCESS EXCLUSIVE. Drop partition lớn giờ cao điểm block query.

CAP & PACELC đọc đúng nghĩa

CAP chỉ mô hình network partition; Consistency trong CAP là linearizability, khác C của ACID; CAP không nói gì về latency. PACELC bù: nếu Partition chọn A hay C, Else chọn L hay C. Kleppmann đề nghị bỏ nhãn "CP/AP cho database": mỗi thao tác trong một hệ có thể mang consistency khác nhau.

  • RDS Multi-AZ: AWS quản synchronous_standby_names, failover ~tens of seconds đổi DNS endpoint, standby không serve reads (cần Multi-AZ cluster hoặc read replica riêng).
  • Patroni tự dựng: toàn quyền topology/extension; phải tự test patronictl switchover định kỳ, route reads qua HAProxy.

Nhãn "AP system" không miễn trừ invariant business: CAP nói về hành vi KHI partition, không cho phép bỏ transaction integrity lúc bình thường. Ngược lại, sync replication không tự động cho HA, nó chỉ đảm bảo durability khi configure đúng; failover vẫn cần thứ gì đó promote standby.

Khi nào rời relational và khi nào quay lại

  1. Còn multi-table invariant cần ACID? Ở lại PostgreSQL, full-text cơ bản chạy bằng GIN + to_tsvector.
  2. Query là search/facet/ranking nâng cao (typo tolerance, relevance)? Tách sang Elasticsearch làm derived index; PostgreSQL vẫn là source of truth, sync qua CDC.
  3. Query là "đường đi" qua nhiều hop (> 3-4), không phải lookup? Cân nhắc graph DB. Con số "3-4 hops" là tiếp thị vendor, tự benchmark với workload thật.
  4. Access pattern là cache/session/counter chịu tải cao? Redis với TTL + invalidation theo outbox event.
  5. Schema đổi mỗi tuần vì document polymorphic? Document store; đổi lại mất JOIN và constraint.
  6. Mọi store mới là một backup, một monitoring, một oncall, polyglot persistence (Fowler) chỉ đáng cho strategic workload.

pg_rewind: đồng bộ lại standby sau timeline split/failover

pg_rewind cho phép rewind (lùi về thời điểm trước diverge) một cluster PostgreSQL để biến nó thành standby hợp lệ của primary mới sau timeline split (vd. failover async, primary cũ vẫn chạy một thời gian). Khác với pg_basebackup (phải copy toàn bộ cluster từ đầu), pg_rewind chỉ sửa các block bị lệch về phía sau so với primary mới.

Điều kiện: cần (wal_log_hints = on hoặc data_checksums = on khi initdb) và full_page_writes = on để pg_rewind có thể đọc đủ thông tin reconstruct changes; cũng cần connection tới primary mới. pg_rewind không thay thế PITR — nó dùng để resync một node cũ đã diverge thành standby hợp lệ.

Bẫy: Nếu wal_log_hints = off và data_checksums = off, pg_rewind có thể không thể xác định chính xác các block cần sửa. Luôn verify điều kiện trước khi dùng trong production.

pg_dump vs pg_basebackup, archive_command/restore_command và PITR

pg_dump là công cụ logical backup: xuất dữ liệu/schema ở dạng SQL (hoặc custom format) theo một snapshot tại thời điểm chạy. Nó không sao chép WAL liên tục, không phục vụ PITR theo thời điểm bất kỳ. Ưu điểm: có thể restore vào cluster khác major version (có giới hạn), restore chọn lọc database/table, nhỏ gọn hơn khi chỉ cần subset. Nhược điểm: không thể restore tới microsecond cụ thể, restore chậm hơn so với physical restore cho toàn bộ DB lớn.

pg_basebackup là physical backup (block-level): copy toàn bộ data directory ở thời điểm consistent (dùng backup_label + WAL bắt đầu từ thời điểm đó). Kết hợp với archive_command (ghi WAL segment ra archive, ví dụ S3/rsync) và restore_command (đọc WAL từ archive khi restore) cho phép PITR (Point-in-Time Recovery): phục hồi cluster về bất kỳ thời điểm recovery_target_time (hoặc LSN) sau thời điểm base backup, replay toàn bộ WAL đã archived.

Razorpay — 12/2019: failover Multi-AZ lộ durability đang tắt

Tối thứ Sáu tháng 12/2019, instance RDS MySQL chính của app "API" tự failover Multi-AZ trong ~110 giây. Traffic tự phục hồi, nhưng cả 5 replica chết replication vì lỗi duplicate-key.

Đối chiếu trace log ứng dụng với binlog, họ tìm ra innodb_flush_log_at_trx_commit đang để bằng 2: commit chỉ flush redo log mỗi 1 giây. sync_binlog đã bằng 1 nên binlog có đủ dữ liệu và replica vẫn áp dụng; khi primary bị thay thế, các giao dịch trong cửa sổ 1 giây chưa kịp xuống EBS biến mất, auto-increment chèn lại va chạm record cũ. Fix ghi trong bài là đổi "from 2 to 1".

Mất đúng "5 seconds of data". Với hệ fintech thì mỗi giao dịch mất là tiền thật. 5 replica chờ 6 tiếng cho snapshot của máy master mới xong mới dựng lại được, sau đó một cuộc họp 8 tiếng để đối soát và sửa dữ liệu thủ công.

Bài học: Với database mà commit phải sống sót qua failover, innodb_flush_log_at_trx_commit=1 và sync_binlog=1 là cấu hình bắt buộc chứ không phải chuyện performance. Failover tự động 110 giây không có ý nghĩa gì nếu cấu hình bên dưới không bảo toàn dữ liệu; drill failover định kỳ là cách duy nhất phát hiện điều này trước khách hàng.

Shopify — 2024: gap lock chồng nhau giữa các ETL upsert song song

Các ETL job upsert batch song song, mỗi process partition theo account, ghi vào bảng transactions trên MySQL/InnoDB. Insert-then-update đụng unique constraint khiến InnoDB cấp gap lock cho record cần update kèm index entry đứng trước nó.

Primary key _pkid tăng tuần tự nên bản ghi của các account khác nằm chen chúc vật lý trên disk. Gap lock của các process chồng lên nhau dù "the processes are operating on a different batch of records": deadlock xảy ra cả khi hai process không đụng record nào của nhau. Trước khi sửa, team phải gắn "artificial delays on our processes" làm mitigation tạm.

Deadlock lặp lại thường xuyên trong production ETL và "could affect the performance of the application significantly". Nguồn không nêu downtime cụ thể.

Bẫy: Lock contention phụ thuộc thứ tự vật lý của dữ liệu trên disk, nên hai job ghi hai account khác nhau vẫn deadlock được. Sửa bằng composite primary key (account, id) để InnoDB lưu theo từng account, thêm unique index riêng trên id giữ backward-compat.

Notion — 10/2021: sharding Postgres 5 năm tuổi với 480 logical shard

Monolith Postgres 5 năm tuổi của Notion trải qua 4 bậc độ lớn trước khi chạm giới hạn: VACUUM stall kéo dài chặn reclaim disk, suýt TXID wraparound (Notion coi wraparound là "existential threat" vì nó chuyển database sang chế độ chặn ghi), CPU spike giữ on-call liên tục, đổi schema tí cũng run.

Họ shard thành 480 logical shard trên 32 physical database (15 schema mỗi DB), cap 500GB mỗi bảng, 10TB mỗi DB, ≥60K IOPS; chọn 480 vì số này có nhiều ước số, cho phép mở rộng 32→40→48 host. Partition key là workspace UUID; backfill trên m5.24xlarge 96 CPU mất ~3 ngày.

Shard quá muộn nên partition key chưa populate ở DB cũ, họ điền on-the-fly để tránh thêm tải backfill. Double-write qua audit log kèm catch-up script (logical replication không theo kịp block write volume), dựng cả reverse audit log làm rollback, verify bằng sample UUID và dark reads so cả hai phía. Double-write throughput thành nút cổ chai nên cutover chấp nhận downtime 5 phút thay vì hot-swap LB; reverse log không bao giờ cần dùng.

Bài học: Shard trước khi VACUUM stall thành thói quen, đừng để partition key phải điền lén khi data đang chật. Tách người viết logic migration và người viết verify để cùng một bug không lọt qua cả hai cửa. Chọn số shard nhiều ước số thay vì power-of-2 để giữ dư địa xếp chồng capacity.

-- Xid age trước ngưỡng wraparound: Notion 2021 suýt chạm ngưỡng này
SELECT datname, age(datfrozenxid) AS xid_age,
       round(100.0 * age(datfrozenxid)
             / current_setting('autovacuum_freeze_max_age')::numeric, 1) AS pct_of_limit
FROM pg_database ORDER BY xid_age DESC;

Phỏng vấn Database: câu hỏi và trả lời

81 câu phỏng vấn database xếp theo 7 nhóm, mỗi câu trả lời theo thứ tự người phỏng vấn muốn nghe: kết luận trước, cơ chế giải thích, bẫy thường gặp, ví dụ cụ thể. Học phần này để nói được câu trả lời 45–60 giây và viết được minh chứng trên psql khi bị yêu cầu live coding.

Mẫu trả lời 4 nhịp

  1. Nhịp 1 — chốt đáp án. Một câu khẳng định: "INNER JOIN chỉ giữ hàng khớp cả hai phía, LEFT JOIN giữ toàn bộ hàng bảng trái".
  2. Nhịp 2 — chỉ cơ chế. Nói database thực thi thế nào: WHERE chạy trước khi gộp, snapshot per-statement ở Read Committed, index seek theo cột trái nhất.
  3. Nhịp 3 — nêu bẫy. Kể đúng một lỗi thật: WHERE sau LEFT JOIN vô tình biến LEFT thành INNER, NOT IN với một dòng NULL trong tập con trả 0 hàng.
  4. Nhịp 4 — ví dụ chạy được. Đưa đoạn SQL 3–5 dòng, hoặc nói thao tác kiểm chứng: chạy EXPLAIN (ANALYZE, BUFFERS) là thấy ngay Seq Scan.

Điểm phân biệt middle và senior nằm ở nhịp 3, không phải ở số lượng khái niệm liệt kê được. Câu trả lời đọc thuộc định nghĩa ACID mà không chỉ ra được một chỗ sai trong query của chính mình thường bị chốt lại ở junior. Câu nào dưới đây có phần Mở rộng thì đó là chỗ bẫy dễ vấp nhất.

Tám khái niệm bị trả lời sai nhiều nhất

  • Leftmost prefix

    Composite index (a, b, c) chỉ seek được từ cột trái nhất; cột phải chỉ filter thêm trong index. Đây là quy tắc quyết định thứ tự cột khi tạo index.

    Bẫy: index (tenant_id, status) không dùng được cho WHERE status = ? một mình, planner trả Seq Scan rồi bị hỏi "sao không dùng index?".

  • Write skew

    Hai transaction đọc cùng điều kiện, ghi hai dòng khác nhau, kết quả cuối vi phạm ràng buộc mà không có xung đột ghi-ghi trên cùng dòng. Nghiệp vụ kinh điển: hai bác sĩ cùng thấy ca trực còn đủ người rồi cùng rút lui.

    Bẫy: Snapshot Isolation lọt vì không detect xung đột; chỉ Serializable (SSI) chặn được, lỗi trả SQLSTATE 40001 và phải retry nguyên transaction.

  • Dead tuple và autovacuum

    UPDATE/DELETE trong MVCC để lại version cũ. Autovacuum trigger theo công thức threshold = 50 + 0.2 × reltuples (mặc định), thu hồi dead tuple và freeze row chống wraparound.

    Bẫy: VACUUM thường không trả space về OS trừ khi trang cuối trống hoàn toàn; bảng giảm dead tuple mà file vẫn giữ nguyên dung lượng.

  • Three-valued logic

    So sánh với NULL trả UNKNOWN, WHERE chỉ giữ TRUE. Mọi câu JOIN, IN, aggregate đều chạy trên thang TRUE / FALSE / UNKNOWN này.

    Bẫy: WHERE deleted_at != x bỏ sót mọi hàng NULL; sửa bằng IS DISTINCT FROM, hoặc viết IS NOT NULL AND ... tường minh.

  • N+1 query

    List 50 bài viết rồi vòng lặp query riêng lấy author mỗi bài: 51 round-trip, latency O(N). Sửa bằng JOIN/include một lần hoặc batch WHERE id IN rồi map trong bộ nhớ, mục tiêu 2–3 query mỗi request.

    Bẫy: Prisma include sâu nhiều tầng sinh join khổng lồ; cần thì tách query theo layer thay vì include 5 cấp.

  • SKIP LOCKED

    SELECT ... FOR UPDATE SKIP LOCKED bỏ qua dòng đang bị khóa, biến bảng thành hàng đợi việc: 100 worker mỗi em lấy một job khác nhau, không block nhau.

    Bẫy: FOR UPDATE không ghi OF khóa hết mọi bảng trong câu lệnh, kể cả bảng chỉ định đọc, giữ lock lâu hơn và tăng nguy cơ deadlock; ghi OF <bảng> thì chỉ khóa đúng bảng đó. Bẫy thật là outer join: PostgreSQL chặn khóa bảng phía nullable của LEFT JOIN với thông báo "FOR UPDATE cannot be applied to the nullable side of an outer join". Sửa bằng FOR UPDATE OF bảng phía không nullable, hoặc tách query.

  • Replication lag

    Streaming replication async mặc định, lag thường dưới 1 giây khi standby đủ mạnh. Standby chạy hot standby nhận SELECT chỉ đọc.

    Bẫy: Ghi xong trả client 200 rồi đọc ngay replica để verify: dữ liệu chưa tới, kết quả "mất". Read-your-writes cần route session về primary.

  • Retry nguyên transaction

    PostgreSQL abort transaction tranh chấp với SQLSTATE: 40001 (serialization failure), 40P01 (deadlock detected), 55P03 (NOWAIT lock conflict).

    Bẫy: Retry từng statement thay vì retry cả khối BEGIN...COMMIT: dữ liệu nửa vời giữa hai lần chạy.

Nhóm 1 — Mô hình quan hệ và khóa

  1. Câu 1 — ERD và lược đồ quan hệ (relational schema) khác nhau thế nào?

    Trả lời: ERD vẽ thực thể, thuộc tính và quan hệ ở mức nghiệp vụ, dành cho thảo luận với người không viết SQL. Lược đồ quan hệ là bản dịch sang bảng, cột, khóa, ràng buộc mà database hiểu và cưỡng chế được. Quan hệ 1-n thì FK nằm ở phía n; quan hệ n-n luôn tách thành hai bảng 1-n và một bảng mapping giữ khóa ghép ở giữa.

  2. Câu 2 — Trong bảng học sinh nên đặt mã lớp hay trong bảng lớp đặt mã học sinh? Vì sao?

    Trả lời: Đặt mã lớp (FK) trong bảng học sinh, vì một lớp có nhiều học sinh còn một học sinh chỉ thuộc một lớp. FK luôn nằm ở phía n của quan hệ 1-n. Đặt ngược lại thì mỗi lớp chỉ chứa được đúng một học sinh, mô hình sai ngay từ dữ liệu mẫu đầu tiên.

  3. Câu 3 — Vì sao phải có bảng order_item dù đã có orders và products?

    Trả lời: Vì orders và products là quan hệ nhiều-nhiều, không thể giữ FK trực tiếp mà không mất dữ liệu. Mỗi dòng order_item ghi một sản phẩm kèm số lượng và giá tại thời điểm mua. Không có bảng đó thì báo cáo doanh thu phải join lại products giá hiện tại, sai ngay khi giá bán thay đổi giữa chừng.

  4. Câu 4 — 1NF, 2NF, 3NF và BCNF là gì?

    Trả lời: 1NF: mỗi ô một giá trị nguyên tử, không cột lặp. 2NF: đã 1NF và mọi thuộc tính không khóa phụ thuộc hoàn toàn vào khóa chính, loại phụ thuộc một phần với khóa tổ hợp. 3NF: đã 2NF và không còn phụ thuộc chuyển tiếp giữa hai thuộc tính không khóa. BCNF siết hơn 3NF: với mọi functional dependency X → Y, X phải là siêu khóa; trường hợp 3NF-đúng-BCNF-sai chỉ xuất hiện khi có overlap giữa khóa ghép.

  5. Câu 5 — Chuẩn hóa đến mức nào là đủ? Có nên denormalization không?

    Trả lời: OLTP mặc định dừng ở 3NF để tránh update/insert/delete anomaly: một giá trị đúng ở một chỗ. Denormalization có chủ đích hợp lệ khi workload đọc nhiều phải trả giá join, ví dụ cột total đã tính sẵn trên orders. Trade-off phải nói ra: dữ liệu có thể lệch, nên cần chiến lược đồng bộ (trigger, job tính lại, hoặc ghi atomic trong cùng transaction).

    Mở rộng: Trả lời "tùy workload" mà không nêu được anomaly và cách giữ đồng bộ thì bị chốt là chưa hiểu chuẩn hóa. Đối chứng: báo cáo đọc hàng triệu dòng có thể pre-aggregate bảng summary, còn ghi vẫn giữ 3NF.

  6. Câu 6 — Một bảng có mấy khóa chính? Composite key là gì?

    Trả lời: Mỗi bảng đúng một PK; không có khái niệm nhiều PK, ngoài PK chỉ có thêm unique constraints. Composite key là PK gồm nhiều cột cùng định danh một dòng, ví dụ (order_id, product_id) trên order_item. PK tạo unique index và NOT NULL trên toàn bộ cột tham gia.

  7. Câu 7 — ON DELETE CASCADE, SET NULL, RESTRICT khác nhau thế nào?

    Trả lời: CASCADE xóa luôn dòng con khi xóa cha; SET NULL gỡ liên kết bằng cách set FK về NULL; RESTRICT (NO ACTION) báo lỗi và chặn xóa cha khi còn dòng con. Chọn theo nghiệp vụ, không theo mặc định ORM. Xóa customer mà orders còn FK: RESTRICT báo lỗi buộc xử lý đơn trước, CASCADE xóa luôn toàn bộ orders và order_items của khách đó.

    Mở rộng: Prisma và TypeORM có thể khai onDelete mặc định khiến một lệnh xóa user cascade xuống hàng nghìn dòng audit log. Trước khi xóa dữ liệu, hỏi lại: FK của bảng này đang cascade kiểu gì.

  8. Câu 8 — Surrogate key và natural key khác nhau, nên chọn cái nào?

    Trả lời: Surrogate (bigint identity, UUIDv7) là giá trị database cấp, tách định danh khỏi nghiệp vụ. Natural key (email, ISBN) là giá trị nghiệp vụ, dùng được chỉ khi bất biến suốt đời. Đối chứng: orders dùng số hóa đơn natural key làm PK rồi đổi quy tắc đánh số theo chi nhánh, phải UPDATE PK và 6 bảng tham chiếu; dùng surrogate thì việc đổi quy tắc chỉ ảnh hưởng một cột hiển thị.

  9. Câu 9 — UNIQUE và PRIMARY KEY khác nhau thế nào? Soft delete cần gì?

    Trả lời: Cả hai chặn trùng; PK bắt buộc NOT NULL và mỗi bảng chỉ một, còn unique thì nhiều cái được. PostgreSQL coi hai NULL là hai giá trị khác nhau trong unique, nên email NULL lặp thoải mái. Soft delete ba việc bắt buộc: mọi đọc lọc deleted_at IS NULL, unique chuyển thành partial index WHERE deleted_at IS NULL, và ON DELETE CASCADE không kích hoạt vì chỉ UPDATE cột.

    Mở rộng: Không có partial index thì user đã xóa không đăng ký lại được email, lỗi 23505 bí ẩn quay về app. Lệnh chuẩn: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL.

  10. Câu 10 — EXCLUDE constraint dùng để làm gì, khác gì UNIQUE, và khi nào cần btree_gist?

    Trả lời: Đáp án: EXCLUDE diễn đạt ràng buộc "không dòng nào thỏa operator so với dòng khác" — thường dùng với range để chặn hai khoảng chồng nhau; UNIQUE chỉ chặn giá trị trùng exact, không diễn đạt được quan hệ giữa hai khoảng. Cú pháp: EXCLUDE USING gist (cột1 WITH op1, cột2 WITH op2), operator thường gặp là = cho scalar và && cho overlap. btree_gist cần khi trộn int/text (opclass btree) cạnh range (opclass gist) trong cùng constraint, vì GiST mặc định không index được scalar. Bẫy: && là overlap, chèn khoảng lọt bên trong khoảng khác vẫn bị chặn; defer bằng DEFERRABLE INITIALLY DEFERRED nếu cần chèn nhiều dòng chồng nhau trong một transaction rồi kiểm ở COMMIT. Lỗi khi chèn overlap: conflicting key value violates exclusion constraint.

  11. Câu 11 — View PostgreSQL khi nào updatable, WITH CHECK OPTION chặn gì, và security_invoker = true đổi hành vi gì so với mặc định?

    Trả lời: Đáp án: view updatable khi đọc đúng một bảng, không có aggregate/DISTINCT/UNIQUE/GROUP BY/HAVING/window function — mọi INSERT/UPDATE đi thẳng xuống bảng base. WITH CHECK OPTION buộc dòng ghi qua view phải thỏa WHERE của chính view, thiếu nó thì chèn tenant_id=2 qua view WHERE tenant_id=1 vẫn thành công. security_invoker = true (PG15+) đổi từ definer-rights sang invoker-rights: mặc định view chạy quyền người tạo, owner bypass RLS nên người đọc thấy mọi tenant; đặt security_invoker thì RLS của người gọi được áp. Bẫy: view expose bảng multi-tenant mà quên security_invoker là lỗ hổng bypass policy. Ví dụ: cùng một query SELECT count(*) qua 2 view trên bảng RLS, definer trả 3 dòng, invoker trả 2 dòng.

  12. Câu 12 — Armstrong axioms gồm những luật nào, và dùng attribute closure để kiểm một FD hay tìm candidate key ra sao?

    Trả lời: Đáp án: ba luật gốc là reflexivity (X → X), augmentation (X → Y suy ra XZ → YZ), transitivity (X → Y và Y → Z suy ra X → Z); từ đó sinh F+ gồm cả union và decomposition. Hình bao X⁺ là mọi cột suy ra được từ X theo F; X → Y đúng trong F+ đúng khi Y ⊆ X⁺. Để tìm candidate key: tính X⁺, X⁺ bằng toàn bộ cột quan hệ thì X là superkey, còn phải minimal (bỏ một cột là X⁺ không đủ) thì mới là candidate key. Bẫy: GROUP BY/HAVING kiểm FD chỉ trên data đang có, không enforce FD cho dòng tương lai — ràng buộc phải nằm ở PK/UNIQUE/CHECK. Ví dụ F={e→d, d→s}: closure({e}) = {e,d,s} đủ cột, closure({d}) = {d,s} thiếu e nên d không phải key.

Nhóm 2 — SQL: JOIN, aggregate, NULL

  1. Câu 13 — Phân biệt INNER JOIN và LEFT JOIN, cho ví dụ.

    Trả lời: INNER JOIN chỉ giữ hàng khớp cả hai phía. LEFT JOIN giữ toàn bộ hàng bảng trái, cột bảng phải trả NULL khi không khớp. Liệt kê tất cả học sinh kèm lớp thì dùng LEFT JOIN vì học sinh chưa xếp lớp vẫn phải hiện ra; đếm "học sinh có lớp" thì INNER.

  2. Câu 14 — LEFT JOIN rồi WHERE trên cột bảng phải thì chuyện gì xảy ra?

    Trả lời: WHERE loại hàng null-pad sinh ra từ nửa ngoài, vô tình biến LEFT JOIN thành INNER. Muốn giữ hàng không khớp thì chuyển điều kiện sang ON, hoặc viết WHERE b.c IS NULL để tìm hàng trái không match. Đây là lỗi đắt nhất của nhóm JOIN vì cú pháp chạy đúng mà kết quả lặng lẽ mất hàng.

    Mở rộng: Sản phẩm thật hay mắc: báo cáo danh sách khách kèm đơn, ai đó thêm WHERE o.total > 100 "cho chắc", khách chưa từng order biến mất khỏi báo cáo.

  3. Câu 15 — GROUP BY và ORDER BY khác nhau thế nào?

    Trả lời: GROUP BY gộp hàng thành nhóm để tính tổng hợp COUNT/SUM/AVG; ORDER BY chỉ sắp xếp kết quả, không gộp. SELECT name, age ... GROUP BY name ORDER BY age thì age phải nằm GROUP BY nếu không được bọc hàm tổng hợp, PostgreSQL báo column must appear in GROUP BY.

  4. Câu 16 — Vì sao SUM/COUNT không đặt trong WHERE mà phải đặt trong HAVING?

    Trả lời: WHERE chạy trước khi GROUP BY gộp nên chưa tồn tại giá trị tổng hợp để so; HAVING chạy sau gộp nên dùng được COUNT(*) > 10, SUM(total) > 1000. Quy tắc dùng: cột thường trong WHERE, cột tổng hợp trong HAVING.

  5. Câu 17 — RIGHT JOIN khác LEFT JOIN thế nào? FULL OUTER JOIN, CROSS JOIN dùng khi nào?

    Trả lời: RIGHT JOIN là mirror của LEFT JOIN, giữ toàn bộ bảng phải; thực tế gần như luôn đảo thứ tự bảng rồi viết LEFT JOIN, kết quả y hệt và dễ đọc hơn. FULL OUTER JOIN giữ hàng cả hai phía, hợp so sánh hai nguồn như danh sách user hệ cũ và hệ mới. CROSS JOIN tạo tích Descartes, hợp ma trận tổ hợp như mỗi user times mỗi template.

  6. Câu 18 — Subquery và CTE khác nhau, khi nào dùng cái nào?

    Trả lời: CTE (WITH) đặt tên result set ở đầu câu, đọc được theo tầng và từ PostgreSQL 12 được inline vào query cha khi side-effect-free và chỉ tham chiếu một lần. Subquery correlated lặp đánh giá cho mỗi hàng ngoài. Ưu tiên CTE cho đa tầng dữ liệu đọc lại nhiều chỗ, EXISTS cho kiểm tra tồn tại.

    Mở rộng: Trước PG12 CTE luôn là optimization fence nên predicate không pushdown; từ PG12 force MATERIALIZED khi muốn giữ ranh giới, NOT MATERIALIZED khi muốn planner xuống tham.

  7. Câu 19 — EXISTS khác IN thế nào, nên dùng cái nào cho subquery lớn?

    Trả lời: EXISTS là semi-join, trả TRUE ngay khi có ít nhất một hàng khớp và thường dừng ở hàng đầu; IN (≡ = ANY) materialize tập con rồi so khớp. Với subquery lớn EXISTS thường rẻ hơn. Nguy hiểm hơn là NOT IN: tập con chứa một dòng NULL là toàn bộ biểu thức không bao giờ TRUE, trả 0 hàng; đổi sang NOT EXISTS.

    Mở rộng: Lý do ngữ nghĩa: NOT IN ≡ <> ALL, mà a <> NULL là UNKNOWN, WHERE chỉ giữ TRUE nên hàng bị loại sạch.

  8. Câu 20 — Window function dùng để làm gì? Cho ví dụ top-3 mỗi nhóm.

    Trả lời: Window function tính trên cửa sổ mà không gộp hàng, giữ nguyên từng dòng. Top-3 đơn mỗi khách: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total DESC) <= 3. SUM(amount) OVER (ORDER BY day) cho lũy kế, LAG/LEAD so dòng trước sau. Một lần quét thay cho self-join.

  9. Câu 21 — Recursive CTE dùng để làm gì?

    Trả lời: Duyệt dữ liệu phân cấp như cây category hoặc org chart mà không cần đệ quy trong application. WITH RECURSIVE có phần base case và recursive case nối bằng UNION ALL. Bắt buộc đặt giới hạn depth hoặc cờ vòng tham chiếu, vì UNION ALL không tự dừng khi dữ liệu có vòng.

  10. Câu 22 — NULL nghĩa là gì? So sánh với NULL ra sao?

    Trả lời: NULL là UNKNOWN, không phải chuỗi rỗng hay số 0. Mọi so sánh với NULL trả UNKNOWN và WHERE chỉ giữ TRUE, nên WHERE phone != '0123' bỏ mọi hàng phone IS NULL. Dùng IS NULL / IS DISTINCT FROM, và COALESCE(x, 0) khi cần giá trị thay thế có chủ đích.

    Mở rộng: COUNT(col) bỏ qua NULL còn COUNT(*) đếm cả hàng; aggregate trên 0 hàng trả NULL (trừ count trả 0) nên báo cáo cần COALESCE(sum(...), 0).

  11. Câu 23 — COUNT(*), COUNT(col) và COUNT(DISTINCT col) khác nhau thế nào?

    Trả lời: COUNT(*) đếm mọi hàng kể cả hàng toàn NULL; COUNT(col) bỏ qua NULL của cột đó; COUNT(DISTINCT col) đếm giá trị khác NULL duy nhất. Đo "bao nhiêu khách đã đặt hàng" bằng COUNT(DISTINCT customer_id) trên orders, vì một khách có nhiều đơn.

  12. Câu 24 — LEFT JOIN rồi WHERE b.c IS NULL và NOT EXISTS, viết cái nào?

    Trả lời: Cả hai là anti-join cho cùng kết quả. NOT EXISTS diễn đạt ý định "không tồn tại dòng con" nên được ưu tiên khi chỉ kiểm tra tồn tại; LEFT JOIN + IS NULL cần cột bảng trái trong SELECT nên tiện khi in danh sách kèm lý do. Planner thường convert cả hai hình thức sang anti-join.

  13. Câu 25 — OFFSET pagination và keyset pagination khác nhau thế nào?

    Trả lời: OFFSET yêu cầu planner fetch rồi drop từng đó hàng theo định nghĩa SQL, chi phí O(offset), trang sâu chậm dần. Keyset so sánh với hàng cuối trang trước qua row-value comparison WHERE (created_at, id) < (?, ?), đi thẳng vùng index tiếp theo, startup thấp và không nhảy số khi có hàng chèn giữa hai lần fetch.

    Mở rộng: Trade-off thật của keyset: không nhảy tới số trang tùy ý, nên infinite scroll hợp, paginator số trang thì không. Thiếu ORDER BY unique thì hàng lặp hoặc mất giữa các trang.

  14. Câu 26 — percentile_cont và percentile_disc khác nhau thế nào? WITHIN GROUP bắt buộc không?

    Trả lời: percentile_cont nội suy (0.5 trên 1,2,3,4 = 2.5); percentile_disc chọn hàng thật (0.5 = 2). mode() trả giá trị lặp nhiều nhất; trên data không có lặp trả một giá trị bất kỳ. WITHIN GROUP (ORDER BY …) là bắt buộc — thiếu nó thì percentile_cont(0.5) báo function does not exist. Aggregate trên 0 hàng nhóm trả NULL.

    Bẫy: quên WITHIN GROUP khi cần dùng; hoặc không rõ nghiệp vụ muốn nội suy hay giá trị có thật rồi chọn hàm sai.

  15. Câu 27 — Toán tử jsonb nào dùng để extract, nào để containment? Khác json ở điểm nào?

    Trả lời: -> trả jsonb, ->> trả text, #> / #>> theo path. @> là containment (object và array), ? existence key. jsonb parse một lần, bỏ duplicate key, chuẩn hóa thứ tự object key — '{"x":1,"y":2}' = '{"y":2,"x":1}'. GIN index dùng được cho @>. Jsonpath (jsonb_path_query) filter mạnh hơn nhưng không GIN-index thẳng.

    So sánh json (text) là so sánh chuỗi, khác jsonb; luôn khai báo cột jsonb.

  16. Câu 28 — DISTINCT ON hoạt động thế nào và bẫy thường gặp là gì?

    Trả lời: DISTINCT ON (expr) giữ một hàng mỗi nhóm expr; hàng được giữ do ORDER BY quyết định — các biểu thức đầu tiên trong ORDER BY phải trùng đúng danh sách expr của DISTINCT ON, rồi mới tới cột phân định thứ tự. Bỏ ORDER BY đúng hoặc để sai cột thì kết quả "mới nhất" thành "lớn nhất" hoặc hàng tùy planner, vẫn hợp lệ cú pháp. Portable hơn: ROW_NUMBER() OVER (PARTITION BY …) rồi lọc rn = 1 ở query ngoài.

    DISTINCT ON là extension PostgreSQL, không phải SQL chuẩn.

  17. Câu 29 — Collation ảnh hưởng gì đến so sánh chuỗi và index? citext dùng để làm gì?

    Trả lời: Collation quyết định thứ tự sort, equality và index opclass. Hai collation khác nhau so sánh → 42P21 collation mismatch. Index B-tree theo default không dùng được cho lookup COLLATE "C" (cần expression index hoặc text_pattern_ops). Citext (contrib) làm equality/DISTINCT/unique case-insensitive — đăng ký email không cần LOWER() index, nhưng không thay full-text search collation-aware.

    'a' < 'B' là true theo en_US, false theo C. Unique index citext chặn 'A@x' và 'a@x' chung hàng.

  18. Câu 30 — CAST assignment khác explicit thế nào? 22P02 là lỗi gì?

    Trả lời: Explicit cast (::int) và assignment cast (INSERT/UPDATE vào cột) là hai ngữ cảnh khác nhau, phân loại bởi pg_cast.castcontext (e/a/i). float8→int4: cả hai ngữ cảnh đều round half-to-even (banker's rounding) — 4.5::float8::int = 4, INSERT 2.5::float8 thành 2, 3.5 thành 4, 4.9 thành 5; không có nhánh trunc. Input không parse được → invalid_text_representation / 22P02. Trong transaction, sau khi statement fail mọi lệnh tiếp theo trả 25P02 cho tới ROLLBACK.

    Bẫy: giả sử assignment cast trunc hoặc round away from zero đều sai với float8 — kết quả là round-half-to-even; 4.5 ra 4 chứ không ra 5. Lỗi 22P02 chỉ xảy ra khi chuỗi không parse được (ví dụ 'abc'::int), không xảy ra khi làm tròn số hợp lệ.

  19. Câu 31 — timestamp và timestamptz khác nhau thế nào? Khi nào chọn loại nào?

    Trả lời: timestamp giữ wall-clock không zone; timestamptz lưu instant UTC, hiển thị theo TimeZone session. So sánh timestamptz là so sánh instant. ::date / date_trunc trên timestamptz cắt theo session TZ — 20:00 UTC là ngày hôm sau ở Asia/Ho_Chi_Minh. Chọn timestamptz cho mọi cột thời điểm nghiệp vụ; timestamp chỉ khi wall-clock cố định không zone.

    Bẫy: để driver lấy local timezone của container rồi so sánh ::date — cùng instant ra hai ngày khác nhau tùy máy. Set TimeZone connection về UTC, đổi zone ở tầng hiển thị.

Nhóm 3 — Index và EXPLAIN

  1. Câu 32 — Index là gì, vì sao query chạy nhanh hơn?

    Trả lời: Index mặc định là B-tree, cấu trúc phụ giữ thứ tự theo khóa, tìm hàng gần O(log n) thay vì quét toàn bảng O(n). Bù lại INSERT/UPDATE/DELETE chậm hơn vì phải cập nhật mọi index liên quan và tốn dung lượng đĩa. CREATE INDEX không chỉ định gì thì PostgreSQL tạo B-tree.

  2. Câu 33 — Nhược điểm của index là gì? Insert có chậm không?

    Trả lời: Ghi chậm hơn theo số index phải update, tốn RAM và đĩa, và plan sai có thể chọn index kém hơn seq scan. Tham khảo thực tế: giữ khoảng 5–10 index mỗi bảng. Dọn index chết bằng pg_stat_user_indexes: idx_scan = 0 sau vài tuần lưu lượng thật thì xóa.

  3. Câu 34 — Đánh index riêng từng cột khác index composite thế nào?

    Trả lời: Index (a) cộng (b) là hai mục lục riêng; index (a,b) một cây, seek hiệu quả khi a bị ràng buộc equality. Query WHERE a = ? AND b = ? thường dùng composite. Planner cũng có thể BitmapAnd hai index đơn nếu thiếu composite, nhưng tốn thêm bước gộp kết quả.

    Mở rộng: Composite quá 3 cột hầu như vô ích (docs: unlikely to be helpful sau ba cột, hard limit 32 cột kể cả INCLUDE).

  4. Câu 35 — Quy tắc leftmost prefix của composite index là gì?

    Trả lời: Cột trái nhất quyết định phần index được seek; cột phải chỉ filter thêm, không thu hẹp vùng seek. Index (tenant_id, status) không dùng được cho WHERE status = ? một mình; theo docs, query không ràng buộc cột trái nhất thì trong hầu hết trường hợp planner chọn sequential scan. Sửa: đổi thứ tự cột theo thứ tự filter equality, hoặc thêm index bắt đầu bằng cột hay bị lọc.

    Mở rộng: Đối chứng cụ thể: index (status, created_at) phục vụ WHERE status = 'pending' và WHERE status = 'pending' AND created_at < now() - interval '1 day', không dùng cho WHERE created_at < ... một mình.

  5. Câu 36 — Partial index và expression index khác gì, dùng khi nào?

    Trả lời: Partial index có WHERE riêng, ví dụ WHERE status = 'active', nhỏ hơn nhiều nhưng query phải mang WHERE khớp đúng. Expression index tạo trên hàm, ví dụ ON users (LOWER(email)), query phải dùng đúng LOWER(email) = .... Cả hai giảm kích thước index và tăng tốc đúng workload.

  6. Câu 37 — GIN, GiST, BRIN, Hash index dùng cho việc gì?

    Trả lời: Hash chỉ cho equality. GIN cho array/JSONB và full-text search. GiST cho geometric, range, nearest-neighbor. BRIN tóm tắt theo block range, rất nhỏ, hợp dữ liệu append-only tương quan vật lý như created_at của log. B-tree là mặc định, hợp equality, range và ORDER BY.

  7. Câu 38 — LIKE %keyword% có dùng index không?

    Trả lời: Không, với B-tree: pattern không neo đầu chuỗi nên không so sánh được theo thứ tự. LIKE 'abc%' thì dùng được B-tree (với opclass text_pattern_ops khi collation không phải C). Dấu % ở đầu cần GIN full-text search hoặc pg_trgm với GiST/GIN.

    Mở rộng: pg_trgm tra cứu "chứa chuỗi" xấp xỉ; ngưỡng false positive khoảng 1% (khoảng 10 bit mỗi phần tử) là vùng cấu hình thực tế của các filter tương tự.

  8. Câu 39 — Vì sao WHERE LOWER(email) = ... không dùng index email?

    Trả lời: Index trên cột email không khớp hàm LOWER nên planner không dùng được: giá trị trong index là 'Alice@...' còn predicate so 'alice@...'. Sửa hai cách: tạo expression index ON users (LOWER(email)) rồi viết query y hệt LOWER(email) = ..., hoặc lưu cột email_lower lúc ghi và index cột đó.

  9. Câu 40 — EXPLAIN và EXPLAIN ANALYZE khác nhau?

    Trả lời: EXPLAIN chỉ in plan ước tính: cost và estimated rows, hai con số để so với thực tế. EXPLAIN ANALYZE thực thi query rồi in actual time, rows, loops. Cost là unit tùy ý với seq_page_cost = 1.0 và cpu_tuple_cost = 0.01; ví dụ trong docs: Seq Scan trên tenk1 có cost 458.00 = 358 trang × 1.0 + 10000 hàng × 0.01. Chênh lệch estimated và actual lớn là dấu hiệu statistics sai.

    Mở rộng: Bộ đọc plan bắt buộc là EXPLAIN (ANALYZE, BUFFERS): thêm khối shared read/hit để biết query chạm disk bao nhiêu trang.

  10. Câu 41 — EXPLAIN ANALYZE có an toàn trên production không?

    Trả lời: Không, vì nó thực thi query thật: side-effects của INSERT/UPDATE/DELETE xảy ra dù kết quả bị discard chỉ để in plan. Docs khuyến nghị bọc BEGIN rồi EXPLAIN ANALYZE rồi ROLLBACK cho câu lệnh ghi. SELECT lớn thì không mất dữ liệu nhưng vẫn tốn thời gian và IO chạy thật.

  11. Câu 42 — Đọc plan: các loại scan và join method chọn khi nào?

    Trả lời: Seq Scan quét toàn bảng, hợp table nhỏ hoặc selectivity kém. Index Scan đi index rồi lấy heap, hợp 1 hàng hoặc range nhỏ. Index Only Scan chỉ đọc index khi mọi cột cần có trong index và hàng đã visible trong visibility map. Bitmap Index Scan gộp nhiều index rồi fetch theo batch, hợp selectivity trung bình. Join: Nested Loop hợp outer nhỏ và inner probe bằng index; Hash Join xây hash từ bảng nhỏ, hợp equality hai bảng lớn; Merge Join hợp hai đầu vào đã sort theo join key.

  12. Câu 43 — Runtime partition pruning khác plan-time pruning như thế nào? Cho ví dụ khi nào planner không thể prune tại plan-time.

    Trả lời: Plan-time pruning loại bỏ partition ngay lúc lập plan (biết giá trị hằng/pseudoconstant) → plan chỉ chứa partition cần thiết. Runtime partition pruning xảy ra lúc thực thi khi giá trị điều kiện chưa biết tại lập plan (subquery/INITPLAN, expression, parameter) → tất cả partition vẫn có trong Append, nhưng một số child bị bỏ qua lúc chạy (never executed trong EXPLAIN ANALYZE; trường Subplans Removed trong JSON chỉ đếm subplan bị loại ở plan-time).

    Cơ chế: Planner dựa trên partition bounds để quyết định partition nào có khả năng chứa tuple. Nếu biểu thức WHERE có thể được fold thành hằng số tại plan-time, pruning diễn ra trước execution. Nếu biểu thức là scalar subquery/INITPLAN (ts >= (SELECT '2024-02-01'::timestamptz)), giá trị chỉ xác định lúc execution → runtime pruning được dùng; PostgreSQL vẫn lập kế hoạch cho mọi partition hợp lệ về bounds nhưng sẽ không thực thi partition ngoài khoảng.

    Bẫy: Dùng subquery làm biên khoảng có thể vô tình chuyển plan-time → runtime. enable_partitionwise_join/aggregate mặc định off, chỉ bật khi join key chứa trọn partition key và sets khớp 1-1. Pruning chỉ dựa trên bounds, index trên partition key phục vụ selectivity trong partition.

    Ví dụ: WHERE ts >= '2024-02-01' AND ts < '2024-02-15' (hằng số) → chỉ events_rt_2024_02 xuất hiện trong plan (plan-time). WHERE ts >= (SELECT '2024-02-01'::timestamptz) AND ts < (SELECT '2024-02-15'::timestamptz) → Append có 4 child, ANALYZE cho thấy 3 child never executed (2024_01, 2024_03, 2024_04; chỉ 2024_02 chạy) — runtime pruning. Trường Subplans Removed trong JSON bằng 0 vì nó đếm subplan bị loại ở plan-time, không phải child bỏ qua lúc runtime.

  13. Câu 44 — Khi nào PostgreSQL chọn GroupAggregate thay vì HashAggregate, và dấu hiệu spill (Batches/Disk Usage) cho thấy gì về work_mem?

    Trả lời: PostgreSQL ưu tiên HashAggregate khi input không cần sort theo key nhóm; chọn GroupAggregate khi input đã được sort theo Group Key (hoặc planner thấy thứ tự sẵn có) — thường kèm Sort/Incremental Sort. Spill xảy ra khi hash table vượt work_mem: Batches > 1 và có Disk Usage (hash table được chia ra nhiều batch, một phần ghi đĩa).

    Cơ chế: HashAggregate build hash table các nhóm trong work_mem (mỗi operation). Nếu không đủ chứa toàn bộ nhóm, PostgreSQL chia thành batches: batch đầu giữ trong RAM, các batch còn lại ghi temp file; khi probe đọc lại từng batch. GroupAggregate đi theo stream đã sort, không cần giữ toàn bộ nhóm trong RAM → ít phụ thuộc work_mem hơn cho việc nhóm.

    Bẫy: work_mem là per operation, per session → tăng toàn cục ẩu có thể gây OOM khi nhiều connection cùng chạy sort/hash. enable_hashagg=off chỉ ép so sánh, không phải cách sửa gốc. enable_seqscan=off không ép chọn HashAggregate.

    Ví dụ: Với work_mem='64kB' và nhóm nhiều (id % 49999, 49999 nhóm), HashAggregate có Batches: 85 kèm Disk Usage: 7112kB — dấu hiệu hash table đã tràn nhiều batch ra đĩa (cần tăng work_mem hoặc filter nhóm trước khi GROUP BY).

  14. Câu 45 — Khi đọc một plan tree, làm thế nào để phân biệt root→leaf và ý nghĩa khác nhau giữa startup cost và total cost?

    Trả lời: Plan là cây: node con cung cấp tuple cho node cha. Đọc cấu trúc từ leaf → root để thấy dữ liệu đi qua node nào, còn đọc chi phí từ root → leaf; startup cost là chi phí để trả hàng đầu tiên, total cost là chi phí để trả toàn bộ hàng.

    Cơ chế: Mỗi node có hai giá trị cost: startup cost (thời điểm node bắt đầu xuất tuple đầu tiên) và total cost (ước tính để xuất hết tuple). Node như Sort phải hoàn tất sort trước khi trả dòng đầu → startup cost cao. Node quét tuần tự/index có thể trả ngay → startup cost thấp. loops nhân lên: actual time/rows là trung bình mỗi loop, cần nhân với loops để ra tổng.

    Bẫy: So sánh cost với milliseconds là sai (đơn vị ước tính). Cost chỉ dùng để so sánh plan cùng query. Không bỏ qua loops khi tính tổng thời gian từ actual.

    Ví dụ: Sort (cost=23818.64..24318.64 rows=200000 width=8) có startup ~23818, total ~24318 (startup rất cao) — phải sort toàn bộ trước khi trả dòng đầu; trái lại Bitmap Index Scan có startup thấp, trả tuple sớm.

-- Mẫu trình bày EXPLAIN trước mặt phỏng vấn viên
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, count(*)
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.status = 'active'
GROUP BY c.id, c.name;

-- Câu lệnh ghi: luôn bọc transaction để rollback được
BEGIN;
EXPLAIN ANALYZE UPDATE orders SET status = 'paid' WHERE id = 1;
ROLLBACK;

Nhóm 4 — Transaction, ACID và isolation

  1. Câu 46 — Transaction là gì, ACID gồm những gì?

    Trả lời: Transaction gộp nhiều lệnh thành một đơn vị nguyên tử: BEGIN rồi thao tác rồi COMMIT hoặc ROLLBACK. Atomicity ghi hết hoặc bỏ hết. Consistency giữ ràng buộc và trigger. Isolation theo mức cô lập đã chọn. Durability nhờ WAL: commit đã durable sống qua crash. Thuật ngữ do Härder và Reuter đặt năm 1983.

  2. Câu 47 — Trong Prisma + NestJS dùng transaction thế nào?

    Trả lời: prisma.$transaction(async (tx) => { ... }) cho callback-style, hoặc $transaction([op1, op2]) cho chuỗi thao tác đơn giản. Giữ transaction ngắn, không gọi API network bên trong, map lỗi Prisma P2002 sang 409 và P2025 sang 404 ở tầng exception filter. Callback trả về giá trị nên service nhận tx thay vì client toàn cục.

  3. Câu 48 — Dirty read là gì? PostgreSQL có cho phép không?

    Trả lời: Dirty read là đọc dữ liệu chưa commit của transaction khác; nếu bên đó rollback thì bạn giữ giá trị chưa bao giờ tồn tại trong DB. Ở mức READ UNCOMMITTED, PostgreSQL behaves like READ COMMITTED nên không có dirty read thật, chỉ có ba mức cô lập thực sự được implement.

  4. Câu 49 — Nonrepeatable read và phantom read khác nhau thế nào?

    Trả lời: Nonrepeatable read: đọc lại một hàng rồi thấy giá trị đã đổi vì transaction khác commit UPDATE. Phantom read: chạy lại cùng WHERE rồi thấy tập hàng đổi vì transaction khác INSERT. Cả hai đều bị chặn ở Repeatable Read của PostgreSQL, vì PG implement mức đó bằng Snapshot Isolation.

  5. Câu 50 — PostgreSQL default isolation level là gì?

    Trả lời: READ COMMITTED. Mỗi SELECT thấy snapshot tại thời điểm bắt đầu câu lệnh đó, nên hai SELECT liên tiếp trong cùng transaction có thể thấy dữ liệu khác nhau nếu có commit giữa chừng. Đổi mức bằng SET TRANSACTION ISOLATION LEVEL ... hoặc ALTER DATABASE x SET default_transaction_isolation.

  6. Câu 51 — Repeatable Read trong PostgreSQL khác textbook thế nào?

    Trả lời: PG implement bằng Snapshot Isolation: snapshot lấy tại statement đầu tiên và PG cũng chặn phantom read, được phép vì SQL standard chỉ qui định anomaly tối thiểu phải chặn. Khi transaction khác commit bản ghi bạn đã đọc hoặc sửa, PG abort với could not serialize access due to concurrent update, client phải retry toàn transaction.

  7. Câu 52 — Write skew là gì, vì sao Snapshot Isolation không chặn?

    Trả lời: Hai transaction đọc điều kiện rồi ghi hai hàng khác nhau, kết quả cuối vi phạm ràng buộc mà không có write-write conflict trên cùng hàng. Ca trực: hai bác sĩ cùng thấy vẫn đủ người rồi cùng rút lui, ca trực còn 0 người. SI chỉ detect xung đột ghi trên hàng đã đọc bị ghi đè nên lọt anomaly này; khái niệm do Berenson và cộng sự nêu năm 1995.

  8. Câu 53 — PostgreSQL chặn write skew bằng cách nào?

    Trả lời: SERIALIZABLE dùng Serializable Snapshot Isolation (SSI) với predicate lock SIReadLock, theo dõi rw-dependency mà không blocking và không gây deadlock, abort khi có chu kỳ nguy hiểm. Lỗi trả SQLSTATE 40001 nên application must be prepared to retry nguyên transaction. Workload tranh chấp cao thì abort nhiều, cân nhắc READ ONLY cho transaction chỉ đọc.

  9. Câu 54 — 2PL và MVCC khác nhau cơ bản thế nào?

    Trả lời: 2PL là pessimistic: giữ lock tới commit để đảm bảo serializability, chặn mạnh và dễ deadlock. MVCC đọc không lock, writer tạo version mới, reader thấy snapshot; theo docs PG đọc không bao giờ chặn ghi và ghi không bao giờ chặn đọc. PostgreSQL dùng MVCC cộng optional SELECT FOR UPDATE, còn SSI là MVCC cộng dependency tracking.

  10. Câu 55 — Lỗi 25P02 (in_failed_sql_transaction) xuất hiện khi nào và recover ra sao?

    Trả lời: 25P02 nổ khi chạy tiếp câu lệnh sau khi một statement trong cùng transaction đã fail; thông báo là "current transaction is aborted, commands ignored until end of transaction block". Recover bằng ROLLBACK cả transaction, hoặc SAVEPOINT trước điểm mạo hiểm rồi ROLLBACK TO SAVEPOINT để clear aborted flag và chạy tiếp phần sau. Bẫy Prisma: interactive $transaction bắt exception và rollback nguyên khối; catch lỗi rồi $executeRaw tiếp trong callback sẽ dính 25P02 (hoặc client ném P2028 'Transaction already closed: …') —hoặc ném lại exception, hoặc SAVEPOINT + retry từng phần. COMMIT trên transaction aborted bị thực thi thành ROLLBACK, không phải lối thoát.

    SQLSTATE class 25 = Invalid Transaction State; 25P02 condition name = in_failed_sql_transaction.

  11. Câu 56 — Read skew (A5A) khác write skew (A5B) thế nào trên PostgreSQL?

    Trả lời: A5A là T1 đọc x, T2 ghi x và y rồi commit, T1 đọc y và gộp hai snapshot thành kết quả sai — dưới RC PostgreSQL cho phép vì mỗi statement lấy snapshot mới; RR/SER chặn vì đóng băng snapshot từ statement đầu. A5B là hai transaction đọc row rời nhau rồi ghi row của nhau, RR vẫn cho phép, chỉ SERIALIZABLE chặn. Cơ chế khác nhau: A5A không cần write-write conflict (T2 đã xong trước khi T1 đọc phần sau), A5B cần hai write song song trên hai row. Bẫy: nghĩ RR chặn hết skew: RR chặn A5A nhưng vẫn lọt A5B. Ví dụ bank transfer dưới RC: đọc A=100 trước khi T2 commit, đọc B=110 sau, gộp ra 210 dù tổng đúng là 200.

    Bảng phenomenon trong section transaction-concurrency liệt kê cả sáu: P1–P4, A5A, A5B.

Nhóm 5 — MVCC, WAL, VACUUM

  1. Câu 57 — MVCC là gì, lợi ích chính?

    Trả lời: Multiversion Concurrency Control: mỗi transaction thấy snapshot của mình, UPDATE tạo version mới thay vì ghi đè tại chỗ. Docs chốt: reading never blocks writing and writing never blocks reading. Đổi lại tốn storage và cần VACUUM dọn version cũ (dead tuple).

    Mở rộng: Nói được nhận xét sau là điểm cộng senior: PG giữ guarantee không chặn này kể cả ở Serializable nhờ SSI, thay vì hạ về locking như một số hệ khác.

  2. Câu 58 — WAL (Write-Ahead Logging) hoạt động thế nào?

    Trả lời: Mọi thay đổi ghi vào log durable trước khi chạm data page. Crash thì replay WAL: redo transaction đã commit, undo phần chưa commit. Checkpoint định kỳ flush buffer pool xuống đĩa để recovery chỉ replay từ checkpoint gần nhất. Nền tảng lý thuyết là ARIES (Mohan và cộng sự, 1992) đã chuẩn hóa giao thức này.

  3. Câu 59 — VACUUM làm gì, vì sao bắt buộc ở PostgreSQL?

    Trả lời: UPDATE/DELETE không xóa ngay vì còn transaction có thể thấy version cũ. VACUUM thu hồi dead tuple, cập nhật visibility map để bật Index Only Scan, cập nhật statistics, và freeze row cũ chống xid wraparound. Không vacuum thì bloat, quét chậm dần, cuối cùng là wraparound emergency.

    Mở rộng: VACUUM FULL rewrite toàn bộ table, cần ACCESS EXCLUSIVE lock; docs khuyên administrators should strive to use standard VACUUM and avoid VACUUM FULL. Production thường thay bằng pg_repack.

  4. Câu 60 — Autovacuum quyết định vacuum bảng khi nào?

    Trả lời: Threshold = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples; mặc định 50 + 0.2 × số dòng. Analyze trigger: 50 + 0.1 × reltuples. Bảng ghi liên tục nên override per-table: ALTER TABLE t SET (autovacuum_vacuum_scale_factor = 0.02). Autovacuum cần track_counts = on mới thấy số liệu hoạt động.

    Mở rộng: Số mặc định 50/0.2 lấy từ skill docs cục bộ, còn trang routine-vacuuming của PostgreSQL nêu công thức và tên GUC; khi phỏng vấn nên nói cả công thức lẫn cách override.

  5. Câu 61 — Xid wraparound là gì, nguy hiểm thế nào?

    Trả lời: Transaction ID là 32-bit, sau hơn 4 tỷ transaction sẽ wraparound làm transaction quá khứ trở thành tương lai: dữ liệu invisible, mất dữ liệu. PG freeze row cũ để chúng visible cho mọi transaction. Cần vacuum mọi bảng ít nhất một lần mỗi 2 tỷ transaction; autovacuum_freeze_max_age mặc định 200 triệu sẽ force vacuum kể cả khi autovacuum bị tắt. Monitor bằng SELECT age(relfrozenxid) FROM pg_class.

    Mở rộng: Lưu ý đắt: VACUUM FULL không dùng được trong emergency wraparound vì bản thân nó cần XID mới; lối thoát là vacuum thường hoặc single-user mode.

  6. Câu 62 — Transaction idle-in-transaction gây hại gì?

    Trả lời: Session đã BEGIN nhưng không chạy lệnh vẫn giữ snapshot xmin horizon, chặn autovacuum cắt version cũ; nó cũng giữ row lock và có thể chặn DDL trên bảng liên quan. Xử lý: đặt idle_in_transaction_session_timeout, không gọi network bên trong transaction, alert khi pg_stat_activity state là idle in transaction.

    Mở rộng: Đối chứng hình dung: bảng logic 2GB nhưng file 40GB, n_dead_tup hàng triệu; nguyên nhân thường gặp là một connection pool giữ transaction mở. Xem thêm nhóm 7 câu connection pool.

  7. Câu 63 — Hint bits là gì và tại sao PostgreSQL dùng chúng?

    Trả lời: Hint bits là bit trong t_infomask của tuple header ghi nhanh trạng thái commit/abort của xmin/xmax, tránh phải đọc clog (pg_xact) mỗi lần visibility check.

    Khi transaction commit/abort, PostgreSQL không sửa mọi tuple ngay; lần đầu tuple được đọc, hệ thống set hint bit (HEAP_XMIN_COMMITTED/INVALID, HEAP_XMAX_COMMITTED/INVALID) lên tuple đó (lazy). VACUUM/FREEZE cũng set hint bits (kể cả xmin_frozen). Nhờ vậy visibility check rút ngắn đáng kể, giảm I/O.

    Bẫy: Hint bit không được set ngay lúc commit — chỉ lazy hoặc bởi VACUUM, nên đọc lần đầu sau commit có thể vẫn phải tra clog một lần trước khi set hint. Dùng bitwise AND để decode t_infomask chính xác.

    Ví dụ: Sau INSERT, infomask có thể là 2050 (chưa set xmin_committed rõ ràng), sau khi SELECT 1 row đọc tuple đó, infomask đổi thành 2306 (xmin_committed được set) — quan sát thực tế qua pageinspect.heap_page_items().

  8. Câu 64 — pg_dump khác pg_basebackup và PITR khác nhau thế nào?

    Trả lời: pg_dump là logical backup (SQL-level), không hỗ trợ PITR; pg_basebackup là physical backup (block-level), kết hợp với WAL archive mới cho phép PITR.

    pg_dump tạo snapshot tại thời điểm chạy và xuất schema+data; pg_basebackup copy toàn bộ data directory ở trạng thái consistent kèm backup_label, sau đó replay archive WAL qua restore_command để phục hồi tới thời điểm bất kỳ (PITR). Streaming replication chỉ là sao chép liên tục, không thay thế backup offline.

    Bẫy: Chỉ dựa vào streaming replication khi primary bị xoá toàn bộ (GitLab 2017) là sai — replication không lưu WAL archive độc lập ngoài cluster. archive_mode phải bật và archive_command phải thành công.

    Ví dụ: pg_dump dùng để migrate 1 bảng giữa major version khác; pg_basebackup + restore_command dùng để phục hồi production về 08:00:05 hôm qua sau khi phát hiện ghi nhầm lúc 08:10.

Nhóm 6 — Lock và deadlock

  1. Câu 65 — Row lock và table lock khác nhau thế nào?

    Trả lời: Row lock qua SELECT FOR UPDATE chỉ chặn dòng liên quan nên đồng thời cao nhưng dễ deadlock nếu hai transaction khóa hai dòng theo thứ tự khác nhau. Table lock đơn giản hơn nhưng chặn mọi truy vấn khác trên bảng; ACCESS EXCLUSIVE thì chặn cả DDL.

  2. Câu 66 — Deadlock là gì, PostgreSQL xử lý ra sao?

    Trả lời: A giữ lock dòng 1 và chờ dòng 2, B giữ dòng 2 và chờ dòng 1: vòng chờ. PG detect bằng wait-for graph rồi abort một transaction với SQLSTATE 40P01 (deadlock detected), application retry. Phòng tránh: khóa theo cùng thứ tự, giữ lock ngắn, retry có backoff.

  3. Câu 67 — FOR UPDATE SKIP LOCKED và NOWAIT dùng khi nào?

    Trả lời: SKIP LOCKED bỏ qua dòng đang bị khóa, nên 100 worker làm hàng đợi việc không block nhau: SELECT * FROM jobs WHERE status = 'pending' FOR UPDATE SKIP LOCKED LIMIT 1. NOWAIT fail ngay với 55P03 thay vì chờ. Với join nhiều bảng, FOR UPDATE không OF khóa hết các bảng tham gia; thêm OF <bảng> để giới hạn khóa đúng bảng cần sửa. Khóa không đặt được lên phía nullable của outer join, nên phải trỏ OF vào bảng phía không nullable.

    Mở rộng: Đây là câu hỏi vận dụng hay: biến PostgreSQL thành work queue mà không cần broker ngoài, đánh đổi là không có dead-letter queue có sẵn.

  4. Câu 68 — Optimistic locking khác pessimistic thế nào?

    Trả lời: Pessimistic qua SELECT FOR UPDATE khóa trước khi sửa, an toàn nhưng blocking. Optimistic đọc version rồi UPDATE ... WHERE version = ?, 0 rows affected nghĩa là conflict và retry. Hợp khi conflict hiếm; ORM như Prisma qua cột version hoặc @Version, JPA/Hibernate qua @Version field.

  5. Câu 69 — UPSERT trong PostgreSQL viết thế nào?

    Trả lời: INSERT ... ON CONFLICT (email) DO UPDATE SET ... hoặc DO NOTHING, cần unique index trên cột nhận diện; có từ PostgreSQL 9.5 (2016). Atomic, tránh race check-then-insert của application. RETURNING id, (xmax = 0) AS was_inserted để biết nhánh nào đã chạy. Từ PG15 có thêm MERGE cho nhiều WHEN, nhưng không có RETURNING.

Nhóm 7 — Replication, scaling và vận hành ORM

  1. Câu 70 — Streaming replication cấu hình chính gồm những gì?

    Trả lời: Primary: wal_level = replica, max_wal_senders đủ, wal_keep_size hoặc replication slot, pg_hba cho database = replication. Standby: base backup (pg_basebackup) cộng file standby.signal cộng tham số primary_conninfo. Async là mặc định với lag thường dưới 1 giây khi standby đủ mạnh; sync qua synchronous_standby_names, latency tối thiểu bằng RTT.

    Mở rộng: Failover async có window mất dữ liệu đúng bằng lag tại thời điểm primary chết; muốn không mất thì synchronous_commit = on với standby đồng bộ, đổi lại mỗi commit chậm hơn RTT.

  2. Câu 71 — Replication lag ảnh hưởng gì đến ứng dụng?

    Trả lời: Đọc replica có thể thấy dữ liệu cũ sau khi đã commit trên primary, tức stale read. Read-your-writes cần route session về primary hoặc đợi replica catch-up. Không dùng replica để verify ngay kết quả ghi vừa trả client 200. Kiểm tra lag qua pg_stat_replication (pg_wal_lsn_diff).

    Mở rộng: Pattern cấu hình: ghi + đọc immediately → primary; đọc báo cáo, dashboard → replica; có bảng cache session sticky thì ghi qua primary, đọc replica sau khi invalidate.

  3. Câu 72 — Logical replication khác physical thế nào?

    Trả lời: Physical ship WAL nhị phân, replica giống hệt primary và phải cùng major version. Logical decode WAL thành row change qua publication/subscription, chọn bảng được, major version khác nhau được, hợp nâng cấp PG hoặc CDC ra hệ khác. DDL không replicate. Lưu ý vận hành: replication slot bỏ quên thì WAL tích đầy đĩa, apply mặc định single-threaded.

    Mở rộng: Kịch bản nâng cấp: PG 13 sang 16 với downtime vài phút bằng logical replication cho 5 bảng quan trọng, thay vì physical replica yêu cầu cùng major version.

  4. Câu 73 — Sharding và partitioning khác nhau thế nào?

    Trả lời: Partitioning chia một logical table thành partition trên cùng instance theo range hoặc hash: thu hẹp scan và maintenance (ATTACH/DETACH partition nhanh hơn DELETE). Sharding chia data sang nhiều instance, mỗi shard là một DB riêng: thêm node là thêm shard, JOIN cross-shard khó, hot shard là rủi ro. Consistent hashing giảm remap khi thêm bớt node.

    Mở rộng: Thứ tự thường gặp khi scale: index → read replica → partitioning → sharding. Sharding là quyết định kiến trúc, không phải tối ưu query lẻ.

  5. Câu 74 — PITR (point-in-time recovery) làm thế nào?

    Trả lời: Backup full hoặc incremental định kỳ cộng archive WAL liên tục, khôi phục bằng restore backup rồi replay WAL tới LSN hoặc mốc thời gian cần (recovery_target). RPO xuống mức phút thay vì 24h với dump nightly. Backup chống mất dữ liệu (kể cả ghi sai có chủ đích); replication chống downtime, async replication không thay backup vì primary chết vẫn mất transaction chưa ship.

    Mở rộng: Chưa restore thử thì chưa tính là có backup; drill định kỳ restore xuống staging là hạng mục kiểm chứng duy nhất.

  6. Câu 75 — N+1 query là gì, nhận diện bằng mắt thường?

    Trả lời: List 50 bài viết rồi trong vòng lặp query riêng lấy author mỗi bài: 51 round-trip, QPS vào DB phình gấp ~50 lần và latency O(N). Dấu hiệu: ORM lazy loading trong loop. Đo bằng pg_stat_statements (xem query lặp với parameters khác nhau) hoặc log slow query.

  7. Câu 76 — Sửa N+1 trong Prisma ORM cụ thể thế nào?

    Trả lời: Gộp bằng findMany({ include: { author: true } }): mặc định Prisma phát hai query, một lấy bảng cha và một lấy bảng relation, rồi gộp ở tầng application. Muốn gộp thành một câu JOIN SQL thì bật preview relationJoins trong schema — lúc đó relationLoadStrategy mặc định đã là join, muốn giữ multi-query thì đặt relationLoadStrategy: "query". Trên PostgreSQL strategy JOIN chạy LATERAL JOIN cộng JSON aggregation. Hoặc collect ids rồi findMany({ where: { id: { in: ids } } }) rồi map trong bộ nhớ. Mục tiêu 2–3 query mỗi request thay vì N+1. Include quá sâu sinh join khổng lồ nên tách query theo layer khi quan hệ 4–5 cấp.

  8. Câu 77 — Connection pool sizing thế nào cho NestJS và PostgreSQL?

    Trả lời: Tổng pool × số instances không vượt max_connections của PG (mặc định 100), vượt thì báo too many connections. Công thức thực tế: mỗi instance giữ pool nhỏ (ví dụ 5–10) và scale ngang bằng thêm instance với pgbouncer ở giữa khi cần. Đặt idle_in_transaction_session_timeout và statement_timeout từ tầng pool.

  9. Câu 78 — ORM và SQL thuần khi nào dùng cái nào?

    Trả lời: ORM như Prisma cho CRUD, type-safety, migration để tăng tốc dev. SQL thuần hoặc query builder cho báo cáo, query phức tạp, batch update, hoặc khi cần kiểm soát chính xác plan (index hint qua plan shape, CTE, window function nâng cao). Đọc query log ORM để bắt N+1; biết ORM không đồng nghĩa biết SQL, và phần lớn phỏng vấn database hỏi SQL.

    Mở rộng: Với Prisma, $queryRaw có tham số giữ nguyên prepared statement; tuyệt đối không nối chuỗi thành SQL.

  10. Câu 79 — Theo dõi database production bằng gì?

    Trả lời: Ba truy vấn nền: pg_stat_statements cho query chậm và lặp (total_exec_time, calls), pg_stat_activity cho session đang chạy và idle in transaction, pg_stat_replication cho lag. Ngưỡng cảnh báo cache hit ratio tính bằng blks_hit / (blks_hit + blks_read), mục tiêu trên 0.99. ALERT cụ thể: idle-in-transaction kéo dài, số kết nối tiến sát max_connections, replication slot không consume WAL.

  11. Câu 80 — Khi nào chọn logical replication thay vì streaming replication (physical)?

    Trả lời: Chọn streaming replication (physical) khi cần bản sao hot-standby y hệt primary ở cấp block, phục vụ read scaling, HA/failover với cùng major version PostgreSQL. Chọn logical replication khi cần chọn lọc dữ liệu (theo bảng, theo hàng với row filter, theo cột), hoặc cần replicate giữa hai cluster khác major version, hoặc để xây dựng CDC (ví dụ đẩy row change ra Kafka/Debezium) hoặc zero-downtime migration giữa hai PostgreSQL riêng biệt.

    Cơ chế: Physical ship WAL byte-level; logical decode WAL thành row changes qua publication/subscription (wal_level=logical).

    Bẫy: Logical replication không replicate DDL và không replicate sequence counter. Bảng không có PRIMARY KEY cần REPLICA IDENTITY đầy đủ để UPDATE/DELETE hoạt động. Replication slot không được consume (subscriber/CDC chết) sẽ giữ WAL và làm đầy pg_wal; cần giám sát pg_replication_slots và max_slot_wal_keep_size.

    Ví dụ: CDC ra hệ ngoài (Debezium/pgoutput) dùng logical replication. Failover/HA đơn giản trong cùng cluster dùng streaming replication.

  12. Câu 81 — PgBouncer transaction pooling khác statement pooling thế nào, và tại sao Prisma lại cần ?pgbouncer=true với transaction pooling?

    Trả lời: Transaction pooling giữ connection backend trong toàn bộ một transaction (mỗi transaction dùng một connection backend cho đến khi COMMIT/ROLLBACK). Statement pooling giữ connection backend chỉ cho một câu lệnh SQL, trả connection về pool ngay sau khi câu lệnh kết thúc. Vì Prisma dùng prepared statements, ở transaction pooling connection backend có thể thay đổi giữa các transaction kế tiếp hoặc giữa transactions kế tiếp — điều này làm prepared statement không còn sẵn. Do đó Prisma cần ?pgbouncer=true (với PgBouncer ≥1.21 đặt max_prepared_statements > 0 thì Prisma khuyến nghị không cần flag) để query engine chuyển cách xử lý prepared statement sao cho tương thích với transaction pooling.

    Cơ chế: Ở transaction pooling, trạng thái cấp session (bao gồm prepared statements, temp table, SET cấp session) không được bảo toàn giữa transactions. Flag ?pgbouncer=true (với PgBouncer ≥1.21 đặt max_prepared_statements > 0 thì Prisma khuyến nghị không cần flag) điều chỉnh chiến lược prepare của Prisma để tránh phụ thuộc vào việc giữ prepared statement lâu giữa các lượt dùng connection.

    Bẫy: Với transaction pooling, không dùng SET cấp SESSION để lưu context đa transaction — thay vào đó dùng SET LOCAL trong transaction. Temp table cấp session sẽ mất giữa transactions.

    Ví dụ: Với RLS đa tenant, dùng BEGIN; SET LOCAL app.tenant_id = 42; ... COMMIT; thay vì SET app.tenant_id = 42 ở cấp session.

Cách ôn trước phỏng vấn: trả lời miệng từng câu mà không nhìn màn hình, câu nào vấp thì ghi lại tên phần học tương ứng và quay lại phần đó (bản đồ ở đầu section này). Chạy được minh chứng trên psql — EXPLAIN, hai session deadlock, SKIP LOCKED — là phần interviewer nhớ nhất, và nó chỉ đến khi bạn tự gõ lại đoạn code thay vì đọc qua.
