Java như một ngôn ngữ tĩnh

Viết được Java thành thạo tới mức không còn dịch từ ngôn ngữ cũ sang, và hiểu các quy tắc ngầm mà trình biên dịch + JVM áp đặt: giá trị tham chiếu, hợp đồng equals/hashCode, generic erasure, vòng đời bộ nhớ.

5 tuần · khoảng 90 giờ

T1 18 giờ

Tuần 1

Học
  • Cài JDK 25 LTS (Temurin) và kiểm tra bằng java -version; cài Maven 3.9.x. Cài bằng SDKMAN để đổi phiên bản được.
  • Cú pháp Java đọc nhanh: kiểu nguyên thủy và wrapper, mảng một chiều và mảng hai chiều (int[][] là mảng của mảng), String, toán tử, varargs (String...). Kèm khái niệm bytecode, javac, classpath, .jar (JDK vs JRE vs JVM) ở mức đủ dùng để chạy cặp javac rồi java. Đây là phần duy nhất được phép đọc lướt vì đã quen khái niệm.
  • Đọc kỹ phần khác biệt với ngôn ngữ động: Java truyền tham số theo giá trị luôn luôn, kể cả với object — cái được copy là tham chiếu, không phải object.
  • String immutable và String pool: vì sao == trên String so sánh tham chiếu chứ không so sánh nội dung, và khi nào literal được dùng lại từ pool.
  • String vs StringBuilder/StringBuffer: nối chuỗi bằng + trong vòng lặp sinh object trung gian mỗi vòng; StringBuilder nhanh nhưng không thread-safe, StringBuffer thread-safe nhưng chậm hơn — mặc định chọn StringBuilder.
  • Integer cache −128..127: vì sao Integer a=127, b=127; a==b là true nhưng 128==128 là false. Đây là câu hỏi xuất hiện trong corpus.
  • Autoboxing/unboxing và NPE bất ngờ khi unbox null.
  • Null semantics: biến primitive có giá trị mặc định (0, false), reference mặc định null; gọi method trên null ném NPE ngay tại dòng đó. Corpus hỏi nhóm này nhiều nhất trong Java Core — trả lời gọn theo đúng câu hỏi.
Làm
  • Tạo project Maven bằng tay (không dùng IDE wizard) để hiểu pom.xml, src/main/java, src/test/java, plugin compile và surefire.
  • Viết một class Stack và một class LinkedList tự cài, không dùng thư viện, có unit test.
  • Viết 10 đoạn code nhỏ cố tình sai để đọc hiểu thông báo lỗi biên dịch và lỗi runtime: NullPointerException, ClassCastException, ArrayIndexOutOfBoundsException, lỗi generic. Với mỗi lỗi runtime, đọc stack trace từ trên xuống: frame đầu tiên thuộc code mình, phần còn lại là thư viện; tìm dòng Caused by khi có ngoại lệ bọc ngoại lệ.
Checkpoint — bằng chứng đo được

Giải thích bằng lời, không mở tài liệu: (1) vì sao Java gọi là pass-by-value dù truyền object, (2) vì sao so sánh hai Integer 200 bằng == cho false, (3) String pool hoạt động thế nào. Viết câu trả lời vào file notes/java-semantics.md — đây là tài liệu ôn phỏng vấn về sau.

T2 18 giờ

Tuần 2

Học
  • Collections và độ phức tạp: ArrayList vs LinkedList, HashMap (băm, va chạm, resize, treeify khi bucket dài), HashSet, TreeMap, ArrayDeque. Học kèm bảng Big-O chứ không học thuộc API. Thêm cây phân cấp Iterable → Collection → List/Set/Queue (Map đứng riêng), TreeSet, LinkedHashSet, LinkedHashMap khi cần thứ tự, ArrayDeque thay Stack legacy; phân biệt array.length, String.length(), list.size() — ba cách viết cho cùng một ý, dễ nhầm khi viết nhanh.
  • Hợp đồng equals/hashCode: vì sao vi phạm hợp đồng làm mất phần tử trong HashMap mà không báo lỗi gì., kèm toString để debug và Objects.hash/Objects.equals thay vì tự viết dãy 31 * — ngắn hơn, khó sai hơn, đúng bằng cách IDE sinh code.
  • Generics: erasure, wildcard ? extends vs ? super, vì sao không tạo được mảng generic. So sánh với generic ở TypeScript để thấy chỗ nào mạnh hơn chỗ nào yếu hơn. Thêm PECS: ? extends chỉ đọc được, ? super chỉ ghi được — nhớ theo producer/consumer; type inference và diamond <> khi nào compiler tự suy ra được.
  • Map API dùng hằng ngày: getOrDefault, computeIfAbsent, putIfAbsent, merge, và duyệt bằng entrySet thay vì keySet rồi get lại.
  • Tự khai báo generic: viết class và method có tham số kiểu <T>, bounded type (<T extends Comparable<T>>), vì sao không dùng được kiểu nguyên thủy làm tham số kiểu.
  • Exception: checked vs unchecked, vì sao Spring chuyển hầu hết thành unchecked, try-with-resources, thứ tự catch. Cây Throwable ba nhánh: Error không tự phục hồi, RuntimeException là unchecked, phần còn lại checked; throw vs throws — ai gánh trách nhiệm bắt; tự viết exception cho lỗi domain; và mặc định @Transactional chỉ rollback với unchecked, checked không kích hoạt rollback trừ khi khai rollbackFor (Tuần 10).
  • I/O và xử lý chuỗi: Files.readString/BufferedReader với Path, luôn chỉ định StandardCharsets.UTF_8 — encoding sai là nguồn mojibake tiếng Việt; regex validation bằng Pattern/Matcher, compile một lần rồi dùng lại (Pattern thread-safe).
  • Serialization: Serializable, serialVersionUID dùng để làm gì, vì sao transient; và vì sao ngày nay ít dùng Java serialization cho API (dùng JSON) nhưng vẫn gặp trong session cache, RMI, và cảnh báo bảo mật khi deserialize dữ liệu không tin cậy.
  • Optional: dùng đúng chỗ (giá trị trả về) và sai chỗ (field, tham số).
  • Iterator: Iterator, ListIterator, remove() khi lặp — tránh ConcurrentModificationException; dùng removeIf().; fail-fast vs fail-safe: iterator của ArrayList/HashMap ném ConcurrentModificationException ngay khi tập hợp bị sửa giữa chừng, còn concurrent collections (Tuần 4) trả iterator weakly consistent — không ném nhưng dữ liệu có thể cũ.
  • So sánh: Comparable và Comparator — khi nào dùng cái nào, quy tắc compareTo/compare và trả về số âm/0/dương.
Làm
  • Cài đặt HashMap tối giản bằng mảng + linked list để tự thấy cơ chế băm, có test cho trường hợp va chạm.
  • Viết một class Money dùng BigDecimal (không dùng double) có equals/hashCode đúng, dùng nó làm key trong HashMap, viết test chứng minh việc bỏ hashCode làm hỏng tra cứu. Thử RoundingMode khi chia tiền và giải thích vì sao 0.1 + 0.2 != 0.3 với double.
  • Viết một class generic tự khai báo (ví dụ Pair<A,B> hoặc một Box<T> có ràng buộc) kèm method generic tĩnh, rồi dùng nó trong bài Money ở trên.
  • Đếm số lần xuất hiện của từ trong một file văn bản bằng Map<String,Integer> — viết hai bản: một bản dùng containsKey/put, một bản dùng merge hoặc getOrDefault. So sánh độ dễ đọc.
  • Chuyển một module nhỏ từ ngôn ngữ cũ (nên lấy hàm tính toán thuần từ repo NestJS của bạn) sang Java, dùng Optional và exception đúng chỗ.
  • Đẩy repo lên GitHub public ngay từ tuần này: README skeleton (mục tiêu, cách chạy, kết quả), commit nhỏ mỗi ngày làm việc với thông điệp mô tả thay đổi thật. Corpus ghi nhận chuỗi commit kiểu 'update'/'fix'/'final' bị đọc ra ngay là người chưa quen làm việc nhóm.
  • Viết ví dụ dùng Iterator để xóa phần tử an toàn khi lặp và dùng Comparator để sắp xếp danh sách.
Checkpoint — bằng chứng đo được

Tự viết lại bảng độ phức tạp của 8 collection và giải thích vì sao HashMap.get là O(1) trung bình nhưng O(log n) khi bucket bị treeify. Chạy mvn test xanh toàn bộ.

T3 18 giờ

Tuần 3

Học
  • OOP trong Java ở mức dùng được — bốn tính chất (đóng gói, kế thừa, đa hình, trừu tượng) và cách chúng thể hiện: interface vs abstract class, kế thừa và thành phần, final, static, record (bất biến, tự sinh constructor/getter/equals/hashCode), sealed. Kèm bốn mức access modifier (private → package-private → protected → public; protected khác package-private ở chỗ class con khác package vẫn thấy được) và default method trên interface: vì sao Java 8 thêm (bổ sung method mới vào interface cũ không phá implementation cũ), khi nào thay được abstract class, và diamond problem khi hai interface cùng có default method.
  • Constructor: compiler sinh constructor mặc định khi class không viết cái nào (thân là super() gọi constructor cha); chuỗi this()/super() — vì sao super() phải đứng đầu; initializer block static {} và instance block chạy ở đâu trong vòng đời khởi tạo.
  • Overload vs override: overload là đa hình tại biên dịch (compile-time polymorphism), override là đa hình tại runtime (runtime polymorphism); và vì sao method resolution xảy ra lúc compile — khác với dispatch động của ngôn ngữ động.; upcasting/downcasting, instanceof với pattern matching để tránh ClassCastException; field hiding — field truy cập theo kiểu khai báo chứ không dispatch động như method.
  • Inner class, lambda, functional interface (Function, Predicate, Supplier, Consumer), method reference.; anonymous class vs lambda: anonymous giữ được state và nhiều method, lambda chỉ một; biến capture phải effectively final — vì sao Java cấm gán lại biến đã dùng trong lambda.
  • Annotation: @Override để compiler bắt sai chữ ký override, @FunctionalInterface bắt buộc đúng một method trừu tượng, meta-annotation @Retention/@Target, và tự viết @interface — nền để đọc bất kỳ annotation nào của Spring.
  • switch: dạng cổ điển (fall-through, break) so với switch expression (mũi tên, yield, tính đầy đủ khi dùng với enum hoặc sealed); khi nào switch thay được chuỗi if/else dài.
  • enum: khai báo, phương thức, dùng với switch; EnumMap, EnumSet khi phù hợp.
  • Stream API: map/filter/reduce/collect, lazy evaluation, vì sao stream không dùng lại được, khi nào stream làm code tệ hơn vòng lặp.; short-circuit (findFirst, anyMatch, limit dừng ngay khi đủ kết quả, không chạy hết stream) và Collectors (groupingBy, toMap, joining) — thử bằng stream trước khi tự viết vòng lặp gom nhóm.
  • Ngày giờ: java.time, Instant vs LocalDateTime, vì sao không dùng Date/Calendar nữa.
Làm
  • Viết một pipeline xử lý dữ liệu bằng Stream: đọc file CSV, lọc, nhóm, tính tổng, sắp xếp — có test cho từng bước.
  • Cài đặt lại 3 design pattern quen thuộc bằng Java (Strategy, Builder, Repository) và ghi chú khác gì so với cách viết ở ngôn ngữ cũ.
  • Viết record cho các DTO của module tuần 2 và so sánh lượng code với class thường.
Checkpoint — bằng chứng đo được

Trả lời được: khi nào dùng record thay class, khi nào dùng interface thay abstract class, vì sao Stream không nên dùng cho side effect. Có ít nhất 3 pattern đã viết tay, không copy.

T4 18 giờ

Tuần 4

Học
  • JVM ở mức đủ hiểu và đủ nói trong phỏng vấn: cấu trúc bộ nhớ (heap, stack, metaspace), vòng đời object, các garbage collector phổ biến và khi nào chúng chạy, vì sao System.gc() không đảm bảo gì.
  • Classloading, JIT warmup, vì sao ứng dụng Java chậm vài giây đầu rồi nhanh lên (so với V8 của Node để thấy khác biệt vận hành).
  • Công cụ: jps, jstack, jmap, jconsole (có sẵn trong JDK). Chạy thật, đừng chỉ đọc.
  • Vòng đời thread và trạng thái: NEW → RUNNABLE → BLOCKED/WAITING/TIMED_WAITING → TERMINATED; start() (thread mới) khác run() (chạy cùng thread gọi); join, sleep, interrupt — dừng thread đúng bằng kiểm tra cờ ngắt, không dùng Thread.stop (đã bị xóa).
  • Thread và synchronized: mô hình bộ nhớ, race condition, vì sao volatile khác synchronized. Đây là chủ đề hỏi ít trong corpus (14 câu) nhưng phải trả lời được ở mức cơ bản., cộng Java Memory Model ở mức cần: happens-before, và phân biệt visibility với atomicity — volatile đảm bảo thấy giá trị mới nhất nhưng count++ vẫn hỏng vì là read-modify-write.
  • ThreadLocal giữ state theo thread: biến mỗi thread thấy một bản riêng; vì sao phải remove() khi trả thread về pool (thread tái sử dụng giữ lại giá trị cũ); nối trước với MDC correlation ID ở Tuần 17.
  • JUnit 6 và AssertJ: viết test có ý nghĩa, @ParameterizedTest, @Nested, assertion mô tả được lý do fail.
  • Virtual thread (Project Loom): khác platform thread thế nào, khi nào bật (spring.threads.virtual.enabled), và vì sao phải ghi rõ phiên bản khi đo: JDK 21 vẫn bị pinning bởi synchronized, tới JDK 24 (JEP 491) mới hết.
  • Concurrent collections: ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue. Khi nào dùng thay vì đồng bộ hóa toàn bộ.
  • Atomic và CAS: AtomicInteger, AtomicLong, LongAdder. Hiểu ngắn gọn CAS (compare-and-swap) và tại sao tránh lock khi chỉ cần tăng/giảm.
  • java.util.concurrent: ExecutorService và thread pool (Executors.newFixedThreadPool), vì sao không tự new Thread cho mỗi việc; Future/CompletableFuture để chạy việc bất đồng bộ; CountDownLatch khi cần chờ nhiều luồng. Đây là nền để hiểu @Async và thread pool của Tomcat ở phase sau. Học kèm tham số pool thật (corePoolSize, maxPoolSize, hàng đợi, RejectedExecutionHandler khi quá tải) và khác biệt Future.get() chặn chờ vs composition của CompletableFuture (thenApply, exceptionally, allOf).
Làm
  • Chạy một chương trình cố tình gây OutOfMemoryError và một chương trình cố tình gây StackOverflowError; chụp lại thông báo lỗi và hiểu cách đọc chúng.
  • Dùng jstack bắt deadlock từ một chương trình hai thread tự viết, đọc hiểu output.
  • Viết 20 unit test cho thư viện ở tuần 1–3, mục tiêu nhánh phủ thật chứ không phải số test.
  • Chụp heap dump cho chương trình OOM bằng jmap/jcmd GC.heap_dump, tìm dominator và retained size. Lập bảng so sánh thread-per-request (Tomcat mặc định ~200 thread) với virtual thread trên JDK 25, ghi số đo kèm phiên bản JDK.
  • Viết ví dụ đơn giản với AtomicInteger hoặc so sánh hiệu quả giữa synchronized và LongAdder (ghi nhận kết quả ngắn gọn).
  • Viết một chương trình dùng ExecutorService cố định 4 luồng xử lý 100 task, đo thời gian so với chạy tuần tự; rồi gọi shutdown() và giải thích vì sao thiếu nó thì JVM không thoát.
Checkpoint — bằng chứng đo được

Giải thích được luồng: object sinh ra ở đâu, khi nào được thu hồi, vì sao heap chia thế hệ. Chứng minh bằng output jstack/jmap chụp lại được, không phải bằng lời kể.

Tuần 5

Học
  • Build lifecycle của Maven: validate → compile → test → package → verify → install, scope của dependency (compile/provided/test), dependency mediation và xung đột phiên bản; quá trình build cơ bản: javac → bytecode → classpath → chạy bằng java; package thành .jar (mvn package) và ý nghĩa của file jar.
  • Multi-module Maven: parent POM, dependencyManagement, vì sao doanh nghiệp tách module.
  • Logging: SLF4J làm mặt tiền, Logback làm implementation, level, vì sao không dùng System.out.println và vì sao không nên nối chuỗi trong log.
  • Đọc JDK 25 có gì mới ở mức dùng được: record patterns, pattern matching cho switch, text block, var.
  • Khác biệt Java 17 / 21 / 25 ở mức trả lời được khi công ty còn chạy Java 17: record, text block, pattern matching, virtual thread, và những gì JDK 25 thêm. Maven toolchain để build trên nhiều JDK trong cùng một máy.
  • Reflection (java.lang.reflect) ở mức đọc hiểu: Class, Method, Field; Spring dùng reflection ở đâu (đọc annotation, khởi tạo bean, tạo proxy) và vì sao nó chậm — biết đọc là đủ, không cần thuộc API.
Làm

Kết quả cuối lộ trình

Năng lực đạt được

Tự chấm bằng cách đối chiếu với JD: mỗi dòng dưới đây phải trả lời được câu hỏi phỏng vấn tương ứng mà không cần tra cứu.

Java và JVM

  • Viết Java không cần dịch từ ngôn ngữ cũ: generic, lambda, Stream, record, sealed, Optional dùng đúng chỗ.
  • Giải thích được pass-by-value với object, String pool, Integer cache −128..127, hợp đồng equals/hashCode.
  • Cài lại được HashMap bằng mảng + linked list và giải thích treeify khi bucket dài.
  • Đọc được jstack/jmap, phân biệt heap/stack/metaspace, giải thích GC ở mức đủ nói trong phỏng vấn.
  • Xử lý exception đúng: checked vs unchecked, try-with-resources, không nuốt lỗi.

Build, dependency và test

  • Maven: vòng đời build, scope dependency, dependency mediation, mvn dependency:tree khi có xung đột phiên bản.
  • Project multi-module với parent POM và dependencyManagement.
  • JUnit 6 + Mockito 5 + AssertJ: test có ý nghĩa, tham số hóa, assertion đọc lên hiểu ngay nguyên nhân fail.
  • Testcontainers 2.x: test tầng repository trên PostgreSQL thật thay vì H2.
  • JaCoCo: đọc báo cáo độ phủ để tìm nhánh lỗi chưa test, không chạy theo con số.

Spring Boot 4

  • DI hiểu bản chất: vòng đời bean, scope, vì sao constructor injection, vì sao singleton inject prototype là sai.
  • Auto-configuration: đọc file .imports, tự viết được một starter tối giản.
  • REST đúng chuẩn: binding, validation Bean Validation 3.1, ProblemDetail cho lỗi, versioning khi cần.
  • Cấu hình theo profile, @ConfigurationProperties có validate, không nhét secret vào repo.

Tầng dữ liệu

  • JDBC thuần trước ORM: DataSource, PreparedStatement, transaction tự quản lý bằng setAutoCommit(false).
  • Phân biệt JPA (đặc tả) / Hibernate (implementation) / Spring Data JPA (tầng bọc) — câu hỏi lặp lại nhiều lần trong corpus.
  • Ánh xạ quan hệ hai chiều, phía sở hữu khóa ngoại, và bảng mặc định fetch type: @ManyToOne/@OneToOne EAGER, @OneToMany/@ManyToMany LAZY.
  • Phát hiện và sửa N+1 bằng join fetch, @EntityGraph, @BatchSize — kèm số câu SQL đo được trước/sau.
  • @Transactional hiểu ranh giới proxy: vì sao gọi nội bộ cùng class làm mất annotation.
  • Optimistic lock bằng @Version; phân biệt với pessimistic lock và biết khi nào dùng cái nào.
  • Migration bằng Flyway: viết migration an toàn theo trình tự thêm-nullable → backfill → thắt ràng buộc.

Hiệu năng và dữ liệu lớn

  • Thiết kế index theo truy vấn thật, hiểu vì sao bọc hàm lên cột làm mất index.
  • Đọc EXPLAIN ANALYZE, chỉ ra nút cổ chai, phân biệt rows ước lượng với rows thực tế.
  • Đưa ra con số: truy vấn chậm bao nhiêu ms trước index và còn bao nhiêu sau, trên bao nhiêu dòng.

Cache, queue, bất đồng bộ

  • Spring Cache với TTL tường minh; biết vì sao gọi nội bộ không kích hoạt cache.
  • Redis: TTL, INCR+EXPIRE, Lua script cho thao tác nguyên tử, chống cache stampede.
  • Kể được ba chế độ hỏng của cache bằng ví dụ đã tái hiện: mất cache khi restart, dữ liệu cũ, cache xóa nhầm.
  • Phân biệt dữ liệu tái tạo được (được phép lên cache) và dữ liệu không tái tạo được (phải xuống database).
  • Kafka: partition, offset, consumer group, vì sao thứ tự chỉ đảm bảo trong một partition.
  • Outbox pattern để không mất message giữa ghi database và publish; consumer idempotent chịu được nhận trùng.

Chỗ người chuyển ngôn ngữ hay vấp

Bẫy khi chuyển sang Java

Hiểu nhầm mang từ ngôn ngữ động sang Java, kèm cách phát hiện. Mỗi dòng là thứ người phỏng vấn hỏi để kiểm tra bạn hiểu Java hay chỉ chép được cú pháp.

  • Gán lại tham số object rồi mong caller thấy. Ở JavaScript gán lại biến tham chiếu bên trong hàm sẽ ảnh hưởng ra ngoài; ở Java thì không. Sửa field của object truyền vào thì caller thấy, còn x = new Foo() chỉ đổi bản sao cục bộ. Phát hiện bằng cách tự hỏi: hàm này trả về gì, hay đang trông chờ tác dụng phụ?
  • Dùng == để so nội dung. Java so danh tính với mọi object, kể cả String. Phải dùng equals. Cái bẫy phụ nguy hiểm hơn: Integer cache từ −128 đến 127 làm == cho kết quả đúng khi bạn thử với số nhỏ, rồi sai ở production khi giá trị vượt khoảng đó.
  • Coi {} như map. JavaScript object là map với key luôn là chuỗi; Java không có literal cho map và key phải cài equals/hashCode đúng, nếu không thì get trả null mà không báo lỗi gì.
  • Mong array có map/filter/reduce/spread. Array trong Java là cấu trúc thô, không có method. Phải đổi sang List rồi dùng Stream. Bẫy nhỏ nhưng hay gặp: Arrays.asList trả về list có kích thước cố định, gọi add là ném UnsupportedOperationException.
  • Nghĩ Optional là cách thay thế null ở mọi nơi. Optional dành cho giá trị trả về. Nhét nó vào field hay tham số làm code khó đọc hơn chứ không an toàn hơn. Java không có undefined, chỉ có null, và trình biên dịch không giúp bạn ở chỗ này.
  • Mang mô hình một luồng event loop sang. Đây là khác biệt vận hành lớn nhất. Node chạy một luồng, I/O không chặn, nên gọi database trong vòng lặp là bình thường. Java chạy thread-per-request: chặn thì được, nhưng thread pool có giới hạn (Tomcat mặc định khoảng 200), nên một đoạn chặn lâu hoặc gọi mạng thiếu timeout sẽ làm cạn pool và sập cả ứng dụng. Lỗi này không tồn tại ở Node nên bạn chưa có phản xạ phòng nó.
  • Chờ có await. Java không có. Mọi thứ mặc định là đồng bộ. Muốn bất đồng bộ phải chủ động: CompletableFuture, @Async, hoặc đẩy sang message queue.
  • Tưởng @Transactional, @Cacheable, @Async là annotation trang trí. Cả ba chạy qua proxy, nên gọi từ một method khác trong cùng class là mất tác dụng mà không có cảnh báo nào. NestJS không có cái bẫy tương đương vì interceptor nằm ở tầng HTTP, không nằm ở tầng method.
  • Mang tư duy ORM không trạng thái sang JPA. Prisma là query builder: gọi là có dữ liệu, object trả về là plain object. JPA giữ một session có trạng thái, entity nằm trong đó được quản lý, sửa field là tự động update khi flush, và truy cập quan hệ lazy sau khi session đóng thì ném LazyInitializationException. Đây là cú sốc lớn nhất khi chuyển từ NestJS + Prisma sang Spring + JPA. Phản xạ cần luyện: luôn tự hỏi entity này còn managed không, và transaction còn mở không.
  • Tìm include của Prisma. Ở JPA quan hệ được khai trên entity, và mặc định fetch type quyết định bạn có N+1 hay không. Không có chỗ nào khai một lần rồi mọi truy vấn đều kèm dữ liệu.
  • Chờ migration tự sinh. Prisma migrate so schema rồi sinh SQL; Flyway bắt bạn viết tay và không cho sửa file đã chạy (checksum sẽ báo lệch). Tư duy đúng là mỗi migration là một bước không thể quay lại trên production, nên phải viết theo trình tự thêm-nullable → backfill → thắt ràng buộc.
  • Coi entity là nguồn sự thật duy nhất. schema.prisma là nguồn sự thật ở Prisma; ở JPA entity và database phải khớp nhau, và lệch nhau thì lỗi chỉ lộ ra lúc chạy chứ không lúc build.
  • Trả Entity thẳng ra response. Express res.json(obj) xử lý được mọi thứ nên thói quen này dễ mang sang. Jackson sẽ serialize cả đồ thị object, nổ vòng lặp vô hạn với quan hệ hai chiều, và làm lộ field nội bộ. Luôn có DTO request/response riêng.
  • Bọc mọi lỗi thành RuntimeException. JavaScript cho throw bất cứ thứ gì và catch bắt hết. Java phân biệt checked và unchecked, và trình biên dịch buộc bạn khai báo. Bọc tất cả thành một loại exception rồi ném lại là cách nhanh nhất để mất ngữ nghĩa lỗi.
  • Coi pom.xml như package.json. npm cài phẳng và lockfile ghim cả cây; Maven phân giải phiên bản theo quy tắc nearest-wins và có scope (compile, provided, test). Xung đột phiên bản ở Maven lộ ra lúc chạy chứ không lúc cài, nên mvn dependency:tree là công cụ đầu tiên khi có lỗi lạ.
  • Chờ hot reload như npm run dev. JVM khởi động chậm, devtools chỉ reload được phần hạn chế. Vòng phản hồi chậm dễ làm bạn bỏ qua việc chạy test thường xuyên — đây là chỗ tụt chất lượng âm thầm. Bù lại bằng cách viết test nhanh ở tầng service.
  • Học theo tutorial cũ mà không kiểm tra phiên bản. Phần lớn nội dung Spring trên mạng dạy 2.x và 3.x. javax.* biến mất từ Spring Boot 3.0, cả cây package đổi sang jakarta.*; WebSecurityConfigurerAdapter và antMatchers bị gỡ ở Spring Security 6.0; and() và authorizeRequests bị gỡ ở 7.0; Spring Boot 4 gỡ tiếp @MockBean. Code copy về không biên dịch được là dấu hiệu nhận ra, không phải bạn viết sai. Hãy đổi nguồn.
  • Chỉ đề phòng lỗi biên dịch, bỏ qua lỗi im lặng của Spring Boot 4. Phần ồn ào thì dễ thấy: @MockBean/@SpyBean bị gỡ hẳn, phải dùng @MockitoBean/@MockitoSpyBean; khối spring-boot-autoconfigure khổng lồ tách thành module theo công nghệ. Nhưng spring-boot-starter-web thì vẫn chạy — nó chỉ chuyển sang deprecated, nhường chỗ cho spring-boot-starter-webmvc. Thứ thật sự cắn mà không báo gì là các property bị đổi tên: spring.jackson.read.* → spring.jackson.json.read.*, spring.session.redis.* → spring.session.data.redis.*, spring.dao.exceptiontranslation.enabled → spring.persistence.exceptiontranslation.enabled. Property sai tên không gây lỗi, chỉ lặng lẽ không có tác dụng. Cùng nhóm đó: khai báo ObjectMapper bean không còn thay được mapper JSON nữa, phải là JsonMapper.
  • Mong structural typing như TypeScript. Java là nominal: muốn truyền vào một interface thì phải khai báo implement đúng interface đó, không đủ hình dạng là được. Boilerplate nhiều hơn, nhưng bù lại lỗi lộ ra lúc biên dịch thay vì lúc chạy.
  • Chiến đấu với erasure của generic. Java xóa thông tin generic lúc chạy, nên không tạo được new T[] và không viết được instanceof List<String>. Đây là giới hạn của ngôn ngữ, không phải chỗ để bạn chứng minh mình thông minh.

Đối phó

Rủi ro và đối sách

Những chỗ lộ trình có thể gãy. Đọc trước khi bắt đầu để nhận ra sớm thay vì sau ba tháng.

  • Sáu tháng là đường gấp, không phải đường chuẩn. howlongfor.com ước 8–12 tháng để lên mức advanced khi xuất phát từ ngôn ngữ khác; codingshuttle nói 20–30 tuần chỉ để đi hết khái niệm, rồi nhân đôi thời gian đó mới gọi là thành thạo. Đối sách: mốc cắt nằm ở tuần 18. Hết tuần 18 mà dự án 1 chưa chạy được thì bỏ phase 4 và đi phỏng vấn bằng những gì đang có — Java core, Spring Boot, JPA, SQL, bảo mật và Docker đã đủ cho phần lớn JD middle ở Hà Nội và TP.HCM.
  • Microservices, Kafka, Redis và MongoDB đều là mục tùy chọn, không phải điều kiện tuyển dụng. Mọi nguồn khảo sát đều xếp chúng sau khi đã có một dự án Spring Boot chạy được, và trong mẫu 20 tin trang đầu của itviec (cả trang Java Spring Boot lẫn trang fresher-java) không tin nào lấy chúng làm yêu cầu bắt buộc duy nhất. Lưu ý cách đọc: trang fresher-java của itviec trộn cả tin Principal/Staff/Senior, nên đừng coi đó là danh sách đúng cấp fresher. Đối sách: phase 3 và phase 4 vẫn đặt chúng ở đây vì mục tiêu là mức middle, và vì nhóm 183 câu middle/senior trong corpus hỏi nặng về transaction xuyên service cùng xác thực giữa các service. Nếu đổi mục tiêu sang fresher, dừng sau tuần 18 là đủ.
  • Phần thời gian dành cho thuật toán là ước lượng, không phải số đo. Trong 1.796 câu, chữ LeetCode chỉ xuất hiện đúng 2 lần, và cả hai đều là lời khuyên dành cho ứng viên chứ không phải câu hỏi thi: một ứng viên tự nhận hổng DSA và nói sẽ luyện trên đó, một ứng viên khác nhắc "các trang luyện code" khi so sánh Selection sort với Merge sort. Bài live-coding thật trong corpus chỉ 2–3 phút. Con số 20–25% là suy đoán của tôi, không phải số đo từ corpus. Đối sách: coi đây là mặc định rồi chỉnh theo JD của 10 công ty bạn nhắm. Chỉ nhóm có vòng thuật toán riêng (ngân hàng, công ty sản phẩm lớn) mới cần luyện thêm.
  • Trang này không có bảng lương theo cấp, và đó là chủ đích. Các nguồn khảo sát lương Java của itviec và TopDev đều trả 404 khi truy cập, tìm kiếm không trả về số liệu nào kiểm chứng lại được, nên không có con số nào đủ tin để đưa vào đây. Đối sách: đọc mức lương ghi trong JD đang tuyển, hoặc hỏi trực tiếp ở buổi phỏng vấn sớm. Đừng lấy số trên blog làm kỳ vọng đàm phán.
  • Máy hiện tại có JDK 21, lộ trình dùng JDK 25. Thực nghiệm virtual thread trên JDK 21 sẽ vẫn thấy hiện tượng pinning khi gặp synchronized, vì JEP 491 chỉ gỡ được ở Java 24. Làm thực nghiệm trên bản cũ rồi kết luận về hành vi của JDK 25 là sai. Maven cũng chưa cài trên máy. Đối sách: cài JDK 25 và Maven bằng SDKMAN ngay tuần 1, trước mọi việc khác.
  • Spring Boot 4.0 hết hỗ trợ OSS ngày 31/12/2026, tức trước khi bạn học xong. Dòng duy nhất còn được hỗ trợ là 4.1. Trong khi đó nhiều JD ở Việt Nam vẫn ghi 3.x, thậm chí 2.x. Đối sách: học trên 4.1 nhưng vẫn đọc hiểu được 3.5 để không khớp khi vào công ty dùng bản cũ. Đây là lý do phần Spring Security và JPA trong lộ trình dạy cả cách nhận ra API đã bị gỡ.
  • Phần lớn tài liệu Spring trên mạng đã lỗi thời. WebSecurityConfigurerAdapter, antMatchers, mvcMatchers bị gỡ từ Spring Security 6.0; and() và authorizeRequests bị gỡ ở 7.0; @MockBean/@SpyBean bị gỡ ở Spring Boot 4. Đây là rủi ro tốn thời gian lớn nhất của cả lộ trình, vì nó không báo lỗi rõ ràng: code không biên dịch được khiến bạn tưởng mình sai chứ không nghĩ tài liệu sai. Đối sách: chỉ đọc docs.spring.io và các bài có ghi rõ phiên bản. Gặp javax. trong ví dụ thì đóng tab.
  • Corpus có 77,0% là câu hỏi mức intern/fresher (1.383/1.796 câu). Vì vậy thứ tự chủ đề bị kéo về phía câu hỏi cơ bản, còn nhóm middle/senior chỉ chiếm 183 câu. Đối sách: mục phỏng vấn trong trang này tách riêng tần suất nhóm middle/senior. Khi ôn, đọc phần đó trước rồi mới quét phần còn lại.

Phần thị trường vì thế yếu hơn phần kỹ thuật, vì nó dựa trên tag đọc trực tiếp từ danh sách tin tuyển dụng itviec chứ không phải một khảo sát đầy đủ. Đối sách: coi mọi nhận định về thị trường trong trang này là mẫu nhỏ, tự kiểm lại bằng cách đọc 20 JD đang mở ở Hà Nội và TP.HCM.
  • Hầu hết lộ trình tiếng Việt khảo sát được đều do trung tâm đào tạo viết.
